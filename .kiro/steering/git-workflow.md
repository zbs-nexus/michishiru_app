# Git ワークフロー — ミチシル

---

## ブランチ戦略

| ブランチ | 役割 | 自動デプロイ先 | 直接プッシュ |
|---|---|---|---|
| `main` | 本番 | prod 環境 | 禁止（PRのみ） |
| `develop` | 開発統合 | dev 環境 | 禁止（PRのみ） |
| `feature/...` | 機能開発（レビュー対象） | なし | 禁止（PRのみ） |
| `fix/...` | バグ修正（レビュー対象） | なし | 禁止（PRのみ） |
| `test/...` | 作業用 | なし | 可 |

### フロー

```
test/NZ-X → feature/NZ-X-<内容> → develop → main
                                     ↓         ↓
                                  dev環境   prod環境
```

`develop` と `main` への push は `.github/workflows/deploy.yml` が自動デプロイを実行する。マージ＝デプロイであることを意識すること。

### ブランチ名の規則

| 種別 | 命名規則 | 例 |
|---|---|---|
| 作業用 | `test/NZ-<課題番号>` | `test/NZ-58` |
| 機能開発 | `feature/NZ-<課題番号>-<内容>` | `feature/NZ-84-cd-pipeline` |
| バグ修正 | `fix/NZ-<課題番号>-<内容>` | `fix/NZ-15-route-validation` |
| 緊急修正 | `hotfix/NZ-<課題番号>-<内容>` | `hotfix/NZ-20-api-timeout` |

- `<内容>` は kebab-case（全小文字・ハイフン区切り）で書く
- 課題番号が割り当てられていない作業は `<内容>` のみでよい（例: `feature/cd-pipeline`）
- 課題番号と内容の両方を入れる理由: 番号だけでは何のブランチか分からず、内容だけでは課題と紐付かない

**課題番号（`NZ-X`）の採番ルールは未決定。** `naming-conventions.md` の「未決定事項」を参照。

## コミットメッセージ規約

### フォーマット

```
<種別>: <変更内容の要約>
<種別>(NZ-<課題番号>): <変更内容の要約>   ← 課題番号がある場合
```

### 種別一覧

| 種別 | 用途 |
|---|---|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `refactor` | リファクタリング |
| `docs` | ドキュメント・規約 |
| `style` | スタイル変更 |
| `test` | テスト |
| `chore` | 雑務 |
| `ci` | CI/CD の設定変更 |

### ルール

| ルール | 必須/任意 | 詳細 |
|---|---|---|
| 種別を先頭に付ける | **必須** | `feat:` `fix:` など |
| 課題番号を含める | 課題がある場合は必須 | `feat(NZ-84):` の形。採番前の作業では省略可 |
| 1行目は50文字以内 | 必須 | |
| 日本語OK | - | |
| 1コミット = 1つの変更 | 必須 | |

種別なしのコミット（例: `命名規則作成`）は禁止。何の変更か履歴から判断できなくなる。

## PR手順

### 前提条件

PR作成前に以下を実行し、すべて通っていることを確認する。

| 条件 | 確認方法 |
|---|---|
| 動作確認済み | ローカルで該当機能を操作して確認（`npm run dev` でフロント＋APIを同時起動） |
| ESLint エラーなし | `frontend/` で `npm run lint` |
| フロントのビルド通過 | `frontend/` で `npm run build` |
| バックエンドのテスト通過 | `backend/` で `npm test` |
| IaCのビルド・テスト通過（IaC変更時） | `iac/` で `npm run build` と `npm test` |
| CloudFormation の合成通過（IaC変更時） | `iac/` で `npx cdk synth` |
| コンフリクトなし | |

補足:

- フロントエンドのテストはツール未決定のため、現時点では対象外
- `.github/workflows/ci.yml` は現在 `main` 向けPRでのみ自動実行される。`develop` 向けPRでは自動チェックが走らないため、上記をローカルで必ず実行すること

### PR の方向

| フロー | タイミング | マージ方法 |
|---|---|---|
| `test/...` → `feature/...` | 動作確認完了後 | 通常 merge |
| `feature/...` → `develop` | レビュー承認後 | Squash merge |
| `develop` → `main` | dev環境で動作確認後 | 通常 merge |

`develop` → `main` を通常 merge にする理由: `develop` 上の各機能のコミット履歴を `main` に残すため。Squash すると本番リリースが1コミットに潰れ、問題発生時に切り戻す単位が粗くなる。

### レビュールール

| ルール | 詳細 |
|---|---|
| レビュアー最低1名 | |
| 承認後にマージ | |
| マージ後ブランチ削除 | `develop` と `main` は削除しない |
| コンフリクトはPR作成者が解消 | |
| `develop` / `main` へのマージはデプロイを伴う | マージ前にデプロイして問題ないか確認する |

### レビューで確認すること

| 観点 | 参照 |
|---|---|
| 命名が規則に沿っているか | `naming-conventions.md` |
| 用語辞書にない語を使っていないか | `naming-glossary.md` |
| レイヤーの責務を守っているか | `back-layer-architecture.md` |
| コンポーネントが肥大化していないか | `component-design.md` |
| AWSリソース名が規則に沿っているか | `iac-rules.md` |

`naming-conventions.md` の「例外一覧」に載っているものは指摘不要。

## 規約ファイル自体を変更する場合

`.kiro/steering/` 配下のファイルを変更するときも、通常の開発と同じ手順を踏む。

| ルール | 詳細 |
|---|---|
| 直接 `main` / `develop` にプッシュしない | PRを出す |
| コミット種別は `docs` を使う | 例: `docs(NZ-58): 用語辞書に spot を追加` |
| 用語辞書の変更はチーム全員に通知する | コード全体に影響するため |
| 各ファイル末尾の更新履歴に追記する | いつ何を変えたか追えるようにする |

---

## やってはいけないこと

| NG | 理由 |
|---|---|
| `main` / `develop` に直接プッシュ | レビューなし。かつ即デプロイされる |
| 動作確認せずに `develop` にマージ | dev環境が壊れ、他メンバーの確認が止まる |
| 種別なしのコミットメッセージ | 履歴から変更内容が判断できない |
| 1 PR に複数課題 | revert しづらい |
| コンフリクト放置 | |
| マージ後ブランチ残す | |
| `--force` プッシュ | 他メンバーの作業消失 |
| `--no-verify` でフックを飛ばす | チェックが機能しなくなる |
