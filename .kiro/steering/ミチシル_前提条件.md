# ミチシル - ルート作成地図アプリ 前提条件書

## プロジェクト概要

| 項目 | 内容 |
|------|------|
| アプリ名 | ミチシル |
| 種別 | ルート作成地図アプリ（散歩向け） |
| チーム人数 | 6人 |
| 目的 | ユーザーが条件を入力し、自動で散歩ルートを生成・案内するアプリ |

---

## システム構成（AWS） — 暫定

**現段階で確定している構成**は以下のサーバーレスアーキテクチャ。**AWS Amplify は使用しない。**

地図API等の外部サービスはこれから追加していくため、この構成は確定版ではない。要素が決まり次第、本セクションの構成図・表を更新すること。

```
                        ┌── / ─────────▶ [S3]（静的ファイル）
[user] ──▶ [CloudFront] ┤
                        └── /api/* ────▶ [API Gateway] ┬─ GET  ─▶ [Lambda getRoute]    ──▶ [DynamoDB]
                                                       │
                                                       └─ POST ─▶ [Lambda createRoute] ─┬─▶ [Location Service Places]
                                                                                        ├─▶ [Amazon Bedrock]
                                                                                        └─▶ [Location Service Routes]

[user] ──(ログイン・ユーザー登録)──▶ [Amazon Cognito ユーザープール]

[GitHub Actions] ──(OIDC)──▶ [IAM Role] ──▶ [CloudFormation]（AWS CDK）
```

ログインとユーザー登録はブラウザから Cognito を直接呼ぶ（API Gateway を経由しない）。

フロントとAPIを同一の CloudFront ドメインで配信するため、**同一オリジンとなり CORS 設定は不要**。

### 各サービスの役割

| サービス | 役割 |
|---|---|
| Amazon S3 | ビルド済みフロントエンド（Vue SPA）の静的ファイルを格納する |
| Amazon CloudFront | S3 のコンテンツを配信し、`/api/*` を API Gateway へ転送する。ユーザーのエントリーポイント |
| Amazon API Gateway | REST API のエンドポイントを提供する。HTTPS でのみ受け付ける。ログイン後に呼ぶ3メソッド（`GET`/`POST /api/v1/routes`、`GET /api/v1/conditions`）は Cognito オーソライザーで保護し、ログイン前に呼ぶ照合API（`POST /api/v1/password-reset-verifications`）だけを対象外とする |
| AWS Lambda | バックエンドのビジネスロジックを実行する（Node.js）。`getRoute`（既存ルート取得）/ `createRoute`（ルート生成）/ `getConditions`（検索条件マスタ取得）/ `verifyPasswordResetTarget`（パスワード再設定前の照合）の4関数 |
| Amazon DynamoDB | ルート・スポット等のデータを永続化する |
| Amazon Location Service（Places） | 現在地の周辺スポットをカテゴリごとに検索する（Step 3） |
| Amazon Bedrock | スポットの選定とルートの解説文を生成する（Step 4）。モデルは `jp.anthropic.claude-haiku-4-5` |
| Amazon Location Service（Routes） | 道なりの徒歩経路・距離・所要時間を算出する（Step 5） |
| Amazon Location Service（Maps） | 地図タイルを配信する（Step 6）。フロントの MapLibre GL が参照する |
| Amazon Cognito（ユーザープール） | ログインとユーザー登録を担う。ユーザー名でサインインし、メールアドレスは確認コードで検証する。フロントは Amplify（`aws-amplify/auth`）経由で呼ぶ |
| AWS CDK（TypeScript） | インフラをコードで定義する（`iac/`） |
| GitHub Actions | CI（build / lint / test）と CD（`cdk deploy`）を実行する |
| IAM（OIDC） | GitHub Actions が長期キーなしでデプロイロールを引き受ける |

### 構成上の前提ルール

| ルール | 詳細 |
|---|---|
| Amplify は使わない | ホスティングは S3 + CloudFront、API は API Gateway + Lambda で構成する |
| フロントは SPA として S3 に配置する | サーバーサイドレンダリングは行わない |
| API は API Gateway 経由でのみ公開する | Lambda を関数URL等で直接公開しない |
| API は CloudFront の `/api/*` 経由で配信する | フロントと同一オリジンになるため CORS 設定が不要 |
| S3 バケットは直接公開しない | CloudFront の OAC 経由でのみアクセスさせる |
| 環境（dev/prod）は分離する | CDK でスタックごと分ける（`Michishiru-dev` / `Michishiru-prod`）。テーブル名は `Route-<環境>`、ユーザープール名は `michishiru-users-<環境>` |
| AWSリソースの識別子をコードに直書きしない | ユーザープールIDのように環境ごとに変わる値は、`cdk deploy` の出力（`--outputs-file`）から取り出してビルドへ渡す。人が変数へ登録する運用にはしない |
| デプロイは GitHub Actions 経由で行う | ローカルからの本番デプロイは禁止。OIDCでロールを引き受ける |
| 段階的に構成する | 既定はフロントのみ。バックエンドは `-c withBackend=true` で有効化する |

### 今後追加予定の要素

構成に追加する際は、この表から「各サービスの役割」へ移し、構成図も更新する。

| 要素 | 想定用途 | 状態 |
|---|---|---|
| 地図スタイルの認証方法 | ブラウザから Location Service（Maps）のタイルを取得する手段 | 未定。API キーか Cognito か決めていない。未設定の間は OpenStreetMap のラスタタイルで代替している（`frontend/src/constants/mapDefaults.js`） |
| ジャンルの受け渡し形式 | `createRoute` に渡すジャンルを ID（`nature`）と名称（`自然`）のどちらにするか | **未決定。現状は不整合がある。** `getConditions` は `genreId`（英語ID）を返しフロントはそれを送るが、`createRoute` はジャンルマスタを日本語の `ジャンル名称` で引くため一致しない |
| マスタテーブルのCDK管理 | `michimaster` / `michishiru_genremaster_akutsu` / `michishiru_categorymaster_akutsu` | 未対応。3つともコンソールで手動作成されており、命名規則・環境分離・属性名の規約から外れている |
| 照合APIの保護 | `POST /api/v1/password-reset-verifications` の悪用を防ぐ | 未対応。パスワード再設定の前にユーザー名とメールアドレスの組み合わせを照合するため、ログイン前に呼べる必要がある。認可で守れないので、回数制限（API Gateway のスロットリング / WAF）で総当たりを抑える方針を決める |
| ユーザー単位のデータ管理 | 保存したルートをユーザーごとに分ける | 未定。DynamoDB のキー設計に Cognito の `sub` を含めるかを決める |
| マスコットのレベルの決め方 | ユーザーの実績に応じて Lv.1〜Lv.10 の姿を切り替える | 未対応。Lv.2〜Lv.10 の画像と、レベルを決める実績（累積距離・散歩回数など）のしきい値が未定。実績の保存先も未定（`walkStore` は1回の散歩分しか持たず、リロードで消える）。画像とレベルの対応は `frontend/src/constants/mascotLevels.js` に用意済みで、画像を追加して `mascotImage` の `null` を差し替えるだけで有効になる |

### 外部API利用時のルール

追加する外部APIは、決定前から以下を前提とする。

| ルール | 理由 |
|---|---|
| APIキー・シークレットをフロントに埋め込まない | 静的ファイルは誰でも取得できるため漏洩する |
| 外部APIの呼び出しは Lambda（Repository層）から行う | キーをサーバー側に閉じ込める。レイヤー責務にも合致する |
| キーは環境変数（本番は Secrets Manager / SSM）で管理する | リポジトリにコミットしない |
| フロントのSDKで地図を描画する場合はキーに利用制限をかける | ブラウザで動かす都合上露出するため、リファラ・API種別で制限する |

## ユーザーストーリー一覧と処理フロー

本アプリは以下のユーザーストーリーに基づき、画面遷移・処理フローが構成される。  
全メンバーはこのフローを前提として各担当機能を実装すること。

---

### US-1: 情報入力（ホーム）画面

**ストーリー**  
散歩アプリの利用者として、情報入力（ホーム）画面がほしい。なぜなら散歩のルート検索の条件になるからだ。

**受け入れ条件**

- ヘッダーに「散歩の条件を決める」と記載があること
- 目的を１つ選択できるボタンがあること
- ジャンルを１つ選択できるボタンがあること
- 距離を入力できること
- ルート作成ボタンがあること

---

### US-2: ルート作成処理

**ストーリー**  
散歩アプリの使用者として、ルートを作成したい。なぜなら、散歩のルートを自動で作成したいからだ。

**受け入れ条件**

- ルート作成ボタンが押下できること
- ロード画面を表示させること
- ホーム画面から目的、ジャンル、距離の条件が取得できること
- 条件に合うスポットをDBやAIに選定させること
- 選定させたスポットを地図アプリに渡すこと
- スポットを巡る移動距離とルートを作成すること

---

### US-3: ルート提案モーダル

**ストーリー**  
散歩アプリの利用者として、ルート提案モーダルが欲しい。なぜなら生成された散歩ルートを確認したいからだ。

**受け入れ条件**

- 作成されたルートを地図上に描画すること
- 検索条件が保持されていること
- 確認モーダルを表示すること
- モーダルに移動距離を表示すること
- モーダルに再作成ボタンを表示すること
- モーダルにルート決定ボタンを表示すること

---

### US-4: ルート決定（ナビ開始）

**ストーリー**  
散歩アプリの利用者として決定ボタンを押下したときに、ナビを開始したい。なぜなら提案されたルートで歩きたいからだ。

**受け入れ条件**

- モーダルが非表示されること

---

### US-5: ルート再作成

**ストーリー**  
散歩アプリの利用者として再作成ボタンを押下したい。なぜなら別のルートに変更したいからだ。

**受け入れ条件**

- 再作成ボタンを押下したときにロード画面に遷移すること
- 保持した検索条件をもとにUS-2の処理を再実行できること

---

### US-6: 案内画面表示

**ストーリー**  
散歩アプリの利用者として、案内画面を表示してほしい。なぜならどのルートで歩くかを見たいからだ。

**受け入れ条件**

- 終了ボタンを画面下部に追加する

---

### US-7: 案内画面終了

**ストーリー**  
散歩アプリの利用者として、案内画面を終了したい。なぜなら、散歩を終了したいからだ。

**受け入れ条件**

- ルート終了ボタン押下すると、確認ポップアップが画面中央に表示され、「ルート案内終了しますか」のメッセージが表示される
- 確認ポップアップの右に「はい」ボタン、左に「いいえ」ボタンが表示される

---

### US-8: 散歩結果確認

**ストーリー**  
散歩アプリの利用者として、散歩の結果を確認したい。なぜなら、距離や訪れたスポットを確認したいからだ。

**受け入れ条件**

- はいボタンを押下すること
- 確認ポップアップを非表示にすること
- 散歩結果モーダルを表示すること
- 散歩結果モーダルに散歩の総距離を表示されること
- 散歩結果モーダルに廻ったスポット数を表示されること
- 散歩結果モーダルにホーム画面ボタンを置くこと
- ホーム画面ボタン押下で、ホーム画面に遷移されること

---

## 共通前提条件

### データフロー

| データ項目 | コード上の名前 | 型 | 説明 |
|------------|------|------|------|
| 目的 | `purpose` | String | ユーザーが選択した散歩の目的（1つ） |
| ジャンル | `genre` | String | ユーザーが選択したスポットのジャンル（1つ） |
| 距離 | `distance` | Number | ユーザーが入力した希望移動距離（km） |
| スポットリスト | `spots` | Array | DBまたはAIが選定したスポットの一覧 |
| ルート情報 | `route` | Object | 生成されたルート（経路座標、移動距離等） |
| 総距離 | `totalDistance` | Number | 実際に歩いた散歩の総距離（km） |
| スポット数 | `spotCount` | Number | 実際に廻ったスポットの数 |

用語の定義は `naming-glossary.md` を参照。特に以下を混同しないこと。

| 語 | 何を指すか |
|---|---|
| `spot` | ユーザーが立ち寄る場所（公園・神社・カフェ等） |
| `waypoint` | 経路を描くための座標の点（交差点・道の折れ点） |

### 状態管理

- ホーム画面で入力された検索条件（目的・ジャンル・距離）は、ルート再作成時にも利用されるため、画面遷移を通じて保持すること
- ルート決定後、案内中は現在のルート情報を保持し続けること
- 散歩終了時に総距離・スポット数を集計し結果画面に渡すこと

### 画面共通仕様

- ロード画面はルート生成処理中に表示し、完了後に自動遷移する
- モーダル/ポップアップは画面中央に表示する
- ボタンの配置について：確認ポップアップは右に「はい」、左に「いいえ」とする

## 開発ルール

### 分担における注意事項

1. **インターフェースの統一**: 各画面間で受け渡すデータの型・形式は本ドキュメントの「データフロー」に従うこと
2. **命名規則の統一**: 変数名・関数名・コンポーネント名は `.kiro/steering/naming-conventions.md` と `.kiro/steering/naming-glossary.md` に従うこと
3. **状態管理の方式統一**: 検索条件やルート情報の保持方法はチーム全体で同一の仕組みを使用すること
4. **API仕様の事前合意**: バックエンド・フロントエンド間のAPI仕様は実装前に合意すること
5. **ユーザーストーリー単位での実装**: 各メンバーはUS単位で担当し、受け入れ条件を満たすことを確認してから完了とすること
