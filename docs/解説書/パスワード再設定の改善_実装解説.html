🗓 対象期間: 2026-10-01 〜 2026-10-07
📅 マージ日: 2026-10-07（3件すべて）
🌿 対象ブランチ: feature/NZ-207, fix/auth-error-messages
🔖 対象マージ: 5e15505（照合APIの追加）, c7c3ddc（パスワード表示ボタン・完了メッセージの見直し）, b3f785b（エラー文言の修正）

パスワードを忘れた利用者が自分で再設定できる画面は以前からありました。この3つのマージは、その画面の 「入力の間違いに気付けない」「エラーの文言が実態と合っていない」「パスワードを確認しづらい」 という3つの困りごとをまとめて直したものです。 バックエンドに照合用の Lambda 関数を1つ追加し、フロントは入力チェック・表示ボタン・文言を整えました。

🧩 先に知っておきたいこと

Amazon Cognito とユーザープール
ミチシルのログイン・ユーザー登録・パスワード再設定は、AWS の認証サービス Amazon Cognito の「ユーザープール」が担っています。ユーザー名・メールアドレス・パスワードはアプリの DynamoDB ではなくユーザープールに保存され、ブラウザからは aws-amplify/auth というライブラリ経由で呼び出します。 画面そのものの作りは パスワード再設定画面の解説書 にあります。
Lambda の4ファイル構成（handler / service / repository / validator）
バックエンドの1機能は1フォルダにまとまっていて、ファイル名が役割を表します。handler.js が入口（受付と返却）、 service.js が判断（業務ロジック）、repository.js が外部サービスへのアクセス、 validator.js が入力チェックです。詳しくは ルート作成APIの解説書 の「レイヤーの責務を守る」を参照してください。
Composable（コンポーザブル）
Vue で「画面をまたいで使い回したい状態と処理」をまとめた関数のことです。名前は必ず use で始まり、 frontend/src/composables/ に置きます。呼ぶと状態（ref）と操作する関数がセットで返ってくるので、 複数の画面で同じ挙動を再現できます。今回は「パスワードを平文で見せるかどうか」をこの形で切り出しています。
API Gateway の Cognito オーソライザー
ミチシルの API は、ログイン済みの人だけが呼べるように API Gateway 側で入口をふさいでいます。 ブラウザは Cognito から受け取った idToken を Authorization ヘッダーに載せて送り、 API Gateway がそれを検証します。ログイン前に呼ぶ必要があるAPIは、この保護を付けられません（後述の注意ポイントで触れます）。
例外の name で文言を切り替える作り
このプロジェクトのフロントは、失敗したときに例外（Error）を投げ、 その例外の name（例: CodeMismatchException）をキーに表示用の日本語を引く作りになっています。 つまり name が対応表に無いと、ひとつ上の「〜に失敗しました」という大まかな文言に落ちます。 今回の文言修正はここを直したものです。

🎯 なぜこの機能が必要？

Cognito は「そのユーザーが居るか」を教えてくれない

パスワード再設定は、Cognito の resetPassword を呼ぶと登録済みのメールアドレスへ確認コードが飛ぶ仕組みです。 ところがこのAPIは、存在しないユーザー名を渡しても成功したかのように振る舞うことがあります。 これはセキュリティ上わざとそうなっていて、「このユーザー名は登録されている／されていない」を外部から探られないための配慮です。

利用者から見ると、こうなります。

  • ユーザー名を打ち間違えた → 画面には「確認コードを送信しました」と出る
  • いくら待ってもメールは届かない
  • 何が悪いのか分からないまま詰まる

そこで、コードを送る前に「ユーザー名」と「そのユーザーに登録されているメールアドレス」の組み合わせを照合する 手順を挟みました。一致したときだけコードを送り、一致しなければその場で 「ユーザー名とメールアドレスの組み合わせが一致しません」と伝えます。 利用者は自分の入力を見直せますし、他人のユーザー名を当て推量で入れただけでは 「メールアドレスが何なのか」は分からないままです。

なぜブラウザからは照合できないのか

「登録されているメールアドレスを取ってきて比べるだけなら、ブラウザでできそう」と思えますが、できません。 Cognito が利用者の登録情報を返すのはその本人のトークンがあるときだけで、 パスワードを忘れている＝ログインできていない状況ではトークンがありません。

登録情報を参照するには、管理者向けの API（AdminGetUser）を使う必要があります。これは強い権限なので、 ブラウザに権限を持たせるわけにはいきません。だからサーバー側（Lambda）に照合だけを任せるという形になりました。

関連するユーザーストーリー

US-1〜US-8 はルート作成と案内のストーリーで、認証はそこに含まれていません。 パスワード再設定は前提条件書の「確定した要素」にある認証基盤（Amazon Cognito のユーザープール。ログイン画面はアプリ内に自作する） に属する機能で、その画面を使いやすく・安全にするのが今回の修正です。

🔄 処理の流れ

パスワードの再設定は2段階の画面で進みます。1段目が「誰のパスワードを再設定するか」、2段目が「新しいパスワードを決める」です。

【1段目】ユーザー名 + メールアドレスを入力
   ↓ 送信前に入力チェック（authValidator）
   ↓ POST /api/v1/password-reset-verifications  ← 今回追加した照合API
   ↓ 一致した場合のみ
   ↓ Cognito の resetPassword で確認コードを送信
【2段目】確認コード + 新しいパスワード + 確認入力
   ↓ 送信前に入力チェック
   ↓ Cognito の confirmResetPassword で確定
   ↓ ログイン画面へ戻り、トーストで完了を知らせる
Step 1: 送信前に入力の形を調べる（フロント / 5e15505）

PasswordResetRequestForm.vue の送信ボタンを押すと、まず authValidator.js の関数で ユーザー名とメールアドレスを調べます。問題があればその項目の下に理由を出し、APIは呼びません。 前後の空白はコピー貼り付けで混ざりやすいため、調べる前に取り除きます。

Step 2: 照合APIへ問い合わせる（フロント / 5e15505・b3f785b）

passwordResetService.js が POST /api/v1/password-reset-verifications へ ユーザー名とメールアドレスを送ります。応答が返らなかった場合（オフラインなど）や、 JSON ではないものが返った場合は VerificationUnavailable という名前の例外を投げます。

Step 3: Lambda の入口で受け取り、入力を検証する（バックエンド / 5e15505）

handler.js がリクエストボディを JSON として解析し、validator.js に渡します。 解析できない・必須項目が無い・文字数や文字種が条件に合わない場合は、ここで 400 と VALIDATION_ERROR を返して終わります。

Step 4: Cognito から登録済みのメールアドレスを取り、比べる（バックエンド / 5e15505）

service.js が repository.js を通じて Cognito の AdminGetUser を呼び、 そのユーザーの email 属性を取り出します。比べるときは大文字小文字の違いと前後の空白を無視します （USER@EXAMPLE.COM と user@example.com は同じアドレスとして扱う）。

ユーザーが存在しない場合、Cognito は UserNotFoundException を投げます。 これはエラーとして扱わず「見つからなかった（null）」として上に返し、結果は不一致になります。

Step 5: 一致したときだけ確認コードを送る（フロント / 5e15505）

照合APIは { "isMatched": true } または { "isMatched": false } だけを返します。 authStore.resetPassword は、照合が通った場合に限って Cognito の resetPassword を呼び、確認コードの送信先（a***@example.com のようにマスクされた形）を 受け取って2段目の画面に表示します。

Step 6: 新しいパスワードを確定し、ログイン画面で知らせる（フロント / 5e15505・c7c3ddc）

2段目では確認コード・新しいパスワード・確認用のもう一度の入力を調べたうえで、Cognito の confirmResetPassword を呼びます。成功したらログイン画面へ ?reset=1 付きで遷移し、ログイン画面がそれを見てトーストで 「パスワードを再設定しました。新しいパスワードでログインしてください。」と知らせます。

💻 コードの解説

backend/functions/verifyPasswordResetTarget/handler.js

照合APIの入口です。入力チェックの呼び出しと、結果の返却だけを行います。

const { isMatched } = await verifyPasswordResetTarget(
  validationResult.value
);

// 一致しない場合もエラーではなく結果として返す。
// 理由を返さないことで、ユーザーの有無や登録アドレスを推測させない
return buildSuccessResponse({ isMatched });

ここが設計の勘所です。不一致はエラー（4xx）ではなく成功（200）で isMatched: false として返します。 「ユーザーが居ない」と「メールアドレスが違う」を呼び出し側から区別できないようにするためで、 どちらの場合も同じ応答になります。

backend/functions/verifyPasswordResetTarget/service.js

照合の判断そのものを担います。HTTP の知識は持たず、オブジェクトを受け取ってオブジェクトを返します。

const normalizeEmail = (email) => email.trim().toLowerCase();

export const verifyPasswordResetTarget = async (
  { username, email },
  repositories = defaultRepositories
) => {
  const registeredEmail = await repositories.findUserEmail(username);

  if (registeredEmail === null) {
    logInfo('照合の結果、対象のユーザーが見つかりませんでした', { username });

    return { isMatched: false };
  }

  const isMatched = normalizeEmail(registeredEmail) === normalizeEmail(email);

  return { isMatched };
};

第2引数の repositories に注目してください。既定では本物の findUserEmail が入りますが、テストのときは「決まった値を返す偽物」を渡せます。 そのおかげで、Cognito に接続しなくても照合の判断だけをテストできます （__tests__/service.test.js がそうしています）。

backend/functions/verifyPasswordResetTarget/repository.js

Cognito とのやり取りを閉じ込めた層です。判断はせず、取得だけを行います。

const response = await getClient().send(
  new AdminGetUserCommand({
    UserPoolId: USER_POOL_ID,
    Username: username
  })
);

const emailAttribute = (response.UserAttributes ?? []).find(
  (attribute) => attribute.Name === 'email'
);

return emailAttribute?.Value ?? null;

AdminGetUser は管理者向けのAPIで、ユーザーの属性を一覧（UserAttributes）で返します。 その中から email という名前の属性を探して値を取り出しています。

例外の扱いも決まっています。UserNotFoundException（そのユーザーが居ない）は null を返して正常系として処理し、それ以外の失敗は createDataSourceError でアプリ共通のエラーに変換して投げます。 AWS SDK のエラーをそのまま上の層へ流さないのは、このプロジェクトのバックエンド共通のルールです。

ユーザープールIDは constants.js が process.env.USER_POOL_ID から読み、 未設定なら照合する前に分かるようエラーにします。

backend/functions/verifyPasswordResetTarget/validator.js

副作用を持たない純粋な関数として入力を調べます。

/** 受け付ける文字の範囲（半角英数字と半角記号。空白は含まない） */
const HALF_WIDTH_PATTERN = /^[\x21-\x7E]+$/;

\x21 は !、\x7E は ~ を表す書き方で、 この2つの間にある半角の文字だけを通します。全角文字や空白は弾かれます。 文字数の上限（ユーザー名20文字・メールアドレス254文字）は constants.js に置かれ、 フロントの authValidation.js と同じ値になるよう揃えてあります。

frontend/src/services/passwordResetService.js

照合APIとの通信を担当します。b3f785b で fetch の囲みが足されたのがこのファイルです。

let response;

try {
  response = await fetch(`${API_BASE_PATH}/password-reset-verifications`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ username, email })
  });
} catch (error) {
  // オフラインや通信の遮断では応答が返らず、fetch が TypeError を投げる。
  // 応答のエラーと同じく「確認できなかった」として扱う
  throw createNamedError(
    'VerificationUnavailable',
    `組み合わせの確認に失敗しました（通信エラー: ${error.message}）`
  );
}

// APIが未配線の環境ではSPAのindex.html（HTML）が200で返るため、解析前に判定する
if (!response.ok || !isJsonResponse(response)) {
  throw createNamedError('VerificationUnavailable', ...);
}

const { isMatched } = await response.json();

if (!isMatched) {
  throw createNamedError('EmailMismatch', ...);
}

ポイントは3つあります。

  • 不一致を例外にしている。 API は isMatched: false を正常応答で返しますが、 フロント側では EmailMismatch という例外に変換します。こうすると呼び出し側は 「例外が出なければ一致」とだけ考えればよくなります。
  • JSON かどうかを解析前に調べる。 API が繋がっていない環境では、 SPA の index.html（HTML）が 200 で返ってきます。 これをそのまま response.json() にかけると意味の分からないエラーになるため、先に中身の種類を確かめます。
  • 応答が返らない場合も同じ名前にする。 オフラインのとき fetch 自身が TypeError を投げます。b3f785b 以前はこれが素通りしていました（後述）。

frontend/src/stores/authStore.js

「照合してから送る」という順番を守っているのがここです。

const resetPassword = async (inputUsername, inputEmail) => {
  isResettingPassword.value = true;
  errorMessage.value = null;

  try {
    // 先に組み合わせを照合する。一致しない場合は例外になり、コードは送らない
    await verifyPasswordResetTarget(inputUsername, inputEmail);

    const codeDeliveryDestination = await sendPasswordResetCode(inputUsername);

    return { isSucceeded: true, codeDeliveryDestination };
  } catch (error) {
    errorMessage.value = toPasswordResetErrorMessage(error);

    return { isSucceeded: false, codeDeliveryDestination: null };
  } finally {
    isResettingPassword.value = false;
  }
};

照合で例外が出れば sendPasswordResetCode には進まないため、確認コードは送られません。 失敗の理由は errorMessage に入り、フォームがそれを表示します。 finally で通信中フラグを戻しているので、成功・失敗どちらでもボタンは押せる状態に戻ります。

frontend/src/services/authService.js（文言の対応表）

例外の name から画面に出す日本語を引く表が置かれています。再設定のときだけ文言を変えたい例外は別の表に分けています。

const PASSWORD_RESET_ERROR_MESSAGES = {
  // ユーザーの有無を画面で言い当てないよう、あいまいな文言にする
  UserNotFoundException: 'ユーザー名を確認してください',
  // 入力されたユーザー名とメールアドレスの組み合わせが、登録内容と一致しなかった場合
  EmailMismatch: 'ユーザー名とメールアドレスの組み合わせが一致しません',
  // 照合そのものができなかった場合（APIへ到達できない等）
  VerificationUnavailable:
    '組み合わせを確認できませんでした。通信状況を確認してください',
  ...
};

export const toPasswordResetErrorMessage = (error) =>
  PASSWORD_RESET_ERROR_MESSAGES[error?.name] ??
  ERROR_MESSAGES[error?.name] ??
  PASSWORD_RESET_DEFAULT_ERROR_MESSAGE;

?? は「左が null か undefined なら右を使う」という書き方です。 再設定専用の表 → 共通の表 → 既定の文言、という順で探します。 同じ UserNotFoundException でも、ログインでは「ユーザー名またはパスワードが違います」、 再設定では「ユーザー名を確認してください」と出し分けられるのはこの仕組みのおかげです。

エラー文言をどう直したか（b3f785b）

2か所です。どちらも「文言を書き換えた」のではなく、正しい文言が引かれるように例外の名前を整えた修正です。

1. 照合APIへ届かなかったとき

　 起きていたこと 画面に出た文言
修正前 fetch が投げる TypeError がそのまま上がり、対応表に当たらなかった パスワードの再設定に失敗しました。通信状況を確認してください
修正後 fetch を try で囲み、VerificationUnavailable に変換する 組み合わせを確認できませんでした。通信状況を確認してください

修正前の文言でも間違いではありませんが、まだ再設定そのものは始まっていない段階です。 実際には「組み合わせを確認する通信ができなかった」ので、どこで止まったのかが伝わる文言に寄せました。 応答が返ってきたうえでの失敗（404 や HTML が返るなど）はもともと VerificationUnavailable になっていたため、これで両方の経路の文言が揃いました。

2. 未確認のユーザーがログインしようとしたとき

ユーザー登録した直後は「未確認」の状態で、メールで届いた確認コードを入れるまでログインできません。 この状態でログインすると、Amplify v6 は例外を投げるのではなく 「次の手続きが必要（CONFIRM_SIGN_UP）」として正常に返してきます。 ミチシルにはその手続きの画面が無いため、失敗として扱う必要があります。 

/**
 * サインインで追加の手続きを求められたとき、例外名を読み替える対応。
 * Amplify v6 は未確認のユーザーに対して UserNotConfirmedException を投げず、
 * 次の手続き（CONFIRM_SIGN_UP）として返すため、例外として扱う名前へ寄せる。
 */
const SIGN_IN_STEP_ERROR_NAMES = {
  CONFIRM_SIGN_UP: 'UserNotConfirmedException'
};

// ...

error.name =
  SIGN_IN_STEP_ERROR_NAMES[nextStep.signInStep] ?? nextStep.signInStep;
throw error;
　 例外の name 画面に出た文言
修正前 CONFIRM_SIGN_UP（対応表に無い） ログインに失敗しました。通信状況を確認してください
修正後 UserNotConfirmedException（対応表にある） このユーザーは有効化されていません。管理者に連絡してください

修正前は通信が正常でも「通信状況を確認してください」と出ていました。原因が通信ではないため、利用者は直しようがありません。 例外の名前を対応表にある UserNotConfirmedException へ読み替えることで、 すでに用意されていた正しい文言が出るようになりました。

frontend/src/utils/authValidator.js と fieldErrors の仕組み

入力チェックは「Vue に依存しない純粋な関数」として utils/ に置かれています。 関数はエラーがあれば表示用の日本語を返し、問題なければ null を返します。 

export const validateUsername = (username) => {
  if (username === '') {
    return 'ユーザー名を入力してください';
  }

  if (username.length > USERNAME_MAX_LENGTH) {
    return `ユーザー名は${USERNAME_MAX_LENGTH}文字以内で入力してください`;
  }

  if (!HALF_WIDTH_PATTERN.test(username)) {
    return `ユーザー名は${HALF_WIDTH_HINT}`;
  }

  return null;
};

export const hasNoFieldError = (fieldErrors) =>
  Object.values(fieldErrors).every((error) => error === null);

画面側は、項目名をキーにした fieldErrors というオブジェクトでその戻り値を保持します。

const fieldErrors = ref({
  username: null,
  email: null
});

const handleSubmit = () => {
  const trimmedUsername = username.value.trim();
  const trimmedEmail = email.value.trim();

  fieldErrors.value = {
    username: validateUsername(trimmedUsername),
    email: validateEmail(trimmedEmail)
  };

  if (!hasNoFieldError(fieldErrors.value)) {
    return;
  }

  emit('submitPasswordResetRequest', {
    username: trimmedUsername,
    email: trimmedEmail
  });
};

この形の良いところは3つあります。

  • どの項目が悪いか分かる。 フォーム全体に1つのエラーを出すのではなく、 問題のある入力欄の真下に理由を出せます。
  • 直したら消える。 入力欄の @input で clearFieldError('username') を呼び、その項目のエラーだけを null に戻します。
  • 支援技術にも伝わる。 エラーのある入力欄には aria-invalid が付き、 aria-describedby でエラー文と結び付けられています。

なお <form> には novalidate が付いています。 ブラウザが標準で出す吹き出し（「このフィールドを入力してください」など）は文言を揃えられないため止めて、 チェックを authValidator に一本化しています。

frontend/src/composables/usePasswordVisibility.js

目のアイコンの状態を持つ Composable です。入力欄1つにつき1回呼びます （新しいパスワードと確認用の2欄がある画面では2回呼び、片方を平文にしてももう片方は隠れたままになります）。 

export const usePasswordVisibility = () => {
  /** パスワードを平文で表示しているかどうか */
  const isPasswordVisible = ref(false);

  /** 表示ボタンを出してよい状態かどうか。エラー直後はfalseにする */
  const isPasswordRevealAvailable = ref(true);

  /** パスワード欄に渡す input の type */
  const passwordInputType = computed(() =>
    isPasswordVisible.value ? 'text' : 'password'
  );

  const disablePasswordReveal = () => {
    isPasswordVisible.value = false;
    isPasswordRevealAvailable.value = false;
  };

  const enablePasswordReveal = () => {
    isPasswordRevealAvailable.value = true;
  };
  ...
};

似た名前の状態が2つあるので、役割を分けて覚えてください。

状態 意味 変わるきっかけ
isPasswordVisible いま平文で見えているか。true なら入力欄の type が text になる 目のアイコンを押したとき
isPasswordRevealAvailable 目のアイコン自体を出してよいか。false ならボタンが消える エラーが出たら false、入力が直されたら true

なぜエラー直後は表示ボタンを出さないのか

パスワードを間違えた直後の画面には、エラー文が出たままパスワードが入力欄に残っています。 そこで平文表示に切り替えられると、「エラーが見えている画面」と「パスワードが読める状態」が同時に成立します。 誰かが画面を覗いている状況や、画面共有・スクリーンショットの場面でそのまま漏れてしまいます。

そのため、エラーが出た時点で disablePasswordReveal() を呼んでボタンを隠し、 入力が1文字でも直されるまで出しません。入力し直す＝内容が変わるので、 そのとき平文にできても古い（間違った）パスワードが見えることはありません。

引き金は2つあります。1つは送信前の入力チェックで落ちたとき、もう1つは サーバーから失敗が返って errorMessage が入ったときで、後者は watch で拾っています。 

// 再設定に失敗したときも、修正されるまで表示ボタンを出さない
watch(
  () => props.errorMessage,
  (message) => {
    if (message !== null) {
      disableAllPasswordReveal();
    }
  }
);

テンプレート側は、この状態をボタンの表示条件にそのまま使います。

<!-- エラーが出た後は、入力が修正されるまでこのボタンを出さない -->
<PasswordVisibilityButton
  v-if="newPasswordVisibility.isPasswordRevealAvailable.value"
  :is-password-visible="newPasswordVisibility.isPasswordVisible.value"
  :is-disabled="isResettingPassword"
  label="新しいパスワード"
  @toggle-visibility="newPasswordVisibility.togglePasswordVisibility"
/>

iac/lib/michishiru-stack.ts

照合用の Lambda と、その入口の定義です。他のAPIと違う扱いになっている箇所が2つあります。

// 照合に必要な読み取りだけを、作成したユーザープールに限って許可する
verifyPasswordResetTargetFn.addToRolePolicy(
  new iam.PolicyStatement({
    sid: 'ReadUserForPasswordReset',
    actions: ['cognito-idp:AdminGetUser'],
    resources: [userPool.userPoolArn]
  })
);

// POST /api/v1/password-reset-verifications
// ここだけ認可を付けない。パスワードを忘れた利用者がログインする前に呼ぶため、
// Cognito オーソライザーで守ると機能しなくなる。
const passwordResetVerificationsResource = v1Resource.addResource(
  'password-reset-verifications'
);
passwordResetVerificationsResource.addMethod(
  'POST',
  new apigateway.LambdaIntegration(verifyPasswordResetTargetFn)
);

1つめは IAM の権限です。この Lambda に与えているのは AdminGetUser という 1つの操作だけで、対象もこのスタックが作ったユーザープールだけに絞っています。 管理者向けAPIを使う関数なので、できることを最小限にしてあります。

2つめは 認可を付けていないことです。他のメソッド（/api/v1/routes など）には cognitoAuthorized を渡していますが、ここには渡していません。 パスワードを忘れた＝ログインできない人が呼ぶAPIなので、ログイン必須にすると機能しなくなります。 この判断の裏返しが次の注意ポイントです。

⚠️ 注意ポイント

1. 照合APIには総当たり対策がまだ入っていない

上に書いたとおり、このAPIはログイン前に呼ぶため Cognito オーソライザーで保護できません。 つまりURL を知っていれば誰でも呼べる状態です。 1回の応答は isMatched だけなので、1回では何も分かりませんが、 メールアドレスを機械的に大量に試せば「このユーザー名に紐づくアドレス」を当てられる余地が残ります。

方針は決まっていて、回数制限（API Gateway のスロットリング / WAF）で抑えることになっています。 ただし実装はまだです。前提条件書の「今後追加予定の要素」に 「照合APIの保護」として残っているので、触る人はそこを確認してください。 CDK のコードにも同じ内容がコメントで書かれています。

2. 不一致の理由を増やしてはいけない

「ユーザーが存在しない」と「メールアドレスが違う」は、どちらも isMatched: false として同じ応答になります。 親切心で「そのユーザーは登録されていません」と返す作りに変えると、 ユーザー名の一覧を外部から確かめられるようになります。Cognito が応答を揃えているのと同じ理由です。 応答の形を変えるときは、この意図を壊していないか確かめてください。

3. フロントの入力チェックはサーバー側の代わりにならない

authValidator.js のチェックは「往復を待たずに気付けるようにする」ためのもので、 ブラウザの外から直接APIを叩けば通り抜けられます。 そのため validator.js がサーバー側でも同じ条件を調べています。 どちらか片方だけにするのではなく、両方に置いて値を揃えるのが前提です （文字数の上限はフロントとバックエンドの constants に同じ数字が書かれています）。

4. ローカルで照合APIを動かすには準備が必要

この Lambda は実際に Cognito を呼ぶため、ローカルAPIハーネス経由で叩く場合も AWS の認証情報（AWS_PROFILE など）と環境変数 USER_POOL_ID が必要です。 USER_POOL_ID が空のときは照合に進まず、「ユーザープールIDが未設定のため照合できません」というエラーになります。 これは設定漏れにその場で気付けるようにわざとそうしています。

5. 目のアイコンの状態は「欄ごと」に持つ

usePasswordVisibility() を1回だけ呼んで2つの入力欄で共有すると、 片方を平文にしたときにもう片方も一緒に平文になります。 新しいパスワードと確認用の欄があるフォームでは、必ず欄ごとに呼んでください （PasswordResetConfirmForm.vue と SignUpForm.vue がそうしています）。

✅ 動作確認方法

画面での確認

  1. フロントとローカルAPIを同時に起動する 
    # リポジトリのルートで実行
npm run dev

    照合APIを実際に動かす場合は、起動前に USER_POOL_ID を設定し、 AWS の認証情報が使える状態にしておきます。

  2. 入力チェックを確かめる

    ログイン画面の「パスワードの再設定」から再設定画面へ進み、 何も入れずに「確認コードを送る」を押します。各欄の下に 「ユーザー名を入力してください」「メールアドレスを入力してください」が出て、 APIは呼ばれないことを確認します（ブラウザの開発者ツールの Network タブで確認できます）。

  3. 組み合わせが違う場合を確かめる

    登録済みのユーザー名と、そのユーザーとは別のメールアドレスを入れて送信します。 「ユーザー名とメールアドレスの組み合わせが一致しません」と出て、 確認コードの入力画面へ進まないことを確認します。存在しないユーザー名でも同じ結果になります。

  4. 一致する場合を確かめる

    正しい組み合わせを入れると確認コードの入力画面へ進み、送信先が a***@example.com のような形で表示されます。 メールのコードと新しいパスワードを入れて再設定すると、ログイン画面に戻り、 画面上部にトーストで完了が知らされます。

  5. 目のアイコンの挙動を確かめる

    パスワード欄の右端のアイコンを押すと平文になります。 次にパスワードをわざと短くして送信し、エラーが出た直後にアイコンが消えること、 そのあと1文字入力し直すと再び現れることを確認します。

  6. 通信できないときの文言を確かめる（b3f785b の確認）

    開発者ツールの Network タブでオフラインにしてから送信すると、 「組み合わせを確認できませんでした。通信状況を確認してください」と出ます。
