NZ-176 APIのアクセス制御（Cognito オーソライザー） - 実装解説

📅 マージ日: 2026-10-07（12:50、PR #74、マージコミット 75de23f。実装コミットは 8c9ce56）
🌿 ブランチ: feature/NZ-176
📝 課題番号: NZ-176
🧩 概要: API Gateway に Cognito オーソライザーを付け、ログイン後に呼ぶAPIをログイン済みの人だけが使えるようにした。フロントは Cognito の IDトークンを Authorization ヘッダーで送る

📖 この機能について

これまで、ミチシルのAPI（/api/v1/...）はURLを知っていれば誰でも呼べる状態でした。 画面側はログインしていない人をログイン画面へ送り返していましたが、それは「画面の入口に鍵をかけた」だけで、 APIそのものには鍵がかかっていませんでした。ブラウザのアドレス欄やコマンドから直接APIを叩けば、 ログインせずにルートを生成できてしまいます。

今回の変更で、APIの手前にCognito オーソライザーという鍵を置きました。 オーソライザーは「このリクエストはログイン済みの人のものか」を調べる見張り役です。 ログイン時に Cognito から受け取った引換券（IDトークン）がリクエストに付いていなければ、 Lambda まで届く前に API Gateway が 401 Unauthorized で追い返します。

🎯 なぜこの機能が必要？

  • 無料で使い放題にならないようにする。 ルート生成（POST /api/v1/routes）は Amazon Bedrock（AI）と Location Service を呼ぶため、1回ごとに料金がかかります。鍵がないと、第三者が繰り返し叩くだけで費用が膨らみます。
  • 口コミの投稿者を特定できるようにする。 誰でも投稿できる状態だと、荒らしを止める手段がありません。
  • この先「ユーザーごとのデータ」を扱う土台になる。 オーソライザーを通ると、Lambda は event.requestContext.authorizer.claims.sub から「誰からのリクエストか」を受け取れます。散歩の実績やお気に入りをユーザー単位で保存するには、まずこれが必要です。
用語: sub は Cognito が発行する、ユーザーごとに変わらないIDです。ユーザー名はあとから変更され得るため、データのキーには sub を使います（naming-glossary.md の「認証」節）。

🔄 処理の流れ

[ブラウザ] ホーム画面で「ルート作成」を押す
   │
   ▼
[routeService.createRoute()]
   ├─ ① const idToken = await fetchIdToken()   … authService が Cognito から取得
   │       ↑ 取れなければ例外（name: 'NoValidSession'）→ 画面に日本語のメッセージ
   │
   └─ ② fetch('/api/v1/routes', { headers: { Authorization: idToken } })
   │
   ▼
[CloudFront]  /api/* を API Gateway へ転送（ヘッダーもそのまま渡す）
   │
   ▼
[API Gateway] Cognito オーソライザーが Authorization ヘッダーを検証
   │
   ├─ トークンが無い・壊れている・期限切れ ─→ 401 Unauthorized（Lambda は呼ばれない）
   │
   └─ 正しい
        ▼
     [Lambda createRoute]
        event.requestContext.authorizer.claims.sub で「誰か」が分かる
Step 1: サービス層（routeService / conditionService）が、通信の直前に fetchIdToken() を呼びます。これは authService にある関数で、Amplify の fetchAuthSession() からIDトークンを取り出します。
Step 2: 取れたトークンを Authorization ヘッダーに入れて fetch します。トークンが取れなかった場合はここで例外が投げられ、通信は行われません。
Step 3: リクエストは CloudFront を通って API Gateway に届きます。ミチシルはフロントとAPIを同じドメインで配信しているため（同一オリジン）、CORS の設定は不要です。
Step 4: API Gateway のオーソライザーがトークンを検証します。Lambda の中にトークンを調べる処理を書く必要はありません。検証はAWS側の仕事です。
Step 5: 検証を通ったリクエストだけが Lambda に届きます。このとき、トークンの中身（sub やユーザー名）が event.requestContext.authorizer.claims に入った状態で渡されます。

🔐 どのAPIに鍵をかけたか

現在、API Gateway には7つのメソッドがあります。鍵をかけたのは6つ、かけていないのは1つです。

メソッド 用途 認可
GET /api/v1/routes 既存ルートの取得 必須
POST /api/v1/routes 条件からルートを生成 必須
GET /api/v1/conditions 検索条件マスタ（ジャンル・距離）の取得 必須
GET /api/v1/spots 長押し位置の既存口コミ場所の解決 必須
POST /api/v1/reviews 口コミの投稿 必須
POST /api/v1/review-photo-uploads 写真アップロード用の署名付きURL発行 必須
POST /api/v1/password-reset-verifications パスワード再設定前のユーザー名とメールアドレスの照合 なし

最後の照合APIだけ鍵をかけていないのは、パスワードを忘れた人がログインする前に呼ぶAPIだからです。 ログイン済みであることを条件にしてしまうと、パスワードを忘れた人がこのAPIを使えず、機能そのものが成り立ちません。 「鍵をかけ忘れた」のではなく「かけられない」ものである点に注意してください。

💻 コードの解説

iac/lib/michishiru-stack.ts（変更）

オーソライザーを1つ作り、それを3つ（現在は6つ）のメソッドに渡しています。

const apiAuthorizer = new apigateway.CognitoUserPoolsAuthorizer(
  this,
  'ApiAuthorizer',
  {
    cognitoUserPools: [userPool],
    // API 本体と同じ理由で物理名を指定する（AWSコンソールで識別するため）
    authorizerName: `michishiru-api-authorizer-${stage}`
  }
);

cognitoUserPools: [userPool] で「どのユーザープールのトークンを正とみなすか」を指定します。 userPool は withBackend の分岐の外で作られているため、バックエンドの定義ブロックからそのまま参照できます。 

// 保護する3メソッドへ渡す設定。authorizationType は省略すると
// 既定値に引きずられるため、COGNITO を明示する。
const cognitoAuthorized: apigateway.MethodOptions = {
  authorizer: apiAuthorizer,
  authorizationType: apigateway.AuthorizationType.COGNITO
};

設定を1つの定数にまとめ、各メソッドへ同じオブジェクトを渡す形にしています。 メソッドごとに個別に書き下すと「1つだけ付け忘れる」という事故が起きやすく、しかもその場合エラーにならず静かに穴が開きます。 まとめておけば、渡しているかどうかを見た目で確認できます。 

routesResource.addMethod(
  'GET',
  new apigateway.LambdaIntegration(getRouteFn),
  cognitoAuthorized          // ← 第3引数に渡すだけ
);

addMethod の第3引数に渡すと、そのメソッドが認可付きになります。 照合API（password-reset-verifications）の addMethod だけ第3引数を持ちません。

frontend/src/services/authService.js（変更）

IDトークンを取ってくる fetchIdToken を追加しました。

export const fetchIdToken = async () => {
  const session = await fetchAuthSession();
  const idToken = session.tokens?.idToken?.toString();

  if (idToken) {
    return idToken;
  }

  // composable は error.message をそのまま画面へ出すため、ここに利用者向けの文言を入れる
  const error = new Error(NO_VALID_SESSION_MESSAGE);
  error.name = 'NoValidSession';
  throw error;
};

この関数には判断が2つ入っています。どちらも意図があるので、変更するときは理由を確認してください。

判断 理由
トークンを変数に取り置き（キャッシュ）しない IDトークンの有効期限は1時間ですが、散歩はそれより長く続くことがあります。fetchAuthSession() はリフレッシュトークン（5日）を使って期限切れのトークンを自動で入れ替えるため、リクエストごとに呼ぶのが一番単純で安全です。一度取った値を使い回すと、散歩の途中で期限が切れて 401 になります。
取得できないときは null ではなく例外を投げる 呼び出し側が「通信に失敗した」と「ログインが切れた」を区別できるようにするためです。name に 'NoValidSession' を入れているので、あとから種類で分岐できます。

投げる Error の message には、最初から日本語の文言（「ログインの有効期限が切れました。もう一度ログインしてください」）を入れています。 ルート作成・検索条件の composable は error.message をそのまま画面に出すため、ここに入れておかないと利用者に伝わりません。 同じ文言は ERROR_MESSAGES.NoValidSession にも登録してあり、どちらの経路を通っても同じ文章になるよう定数 NO_VALID_SESSION_MESSAGE から参照しています。

frontend/src/services/routeService.js・conditionService.js（変更）

3か所の fetch に Authorization ヘッダーを付けました。

const idToken = await fetchIdToken();

const response = await fetch(`${API_BASE_PATH}/routes`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: idToken
  },
  body: JSON.stringify(...)
});
Bearer を付けてはいけない
HTTPの慣例では Authorization: Bearer <トークン> と書くことが多いですが、 API Gateway の Cognito オーソライザーは既定でヘッダーの値全体をトークンそのものとして扱います。 Bearer を付けると、その文字列ごとトークンとして検証しようとして失敗し、全リクエストが 401 になります。 テストでもヘッダーの値が 'dummy-id-token' と完全一致することを確認し、うっかり接頭辞が入らないよう固定しています。

同じ処理を2ファイルに書いていますが、今回はあえて共通化していません。呼び出し箇所が3つだけで、 早すぎる共通化は読みづらさを招くためです。3ファイル目が出た時点でまとめる方針をコメントに残しています。

passwordResetService.js は変更していません。照合APIはログイン前に呼ぶため、 トークンを取りに行くと「まだログインしていない」で必ず失敗します。

tools/localApiServer.js（変更）

ローカル開発では API Gateway が存在せず、tools/localApiServer.js という簡易サーバーが Lambda の関数を直接呼んでいます。 本番では API Gateway が requestContext.authorizer.claims を埋めてくれますが、ローカルではそれがありません。 そのままだと「本番では動くがローカルでは claims が undefined」という差が生まれるため、同じ形のデータを入れておきます。 

const LOCAL_DEV_USER_SUB = 'local-dev-user';
const LOCAL_DEV_USERNAME = 'local-dev';

// buildEvent の戻り値に追加
requestContext: {
  authorizer: {
    claims: {
      sub: LOCAL_DEV_USER_SUB,
      'cognito:username': LOCAL_DEV_USERNAME
    }
  }
}
このハーネスは認可の形だけ真似て、検証はしない
Authorization ヘッダーの中身は一切見ていません。そうしてよい理由は2つあります。 ① 127.0.0.1（自分のPC）でだけ待ち受けており、外部から届かない。 ② tools/ 配下はデプロイの対象外で、AWS上では動かない。
値を local-dev-user のようにUUIDに見えない形にしているのは、万一データに混ざったときに本番のユーザーと見分けられるようにするためです。

⚠️ 注意ポイント・残課題

401 のメッセージが英語のまま画面に出る
API Gateway のオーソライザーが返すのは {"message":"Unauthorized"} です。 routeService の extractErrorMessage はレスポンスの message をそのまま画面へ渡すため、 利用者に「Unauthorized」と表示され得ます。
起きるのは「トークンは取れたがAPI側で失効と判断された」という狭いケースです （トークンが取れない場合は fetchIdToken が日本語の文言で止めるため、ここには来ません）。 今回は既存のエラー処理に手を入れない方針のため未対応です。
照合APIの回数制限が未対応
POST /api/v1/password-reset-verifications は認可で守れないため、 ユーザー名とメールアドレスの組み合わせを総当たりで試されると当たってしまう可能性があります。 API Gateway のスロットリングか WAF で回数を制限する方針ですが、どちらにするかは未決定です （ミチシル_前提条件.md の「今後追加予定の要素」に残置）。
VITE_ROUTE_API_URL を使うと別オリジンへトークンが出る
fetchRoute のURLは環境変数で任意のオリジンに差し替えられる作り（既存）で、今回そこにIDトークンが乗ります。 fetchRoute には現在どこからも呼び出しがないため実害はありませんが、 別の API Gateway へ向ける運用を始めるなら、送り先を同一オリジンに限る対応が必要です。
検証していないこと
  • IdentitySource（どのヘッダーを見るか）は CDK の既定値に任せています。フロントは Authorization という名前に依存しているため、既定が変わると全リクエストが落ちます。テストで固定しておくと安全です。
  • バックエンド無効（withBackend なし）のスタックでオーソライザーが作られないことを確かめるテストはありません。
  • Lambda 側で claims.sub を使ってユーザーを識別する実装は、この課題のスコープ外です。backend/ は変更していません。

✅ 動作確認方法

デプロイ後の確認（dev環境）

  1. ブラウザでログインし、ホーム画面でジャンル・距離が表示されること（GET /api/v1/conditions が通っている）。
  2. 「ルート作成」でルートが生成されること（POST /api/v1/routes が通っている）。
  3. 口コミの投稿と写真のアップロードができること。
  4. 開発者ツールの Network タブでリクエストヘッダーを開き、Authorization に長い文字列が入っていること、Bearer で始まっていないことを確認する。
  5. 鍵が効いているかの確認: ログアウトした状態、またはトークンなしで https://<配信ドメイン>/api/v1/conditions を直接開き、401 と {"message":"Unauthorized"} が返ること。以前は中身が返っていました。
  6. 照合APIが未ログインでも動くこと（パスワード再設定画面でユーザー名とメールアドレスを入力して進めること）。

ローカルでの確認

  1. frontend/.env.local に VITE_COGNITO_USER_POOL_ID と VITE_COGNITO_USER_POOL_CLIENT_ID を用意する（既存の前提と同じ）。
  2. リポジトリのルートで npm run dev を実行し、フロントとAPIを同時に起動する。
  3. ログインしてホーム画面からルートを作成する。ローカルのAPIハーネスはトークンを検証しないため、通信が通ることの確認までになる。

チェックコマンド

  1. frontend/ で npm run lint → エラー0。
  2. frontend/ で npm test → 全テスト通過。
  3. frontend/ で npm run build → 成功。
  4. iac/ で npm run build と npm test → 成功・全テスト通過。
  5. iac/ で npx cdk synth Michishiru-dev -c withBackend=true → 成功。
    オーソライザーを作って1つもメソッドに紐付けないと CDK が合成時に例外を出すため、付け忘れの一部はここで気付けます。
