🗓 対象期間: 2026-10-01 〜 2026-10-07
📅 マージ日: 2026-10-07
🌿 対象ブランチ: feature/NZ-176
🔖 対象マージ: 75de23f

🧩 先に知っておきたいこと

「認証」と「認可」は別のもの
認証は「あなたが誰か」を確かめること（ログイン）です。認可は「その人がこの操作をしてよいか」を確かめることです。 ミチシルはログイン画面をすでに作っていましたが、API 側は誰からの呼び出しでも受け付けていました。今回やったのは後者の認可です。
API Gateway とは
ブラウザからの HTTP リクエストを受け取り、対応する Lambda 関数へ渡す AWS のサービスです。 「どの URL とどのメソッド（GET / POST）を、どの Lambda に繋ぐか」をここで定義します。ミチシルでは iac/lib/michishiru-stack.ts が定義しています。
IDトークン（idToken）とは
Cognito がログイン成功時に発行する、文字列になった身分証です。中にユーザーの属性（ユーザー名、不変のID sub など）と有効期限が入っており、 Cognito の署名が付いているため偽造すると検証で弾かれます。ミチシルの設定では有効期限は1時間です。
フロントの「サービス層」とは
frontend/src/services/ に置く、API との通信だけを担当するファイル群です。 画面（Vue コンポーネント）が直接 fetch を呼ばず、ここを経由させることで「通信の作法」を1か所にまとめられます。 今回の「トークンをヘッダーに付ける」処理もここに入ります。
ローカル開発のAPIハーネスとは
tools/localApiServer.js は、自分のパソコンの中で API Gateway の代わりをする小さなサーバーです（npm run dev で起動します）。 Lambda のコードをそのまま呼び出すため、AWS にデプロイしなくても動作を確認できます。デプロイ対象には含まれません。

📖 この機能について

ミチシルの API（ルートの取得・生成、検索条件マスタの取得）を、ログイン済みの人だけが呼べる状態にした修正です。

仕組みは2つに分かれます。

  • サーバー側（守る）: API Gateway に「Cognito オーソライザー」を取り付け、IDトークンを持たないリクエストを Lambda へ届く前に断る
  • フロント側（通す）: API を呼ぶ直前に Cognito から IDトークンを取り出し、Authorization ヘッダーに載せて送る

「オーソライザー（authorizer）」は直訳すると「認可する人」です。 API Gateway に取り付ける門番で、リクエストが届くたびにトークンを検証し、問題なければ Lambda へ通し、だめなら 401 Unauthorized を返します。 検証を API Gateway が引き受けるため、Lambda のコードにトークンを調べる処理を書く必要はありません。

🎯 なぜこの機能が必要？

この修正の前は、画面側だけがログインを要求していました。フロントは frontend/src/router/index.js の router.beforeEach（画面を移る前に必ず通る見張り役）で、未ログインならログイン画面へ送り返しています。

ただし、これはブラウザの中の話です。API の URL を知っている人が、ブラウザを通さず直接リクエストを送れば、ログインせずに応答を得られました。 ルート生成 API は Amazon Bedrock（AI）と Amazon Location Service を呼ぶため、無制限に叩かれると料金にも直結します。

もう1つの理由は、この先の機能の土台になることです。 認可を通ったリクエストでは、API Gateway が検証済みのユーザー情報を Lambda へ渡してくれます（event.requestContext.authorizer.claims）。 Lambda はこれを使って「誰の散歩実績か」「誰の口コミか」を判断できます。 前提条件書で未決だった「API の認可」が、このマージで「確定した要素」へ移りました（2026/10/07）。

🔄 処理の流れ

Step 1: 利用者がログインする。Cognito が IDトークンを発行し、Amplify（aws-amplify/auth）がブラウザに保存する。
Step 2: 画面が API を呼ぶ。サービス層（routeService.js / conditionService.js）が、fetch を呼ぶ直前に authService.fetchIdToken() でトークンを取り出す。期限が切れていれば Amplify が自動で更新する。
Step 3: 取り出したトークンを Authorization ヘッダーにそのまま載せてリクエストを送る。 Bearer のような接頭辞は付けない（理由は「注意ポイント」）。
Step 4: リクエストは CloudFront の /api/* を通って API Gateway に届く。 オーソライザーがヘッダーのトークンを検証する（署名・有効期限・発行元のユーザープールが一致するか）。
Step 5（検証OK）: Lambda が起動する。トークンの中身は event.requestContext.authorizer.claims に展開され、claims.sub でユーザーを一意に識別できる。
Step 6（検証NG）: API Gateway が 401 と {"message":"Unauthorized"} を返す。 Lambda は呼ばれないため、処理も料金も発生しない。

保護したメソッドと、しなかったメソッド

メソッドとパス 認可 理由
GET /api/v1/routes 必須 既存ルートの取得。ログイン後の画面からしか呼ばない
POST /api/v1/routes 必須 ルートの生成。AI と地図サービスを呼ぶため、特に守る価値が高い
GET /api/v1/conditions 必須 検索条件マスタの取得。ホーム画面（ログイン後）からしか呼ばない
POST /api/v1/password-reset-verifications なし パスワードを忘れた人がログインする前に呼ぶ。認可を付けると機能しなくなる

このマージの時点で API Gateway のメソッドは4つあり、そのうち3つを保護しました。 4つ目の照合API（ユーザー名とメールアドレスの組み合わせを確かめる API）だけは、ログイン前に呼ぶ必要があるため認可を付けていません。

この修正のあとに追加された API（口コミの投稿・取得、写真アップロードURLの発行、散歩実績の保存）も、 同じ cognitoAuthorized の設定を渡して保護しています。 つまりこのマージは、以降に増える API が従う型を作ったことになります。

💻 コードの解説

iac/lib/michishiru-stack.ts（変更）

インフラの定義ファイルです。ここにオーソライザーを1つ作り、保護したいメソッドへ渡します。 

const apiAuthorizer = new apigateway.CognitoUserPoolsAuthorizer(
  this,
  'ApiAuthorizer',
  {
    cognitoUserPools: [userPool],
    // API 本体と同じ理由で物理名を指定する（AWSコンソールで識別するため）
    authorizerName: `michishiru-api-authorizer-${stage}`
  }
);

// 保護する3メソッドへ渡す設定。authorizationType は省略すると
// 既定値に引きずられるため、COGNITO を明示する。
const cognitoAuthorized: apigateway.MethodOptions = {
  authorizer: apiAuthorizer,
  authorizationType: apigateway.AuthorizationType.COGNITO
};

cognitoUserPools: [userPool] で「どのユーザープールが発行したトークンを正しいとみなすか」を指定します。 userPool は withBackend（バックエンドを含めるかどうかの切り替え）の外側で作られているため、ここからそのまま参照できます。

設定を cognitoAuthorized という変数にまとめているのは、3か所へ同じものを渡すためです。 authorizationType をわざわざ書いているのは、省略すると既定値に引きずられる可能性があるためで、COGNITO を明示しています。

実際にメソッドへ渡すのは、addMethod の第3引数です。 

const routesResource = v1Resource.addResource('routes');
routesResource.addMethod(
  'GET',
  new apigateway.LambdaIntegration(getRouteFn),
  cognitoAuthorized
);
routesResource.addMethod(
  'POST',
  new apigateway.LambdaIntegration(createRouteFn),
  cognitoAuthorized
);

一方、照合APIには第3引数を渡しません。渡さない＝認可なしです。 この「付けない」という判断には、コードにはっきり理由を書き残しています。 

// POST /api/v1/password-reset-verifications
// ここだけ認可を付けない。パスワードを忘れた利用者がログインする前に呼ぶため、
// Cognito オーソライザーで守ると機能しなくなる。
// 総当たりへの備えは回数制限（API Gateway のスロットリング / WAF）で行う方針だが、
// まだ未対応（ミチシル_前提条件.md の「照合APIの保護」に残置）。
const passwordResetVerificationsResource = v1Resource.addResource(
  'password-reset-verifications'
);
passwordResetVerificationsResource.addMethod(
  'POST',
  new apigateway.LambdaIntegration(verifyPasswordResetTargetFn)
);

frontend/src/services/authService.js（変更）

Cognito とのやり取りをまとめているファイルです。ここに fetchIdToken を追加しました。 

export const fetchIdToken = async () => {
  const session = await fetchAuthSession();
  const idToken = session.tokens?.idToken?.toString();

  if (idToken) {
    return idToken;
  }

  // composable は error.message をそのまま画面へ出すため、ここに利用者向けの文言を入れる
  const error = new Error(NO_VALID_SESSION_MESSAGE);
  error.name = 'NoValidSession';
  throw error;
};

fetchAuthSession() は Amplify の関数で、ブラウザに保存されているセッションを読み出します。 ?.（オプショナルチェーン）は「途中が undefined でもエラーにせず undefined を返す」書き方で、未ログインの場合に備えています。

※ 現在の authService.js では、この関数の先頭に「開発サーバーでデザイン確認用のダミートークンを返す」分岐（import.meta.env.DEV && isPreviewIdTokenEnabled）が増えています。これは後続のマージ 3c4fc0b で加わったもので、上の抜粋（このマージ時点のコード）には含まれません。

トークンが取れなかったとき、null を返さずに例外を投げているのがこの関数の要点です。 呼び出し側が「通信に失敗した」と「ログインが切れた」を区別できる必要があるためです。 例外には name = 'NoValidSession' を付け、画面に出す文言の対応表にも同じキーを登録しています。 

const NO_VALID_SESSION_MESSAGE =
  'ログインの有効期限が切れました。もう一度ログインしてください';

const ERROR_MESSAGES = {
  // ...
  // ここから下はAPIの認可で出るもの
  NoValidSession: NO_VALID_SESSION_MESSAGE
};

文言を定数に切り出しているのは、2つの経路から同じ文言を出す必要があるためです。 ログインの失敗は対応表（toAuthErrorMessage）を引いて表示されますが、API の認可で失敗した場合は error.message がそのまま表示されます。別々に書くと、経路によって文言が変わってしまいます。

frontend/src/services/conditionService.js・routeService.js（変更）

API を呼ぶ関数に、トークンの取得とヘッダーの付与を足しました。検索条件マスタの取得はこうなっています。 

const idToken = await fetchIdToken();

const response = await fetch(`${API_BASE_PATH}/conditions`, {
  headers: { Authorization: idToken }
});

ルート生成（POST）は Content-Type と並べて書きます。 

const response = await fetch(`${API_BASE_PATH}/routes`, {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: idToken
  },
  body: JSON.stringify(/* ... */)
});

fetchIdToken() の例外は、このファイルでは try で捕まえません。 そのまま上位（composable）へ伝わり、画面にメッセージが出ます。「どの層が何を担当するか」を分けているためです。

なお、同じヘッダーの付与が2ファイルに重複しています。これは意図した上での判断で、ファイル先頭のコメントに 「呼び出し箇所が3つだけのため今回は抽象化しない。3ファイル目が出た時点で共通化する」と残してあります。

tools/localApiServer.js（変更）

ローカル開発では Cognito オーソライザーが存在しません。 そこで、API Gateway が入れてくれるはずのユーザー情報を、決め打ちの値で用意しています。 

const LOCAL_DEV_USER_SUB = 'local-dev-user';
const LOCAL_DEV_USERNAME = 'local-dev';

const buildEvent = (request, requestUrl, body) => ({
  httpMethod: request.method,
  path: requestUrl.pathname,
  queryStringParameters: Object.fromEntries(requestUrl.searchParams.entries()),
  headers: request.headers,
  body,
  requestContext: {
    authorizer: {
      claims: {
        sub: LOCAL_DEV_USER_SUB,
        'cognito:username': LOCAL_DEV_USERNAME
      }
    }
  }
});

重要なのは、このハーネスは認可を真似るだけで、検証は一切しないという点です。 Authorization ヘッダーの中身は見ません。それでよい理由は、127.0.0.1（自分のパソコンの中）だけで待ち受けており、 tools/ 配下はデプロイされないためです。本番の守りは API Gateway が行います。

sub の値を local-dev-user という、いかにも開発用の文字列にしているのも意図的です。 本物の sub は UUID 形式なので、データを見たときにローカルの記録だと一目で分かります。

iac/test/iac.test.ts（変更）

認可は「付け忘れても画面は普通に動いてしまう」種類の設定です。気付けないまま穴が残るのを防ぐため、テストで件数を数えています。 

test('未認証のメソッドはログイン前に呼ぶ照合APIだけである', () => {
  // 認可を付け忘れたメソッドを足したら落ちるようにするための検証。
  // 論理IDは CDK の生成規則に依存するため、直書きせず経路から引く
  const resources = template.findResources('AWS::ApiGateway::Resource');
  const passwordResetResourceId = Object.entries(resources).find(
    ([, resource]) => resource.Properties?.PathPart === 'password-reset-verifications'
  )?.[0];

  expect(passwordResetResourceId).toBeDefined();

  const methods = Object.values(template.findResources('AWS::ApiGateway::Method'));
  const unauthorizedMethods = methods.filter(
    (method) => method.Properties?.AuthorizationType !== 'COGNITO_USER_POOLS'
  );

  expect(unauthorizedMethods).toHaveLength(1);
  expect(unauthorizedMethods[0].Properties?.ResourceId?.Ref).toBe(
    passwordResetResourceId
  );
});

template は、CDK のコードから組み立てた CloudFormation テンプレート（AWS へ渡す設計図）です。 実際に AWS へデプロイせずに、設計図の中身を調べられます。

追加したテストは3つです。

テスト名 何を確かめるか
API に Cognito オーソライザーを1つ作成する 種類が COGNITO_USER_POOLS、名前が michishiru-api-authorizer-prod のオーソライザーがちょうど1つあること
ログイン後に呼ぶ3つのメソッドを Cognito 認可で保護する 保護されたメソッドが3件で、その内訳が GET 2件・POST 1件であること

3つ目が特に大事です。「認可なしは照合APIの1件だけ」という形で書いているので、 将来うっかり無認可の API を足すとテストが落ちます。

frontend/src/services/__tests__/（新規2ファイル）

ヘッダーが本当に付いているかを自動で確かめるテストです。Amplify の実体を読み込まずに済むよう、トークン取得を差し替えています。 

// Amplifyの実体を読み込ませないため、トークン取得を差し替える
vi.mock('@/services/authService', () => ({
  fetchIdToken: vi.fn(async () => 'dummy-id-token')
}));

test('トークンにスキーム接頭辞を付けない', async () => {
  stubFetch({ body: {} });

  await createRoute(CREATE_ROUTE_CONDITIONS);

  const [, options] = vi.mocked(fetch).mock.calls[0];

  // Cognitoオーソライザーは値をトークンそのものとして検証するため、
  // `Bearer ` を付けると認可に失敗する
  expect(options.headers.Authorization).toBe('dummy-id-token');
});

vi.mock は「このファイルの代わりに、こちらの偽物を使って」とテストに指示する仕組みです（モック）。 stubFetch は fetch そのものを偽物に差し替えるヘルパーで、実際の通信は発生しません。 toBe('dummy-id-token') という厳密な一致で比べているため、接頭辞が付いたら落ちます。

セッション切れの扱いも確かめています。fetchIdToken が例外を投げた場合、 例外がそのまま上へ伝わり、API は1度も呼ばれないことを検証しています。 

await expect(createRoute(CREATE_ROUTE_CONDITIONS)).rejects.toMatchObject({
  name: 'NoValidSession'
});

// トークンが取れない時点で中断するため、APIは呼ばない
expect(fetch).not.toHaveBeenCalled();

⚠️ 注意ポイント

1. Bearer を付けてはいけない

Web の世界では Authorization: Bearer <トークン> と書く流儀が広く使われていますが、 API Gateway の Cognito オーソライザーは既定でヘッダーの値をトークンそのものとして検証します。 接頭辞を付けると、トークンの先頭に余計な文字が混ざった状態になり検証に失敗します。 

// 正しい
headers: { Authorization: idToken }

// 失敗する
headers: { Authorization: `Bearer ${idToken}` }

この間違いは気付きにくいため、フロントのテストで厳密一致を確認しています。

2. トークンをキャッシュしてはいけない

fetchIdToken の結果を変数に取り置いて再利用したくなりますが、やってはいけません。 IDトークンの有効期限は1時間ですが、散歩はそれより長く続くことがあります。

fetchAuthSession はリフレッシュトークン（有効期限5日）を使って期限切れのトークンを自動で更新してくれるので、 リクエストごとに呼ぶのが最も単純で安全です。キャッシュすると期限切れのトークンを送り続け、401 になります。

3. 照合APIは今も無認可のまま

POST /api/v1/password-reset-verifications は、ログイン前に呼ぶ必要があるため認可で守れません。 総当たり（組み合わせを機械的に試す攻撃）への備えは、回数制限（API Gateway のスロットリング / AWS WAF）で行う方針ですが、 まだ未対応です。前提条件書の「今後追加予定の要素」に残っています。

4. 401 のときは英語の文言が出ることがある

API Gateway のオーソライザーは {"message":"Unauthorized"} を返すため、 この文言がそのまま画面に出る可能性があります。既存のエラー処理には手を入れていないため、残課題です。

ただし、ブラウザ側でトークンが取れないケース（＝多くのセッション切れ）は NoValidSession の経路を通り、 日本語の「ログインの有効期限が切れました。もう一度ログインしてください」が出ます。 英語が出るのは「トークンは取れたが API 側で失効扱いになった」という狭い場合に限られます。

5. ローカルで通ることは、本番で通る保証にならない

ローカルのAPIハーネスはトークンを検証しません。したがって 「ローカルで動いたからヘッダーは正しい」とは言えません。 ヘッダーの正しさはフロントのテストで、認可の設定は IaC のテストで確かめてください。

✅ 動作確認方法

テストの実行

  1. インフラ（認可の設定）を確かめる 
    cd iac
npm ci          # 初回のみ。node_modules が無い場合
npm run build   # TypeScript の型チェック
npm test        # オーソライザーと保護対象の件数を検証

    設計図そのものを見たい場合は、合成（synth）して確かめます。 

    npx cdk synth Michishiru-dev -c withBackend=true --quiet

    生成された iac/cdk.out/Michishiru-dev.template.json の中で、 AWS::ApiGateway::Authorizer が1件あることを確認できます。

  2. フロント（ヘッダーの付与）を確かめる 
    cd frontend
npm run lint
npm test
npm run build

ローカルで画面から確認する

  1. frontend/.env.local に VITE_COGNITO_USER_POOL_ID と VITE_COGNITO_USER_POOL_CLIENT_ID を設定する（これが無いとログイン自体ができません）
  2. リポジトリのルートで npm run dev を実行し、フロント（http://localhost:5173）と ローカルAPIハーネス（http://127.0.0.1:3001）を同時に起動する
  3. ログインしてホーム画面を開く（検索条件マスタの取得が走ります）
  4. ブラウザの開発者ツールの「ネットワーク」タブで conditions のリクエストを選び、 リクエストヘッダーに Authorization があり、値が Bearer で始まっていないことを確認する

認可が効いていることを確認する（デプロイ後）

トークンを付けずに API を直接叩くと 401 が返ります。 

curl -i "https://<配信ドメイン>/api/v1/conditions"
# → HTTP/1.1 401 Unauthorized
#   {"message":"Unauthorized"}

ローカルのAPIハーネスは検証しないため、この確認は AWS へデプロイした環境で行ってください。
