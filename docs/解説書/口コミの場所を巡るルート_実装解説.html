🧩 先に知っておきたいこと

ルート作成の流れ（createRoute）
ジャンル → カテゴリを引き、Amazon Location Service（Places）で周辺の候補を集め、Amazon Bedrock（AI）に選ばせ、 Location Service（Routes）で徒歩経路を計算する、という流れです。全体は ルート作成API を先に読んでください。 この機能は、その「候補」に口コミの場所を混ぜる追加です。
口コミの場所
利用者が案内画面で投稿した口コミは、DynamoDB の Review-<環境> テーブルに「場所（sk = 'SPOT'）」と「口コミ（sk = 'REVIEW#<userId>'）」の行で保存されています。 投稿の仕組みは 口コミ投稿 を参照してください。
GSI（グローバルセカンダリインデックス）
DynamoDB で「本来のキー以外」の項目で検索するための索引です。ここでは場所の一覧を引く GSI-SpotList（キーが sk）と、 利用者ごとの口コミを引く GSI-UserReview（キーが userId）を使います。
ピンの色の意味
地図の色は意味に1対1で固定しています。赤 = 新規で投稿する場所、オレンジ = 自分の口コミの場所、紫 = 他の人の口コミの場所です（用語辞書「口コミのピンの色」）。

📖 この機能について

ルートを作るとき、検索条件のジャンルに合い、現在地から選んだ距離以内にある口コミの付いた場所を、 平均評価の高い順にルートの候補へ混ぜる機能です。選ばれた口コミの場所は地図で番号つきの丸として描き、 他の人の口コミなら紫、自分の口コミならオレンジで塗ります。丸を押すと、その場所の口コミがフォームで開きます。

あわせて、Places の候補のうちチェーン店（BusinessChains を持つ場所）は選ぶ優先順位を下げました。

🎯 なぜこの機能が必要？

Places の候補だけだと、どこにでもあるチェーン店や「地図上は施設だが散歩で寄るほどではない場所」が選ばれがちでした。 実際に歩いた人が評価した場所を巡れば、ルートの満足度が上がり、口コミを投稿する動機（自分の投稿が誰かのルートに入る）にもなります。

関連するユーザーストーリーは US-2（条件に合うスポットを DB や AI に選定させる）です。

🔄 処理の流れ

Step 1: 候補を並行して集める（service.js の createRoute）
Places の周辺検索と、口コミの場所の取得（collectReviewCandidateSpots）を Promise.all で同時に行います。 口コミの場所の取得では、場所の一覧（GSI-SpotList）と自分の口コミ（GSI-UserReview）も並行して引きます。
Step 2: 口コミの場所を絞り込み、並べる
ジャンル（投稿時に選んだ genreId）が検索条件と一致し、現在地から「選んだ距離（km）」以内のものだけを残し、 平均評価 → 評価件数 → 現在地からの近さ の順に並べます。自分が投稿済みかの目印（isMyReviewSpot）もここで付けます。
Step 3: Bedrock へ渡す候補を組み立てる（buildPromptCandidateSpots）
口コミの場所を上位5件まで先頭に置き、それと同じ名前・同じ場所（40m以内）の Places の候補を外し、チェーン店を後ろへ回して、全体を20件までにします。 口コミの場所には "isReviewSpot": true と平均評価、チェーン店には "isChain": true を付けて渡します。
Step 4: AI に選ばせる（prompt.js）
プロンプトで「口コミの場所はスポットの4割程度・最低1か所・評価の高いものを優先。ただし距離を最優先」「チェーン店はほかに候補があれば選ばない」と指示します。
Step 5: 目印の付け直しと上限（markReviewSpots / limitReviewSpots）
AI の出力は名前と座標だけなので、名前から口コミの場所を引き直してIDと元の座標を付けます。 口コミの場所が上限（スポット数 × 0.4 を四捨五入、最低1か所）を超えていれば、評価の低いものから外します。
Step 6: 距離の調整
既存の距離調整（経路から外れたスポットの除外、超過時のスポット削減）を行います。削るときは口コミでないスポットから外し、口コミの場所をできるだけ残します（removeOneSpotForDistance）。
Step 7: 1か所も通らなければ差し込む（ensureReviewSpot）
ルートが口コミの場所を1か所も通らない場合、評価の高い順に「遠回りが最小になる位置へ差し込む」「最寄りのスポットと入れ替える」を最大3通り試します。 徒歩で到達でき（経路から150m以内）、総距離が許容範囲に収まるものだけを採用し、だめなら元のルートのままにします（距離を優先）。
Step 8: 自分の口コミかを最終決定し、応答に載せる
差し込み後の最終スポットに markMyReviewSpots で isMyReviewSpot を付け、応答の各スポットに isReviewSpot / isMyReviewSpot / reviewSpotId / reviewLng / reviewLat を載せます。
Step 9: 地図に描く（フロント）
utils/routeResponse.js がこれらを画面用の形（reviewPosition: { lng, lat }）に変換し、 RouteMap.vue が番号の丸（spot-marker is-review、自分の口コミなら is-mine も付く）として描きます。 押すと selectReviewSpot を emit し、案内画面がその場所の口コミをフォームで開きます。その場所の口コミのピンは重ねて描きません。

2つの座標（lng / lat と reviewLng / reviewLat）

ルートのスポットの lng / lat は、線とマーカーがずれないよう経路上へ寄せた座標です（最大150mずれる）。 一方、口コミを開くときは「半径40m以内を同じ場所とみなす」規則で引くため、寄せた座標では見つからないことがあります。 そこで口コミのピンの元の位置を reviewLng / reviewLat（画面では reviewPosition）として別に返しています。

⚠️ 注意ポイント

ジャンルを持たない口コミの場所は候補にならない
投稿時の genreId と検索条件のジャンルを突き合わせるため、ジャンルの無い場所は条件に合うか判断できず外れます。 ここで比べるのはどちらも検索条件マスタの英語ID（nature など）です。
場所が増えると取りこぼす
場所の一覧は新しい順に最大200件しか読みません（REVIEW_SPOT_QUERY_LIMIT）。現在地からの距離は取得後に絞るため、 投稿が増えると近くの古い場所が候補に入らなくなります。コード中に「現在地周辺だけを引ける索引へ切り替える」TODO があります。
プロンプトの割合と上限は同じ定数から作る
REVIEW_SPOT_RATIO（0.4）を変えると、プロンプトの「4割」と Service 層の上限が両方変わります。片方だけ直さないでください。
テスト用データの投入
backend/tools/seedReviewSpots.js は大手町ビル周辺に架空ユーザーの口コミを入れるスクリプトです。既定は確認だけで、 --apply で投入、--delete で削除します。テーブル名に prod を含む場合は実行しません。

✅ 動作確認方法

  1. dev のテーブルにテスト用の口コミを入れる（任意）: backend で REVIEW_TABLE_NAME=Review-dev npm run seed:review-spots で内容を確認し、問題なければ -- --apply を付けて投入する（AWS の認証情報が必要）
  2. 口コミの場所の近く（例: 大手町）を現在地にしてルートを作成し、提案・案内画面で番号つきの紫の丸が出ることを確かめる
  3. 自分が口コミを投稿した場所がルートに入ったとき、丸がオレンジになることを確かめる
  4. 案内画面で丸を押し、その場所の口コミがフォームで開くことを確かめる
  5. テスト: backend で npm test（functions/createRoute/__tests__/ の service / reviewSpotRepository / prompt / placesRepository）、 frontend で npm test（src/components/feature/route/__tests__/RouteMap.test.js / src/utils/__tests__/routeResponse.test.js）、iac で npm test
