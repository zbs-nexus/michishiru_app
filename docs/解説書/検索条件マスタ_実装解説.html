🧩 先に知っておきたいこと

マスタ
画面の選択肢のように「あまり変わらないが、コードに直書きしたくない一覧」を入れておくテーブルです。ミチシルでは DynamoDB の michimaster テーブルが検索条件マスタです。
項目の種別は pk で見分ける
1つのテーブルに目的（PURPOSE#ALL）・ジャンル（GENRE#ALL）・距離（DISTANCE#ALL）が入っており、パーティションキー pk の値で種別を判別します。 各項目は isActive（使うか）と sortOrder（表示順）を持ちます。
genreId と genreName
genreId はコード上の英語ID（nature など）、genreName は画面に出す日本語名（自然 など）です。API とのやり取りでは英語IDを使います。

📖 この機能について

ホーム画面（US-1）のジャンルの選択肢と距離スライダーの範囲を、コードの定数ではなく検索条件マスタから取得する仕組みです。 バックエンドの getConditions（GET /api/v1/conditions）がマスタの全項目を返し、フロントが画面用の形に整えます。

種別現在の使い方
ジャンル（GENRE#ALL）ボタンの選択肢。genreId / genreName を使う。おまかせのランダム選択の元にもなる
距離（DISTANCE#ALL）表示順の先頭を下限、末尾を上限とするスライダーの範囲（例: 1km〜10km）
目的（PURPOSE#ALL）マスタには残っているが、画面では使わない（8a8c110 でジャンルと距離の2項目に絞った）

🎯 なぜこの機能が必要？

  • 選択肢をコードに書くと、ジャンルを増やすたびにフロントの修正とデプロイが必要になるため
  • ルート作成（createRoute）も同じマスタを引いてジャンル → スポットのカテゴリを決めるので、画面とサーバーで選択肢の食い違いを起こさないため

🔄 処理の流れ

Step 1: ホーム画面を開く
RouteConditionView が useRouteConditionOptions の loadConditionOptions() を呼びます。取得中はマスコットを出さず、失敗したらマスコットの吹き出し（注意の見た目）で理由を伝え、「再読み込み」ボタンを出します。
Step 2: API を呼ぶ（conditionService.js）
idToken を Authorization ヘッダーに載せて GET /api/v1/conditions を呼び、JSON でなければ（SPA の index.html が返ってきた等）その場でエラーにします。
Step 3: サーバー側（getConditions Lambda）
repository が michimaster を全件 Scan して返します。テーブル名の環境変数が未設定（ローカル開発）のときは seedConditions.js の固定データを返します。
Step 4: 画面用に整える（フロント）
種別ごとに有効な項目を表示順に並べ、ジャンルは { value: genreId, label: genreName, icon }、距離は { minKm, maxKm, minLabel, maxLabel, defaultKm } にします。 選択中の距離が範囲外なら範囲内へ補正します。

💻 コードの解説

backend/functions/getConditions/repository.js

export const listConditions = async () => {
  if (!hasConditionTable()) {
    return SEED_CONDITIONS;
  }

  const response = await sendWithRetry(
    new ScanCommand({
      TableName: CONDITION_TABLE_NAME
    })
  );

  return response.Items ?? [];
};
  • 規約では Scan を既定の取得方法にしないことになっていますが、マスタは件数が少なく全件が必要なため Scan を使っています（コメントに理由あり）
  • スロットリング（混雑による拒否）は最大3回まで待ち時間を延ばして再試行します
  • service は全項目をそのまま返します。絞り込み・並べ替えはフロントの役割です

⚠️ 注意ポイント

マスタテーブルは CDK 管理ではない
michimaster はコンソールで手作りされたテーブルで、CDK からは名前で参照しているだけです（Table.fromTableName）。 環境ごとに分かれておらず、命名規則（PascalCase-<環境>）や属性名の規約（camelCase）からも外れています。前提条件書の「マスタテーブルのCDK管理」は未対応のままです。
ジャンルIDの値が資料によって違う
ローカル用のシード（seedConditions.js）のジャンルIDは nature / photo / history / gourmet ですが、 用語辞書の「ジャンルの選択値」は nature / city / history / gourmet のままです。 本番のマスタの値はコンソールで確認してください（フロントの constants/genreImages.js は、IDで引けないときに日本語名でも引く保険を持っています）。
ローカルではシードが返る
CONDITION_TABLE_NAME を設定しないと本物のマスタを読まず、シードの固定データが返ります。本番との差に気付きにくいので、マスタを変えたときは dev 環境で確認してください。

✅ 動作確認方法

  1. npm run dev で起動してログインし、ホーム画面にジャンルのボタンと距離スライダー（1km〜10km）が出ることを確かめる
  2. ローカルAPIを止めて再読み込みし、マスコットの吹き出しに「検索条件の取得に失敗しました（…）」が出て、「再読み込み」ボタンで取り直せることを確かめる
  3. テスト: backend で npm test（functions/getConditions/__tests__/service.test.js）、frontend で npm test（src/services/__tests__/conditionService.test.js。認可ヘッダーの確認を含む）
