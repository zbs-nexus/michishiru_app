📖 この機能について

この機能は、ミチシルアプリの中核となるルート作成機能です。 ユーザーが「自然が好き」「3km歩きたい」と条件を入力すると、AIが現在地の周辺から面白いスポットを選んで、散歩ルートを自動で作ってくれます。

イメージとしては、「散歩のガイドさん」が周辺の公園やカフェを知っていて、あなたの希望に合わせてちょうど良い散歩コースを組んでくれる、そんな機能です。

🎯 なぜこの機能が必要？

散歩をしたいけど、以下のような悩みを持っている人は多いです：

  • 近所にどんな場所があるか知らない
  • いつも同じ道を歩いてしまって飽きる
  • ちょうど良い距離のコースが分からない
  • 行きたいジャンル（自然、カフェなど）に合った場所を探すのが面倒

この機能は、そんな悩みを解決するために、AIと地図サービスを組み合わせて、一人ひとりに合った散歩ルートを自動で作ります。

🔄 処理の流れ（全体像）

ユーザー → フロントエンド → API Gateway → Lambda(createRoute) ↓ 【Step 1】DynamoDBからマスタデータを取得 「自然」→ 公園、展望台などのカテゴリ ↓ 【Step 2】Amazon Location Service (Places) 現在地から半径内の公園や展望台を検索 ↓ 【Step 3】Amazon Bedrock (AI) 候補スポットから、ちょうど良いルートを選定 ↓ 【Step 4】Amazon Location Service (Routes) 選ばれたスポットを繋ぐ徒歩経路を計算 ↓ 【Step 5】距離の調整 長すぎたらスポットを減らす ↓ 完成したルート → フロントエンドへ返す

📝 詳しい処理の流れ

Step 0: リクエストを受け取る（handler.js）

フロントエンドから送られてきたリクエスト（JSON形式）を受け取ります。

// リクエストの例 { "genreId": "nature", // ジャンル（自然） "targetDistanceKm": 3, // 希望距離（3km） "currentLocation": { "lat": 35.6812, // 現在地の緯度 "lng": 139.7671 // 現在地の経度 } }

やっていること：

  • JSONを解析できるかチェック
  • 必須項目（ジャンル、距離、現在地）が入っているかチェック
  • 問題なければService層（ビジネスロジック）に処理を渡す
Step 1: ジャンルから検索カテゴリを決める（service.js + spotCategoryRepository.js）

ユーザーが選んだジャンル（例：「自然」）から、実際に地図サービスで検索するカテゴリ（例：「公園」「展望台」）を決めます。

なぜ変換が必要？
ユーザーには「自然」という分かりやすい言葉で選んでもらいますが、地図サービスは「park」「viewpoint」のような細かいカテゴリで場所を管理しているためです。

具体的な流れ：

  1. ジャンルマスタから「nature」→「1」という数字に変換
  2. カテゴリマスタから「1」→「park, viewpoint, ...」のリストに変換
  3. カテゴリが多すぎる場合はランダムで上限数まで絞る（生成時間短縮のため）
Step 2: 周辺のスポットを検索する（placesRepository.js）

Amazon Location Service（地図サービス）に、現在地の周辺からスポットを探してもらいます。

検索範囲の決め方：
希望距離が3kmなら、出発地から概ね1.5km以内のスポットを探します。 なぜなら、周回コースなので各スポットは希望距離の半分より内側にあることが多いからです。

// 検索の例 現在地: 東京駅 半径: 1500m カテゴリ: 「公園」 → 結果: 皇居外苑、日比谷公園、丸の内仲通り など

重複の除外：
複数のカテゴリで検索すると、同じ場所が何回も出てくることがあります。 例えば「皇居外苑」は「公園」でも「展望スポット」でも出てくるので、名前で重複を除いて1つにまとめます。

Step 3: AIにルート案を作ってもらう（bedrockRepository.js）

Amazon Bedrock（AI）に、候補スポットの中から「どこを巡るか」と「どんなルートにするか」を考えてもらいます。

AIに伝える情報：

  • 現在地
  • 希望距離（3km）
  • 候補スポットのリスト（名前と座標）
  • （再生成の場合）前回の距離と調整の方向
// AIが返してくる内容 { "route_title": "緑豊かな都会のオアシス散歩", "concept_story": "皇居外苑から...", "selected_waypoints": [ { "name": "皇居外苑", "position": [139.7571, 35.6838] }, { "name": "日比谷公園", "position": [139.7544, 35.6742] } ] }

ポイント：
AIは「ただ近い場所を選ぶ」だけでなく、「このルートの魅力」を文章で説明してくれます。 これがユーザーに表示される「コンセプトストーリー」になります。

Step 4: 徒歩経路を計算する（routesRepository.js）

AIが選んだスポットを、実際の道路で繋いだ徒歩経路を計算します。

計算するもの：

  • 各スポット間の道なり距離
  • 各スポット間の所要時間
  • 地図に描くための座標の点（経路の線）
// 経路計算の例 出発地 → 皇居外苑 → 日比谷公園 → 出発地 結果: 総距離: 2800m 総所要時間: 40分 経路の座標: [[139.7671, 35.6812], [139.7670, 35.6813], ...]

「スナップ」とは？
AIが選んだスポットの座標が、実際の道路から少しずれていることがあります。 経路計算サービスは、スポットを「最も近い道路上の点」に移動（スナップ）して、正確な経路を作ります。

Step 5: 距離を調整する（service.js）

計算した総距離が、希望距離と大きくずれていたら調整します。

調整方法：

状況 対処
距離が長すぎる（目標の1.4倍以上） スポットを1つずつ減らして再計算
距離が短すぎる（目標の0.5倍未満。9/30 までは0.6倍） AIに「もっと長くして」と再生成を依頼（前回の距離を伝え、ばらつき temperature を 0.2 → 0.5 に上げる）
許容範囲内（0.5倍〜1.4倍） そのまま採用

なぜ完全に一致しないの？
スポットの配置や道路の形によって、ちょうど3.0kmにするのは難しいです。 そのため、目標3kmなら1.5km〜4.2kmの範囲を「許容範囲」として、その中に収まれば良しとしています（DISTANCE_LOWER_RATIO = 0.5 / DISTANCE_UPPER_RATIO = 1.4）。 AIへの依頼は最大3回（MAX_ROUTE_RETRY_COUNT）で、最後まで範囲に入らなければ「目標距離に近いルートを作成できませんでした」のエラー（404）を返します。

💻 主要なコードの解説

1. handler.js（入口）

Lambda関数の入口です。リクエストを受け取って、レスポンスを返すだけのシンプルな役割です。

export const handler = async (event) => { // 1. JSONをパース（解析） const body = parseRequestBody(event); // 2. バリデーション（必須項目のチェック） const validationResult = validateCreateRouteRequest(body); // 3. Service層にルート作成を依頼 const route = await createRoute(validationResult.value); // 4. 結果を整えて返す return buildSuccessResponse(toResponseBody(route)); };

ポイント： handler.js にはビジネスロジック（どんなルートを作るか）は書きません。 それは全てService層（service.js）に任せます。

2. service.js（ルート作成の司令塔）

ルート作成の全体的な流れを制御します。各Repositoryを呼び出して、結果を組み合わせます。

export const createRoute = async ({ genreId, targetDistanceKm, currentLocation }) => { // Step 1: ジャンル→カテゴリの変換 const spotCategoryIds = await resolveSpotCategoryIds(genreId, repositories); // Step 2: 周辺スポットの検索 const candidateSpots = await collectCandidateSpots(...); // Step 3〜5: AIで選定 → 経路計算 → 調整 while (retryCount < MAX_ROUTE_RETRY_COUNT) { const plan = await repositories.generateRoutePlan(...); const route = await repositories.calculateWalkingRoute(...); // 許容範囲内ならループを抜ける if (isWithinTargetRange(route.totalDistanceM, targetDistanceKm)) { break; } // 長すぎたらスポットを削る // 短すぎたら再生成 } return { routeTitle, conceptStory, totalDistanceM, ... }; };

ポイント： この関数がルート作成の「脳」です。 各Repositoryは「手足」として、外部サービスにアクセスするだけです。

3. placesRepository.js（スポット検索）

Amazon Location Serviceとやり取りして、周辺スポットを取得します。

export const searchNearbySpots = async ({ currentLocation, spotCategoryId, queryRadiusM }) => { const response = await getPlacesClient().send( new SearchNearbyCommand({ QueryPosition: [currentLocation.lng, currentLocation.lat], QueryRadius: Math.round(queryRadiusM), Filter: { IncludeCategories: [spotCategoryId] }, MaxResults: MAX_SPOT_CANDIDATES }) ); return response.ResultItems.map(item => ({ name: item.Title, position: item.Position })); };

ポイント： Repository層は、外部サービス固有の書き方（ここではAWS SDKの使い方）を知っている唯一の場所です。 他の層は、この関数を呼ぶだけで、AWS SDKの詳細を知る必要がありません。

4. bedrockRepository.js（AIでルート案を生成）

Amazon BedrockのAIに、候補スポットからルート案を選んでもらいます。

export const generateRoutePlan = async (promptText, temperature) => { const response = await getBedrockClient().send( new ConverseCommand({ modelId: BEDROCK_MODEL_ID, messages: [{ role: 'user', content: [{ text: promptText }] }], inferenceConfig: { temperature, maxTokens: BEDROCK_MAX_TOKENS } }) ); const rawText = response.output.message.content[0].text; const generated = parseGeneratedJson(rawText); return { routeTitle: generated.route_title, conceptStory: generated.concept_story, spots: generated.selected_waypoints.map(...) }; };

「temperature」とは？
AIの生成結果のばらつきを制御するパラメータです。 低い（0.3）と毎回似た結果、高い（0.7）と毎回違う結果になります。 初回は0.3で、再生成時は0.7にして、違う組み合わせを試すようにしています。

🆕 その後の変更（2026-09-16 〜）

現在の処理の流れ（2026-10-28 時点）

  1. おまかせの項目があれば、検索条件マスタからジャンル・距離をランダムに選ぶ（おまかせ条件）
  2. ジャンルID（英語）→ michimaster の数値ジャンルキー（genre_id）→ カテゴリマスタのカテゴリID群、の順に引く（da45137 以降）
  3. 検索半径を「目標距離 × 0.5」（500m〜5000m に収める）にして、カテゴリごとに Places の周辺検索。同時に口コミの場所も集める
  4. カテゴリが8件を超えるときは毎回ランダムに8件選ぶ。1件も見つからなければ、まだ試していないカテゴリで再検索（65d961c）
  5. 候補を最大20件に絞り、AI（Bedrock）にルート案を作らせる
  6. Routes で徒歩経路を計算。経路から150m以上外れるスポット（徒歩で入れない施設など）を除外して計算し直す（eaca0c2）
  7. 許容範囲（0.5〜1.4倍）に入るまで、長すぎればスポットを減らし、短すぎれば AI に再生成を依頼（最大3回）
  8. 口コミの場所を1か所も通らなければ差し込みを試す（口コミの場所を巡るルート）
  9. スポットのマーカーは経路上へ寄せた座標で返し、区間ごとの線（legs）も付けて応答する

1. 距離の調整（NZ-137: 9f8faf9 / f7dfb0b / 5bafcb3 / da45137 / NZ-158: 2999924）

距離の許容範囲は何度か変わっています。現在の値は上の Step 5 のとおりです。

時期許容範囲スポット数
9f8faf9（9/16）超過したらスポットを削る（最小2個）-
f7dfb0b / 5bafcb3（9/16）目標 ±1km。短すぎたら再生成、最後まで外れたら404最小1個
da45137（9/16）目標 × 0.6〜1.4（固定の±1kmは短距離に厳しすぎたため割合へ）-
2999924（9/30）目標 × 0.5〜1.4。受け付ける目標距離は1〜10km最大15個。プロンプトの「2〜3か所」の制限を外し、AI が距離に応じて数を決める

歩く速さは時速4km（秒速1.11m。WALKING_METERS_PER_SECOND）で、所要時間を API から取れないときの概算に使います（5bafcb3）。

2. 距離・時間の二重計上の解消と検索半径（4824242）

Routes の応答は、経路全体の集計（Summary）・区間ごと・さらに細かい単位で、同じ距離を何重にも持っています。 以前は応答の中の距離を全部足していたため、実際の何倍にもなっていました。現在は Routes[0].Summary だけを見ます。 あわせて、周回コースのスポットは出発地から目標距離の半分より内側にあることが多いので、検索半径を「目標距離 × 0.5」にして遠すぎる候補を検索の段階で外しています（SEARCH_RADIUS_RATIO）。

3. タイムアウト対策（433dd9c）

  • API Gateway は29秒で打ち切るため、Lambda のタイムアウトも29秒に合わせています。食べ歩きのようにカテゴリが20件を超えるジャンルでは周辺検索の並列数が増えて間に合わなかったため、1回に検索するカテゴリを最大8件（MAX_SEARCH_CATEGORIES）に絞りました。再作成のたびに違う組み合わせが選ばれます
  • 経路の座標は Ramer–Douglas–Peucker 法で間引きます（元の線から5m以内の点を省く。SIMPLIFY_TOLERANCE_M）。応答のサイズと地図の描画の負荷を下げるためです
  • フロント（routeService.js）は 502 / 503 / 504 を「一時的に混み合っています。時間を置いて、再試行してください。」と表示します

4. ジャンルの解決を michimaster へ集約（da45137 / e25f22d）

以前はジャンルを日本語の名称で専用のジャンルマスタから引いていたため、フロントが送る英語ID（nature）と一致しない不整合がありました。 現在は検索条件マスタ（michimaster）の pk = 'GENRE#ALL' / sk = 'METADATA#<genreId>' を英語IDで引き、数値のジャンルキー（genre_id）を得てからカテゴリマスタを引きます。 フロントも表示名ではなくジャンルID（genreId）を送るようにしました（e25f22d）。旧ジャンルマスタは廃止です。

const resolveSpotCategoryIds = async (genreId, repositories) => { const genreNumber = await repositories.queryGenreNumberByGenreId(genreId); ... const spotCategoryIds = await repositories.querySpotCategoryIdsByGenreNumber(genreNumber); ... };

5. 経路から外れるスポットの除外（eaca0c2）

Routes は各スポットを最寄りの歩ける道へ寄せて（スナップして）経路を引きます。皇居内の施設のように一般の歩行者が入れない場所だと、元の座標と寄せた座標が大きく離れ、 マーカーが線から外れた「飛び地」に見えていました。現在は区間の終点を寄せた座標とみなし、元の座標から150m（STRANDED_DISTANCE_THRESHOLD_M）を超えるスポットを外して計算し直します（最小スポット数を下回る場合は残す）。 応答のマーカー座標も寄せた座標にしているので、線とマーカーがずれません。プロンプトにも「立入制限区域など、歩行者が自由に入れない施設は選ばない」というルールを足しています。

6. スポットが見つからないときの再検索（65d961c）

// スポットが見つかるか、すべてのカテゴリを試すまで繰り返す while (candidateSpots.length === 0 && usedCategoryIds.length < allSpotCategoryIds.length) { const spotCategoryIds = limitSearchCategories(allSpotCategoryIds, usedCategoryIds); ... }

8件ずつ選んだカテゴリで1件も見つからなかったとき、使っていないカテゴリで検索し直します。あわせて、写真映えのジャンル（genre_id = 1）用のカテゴリを カテゴリマスタへ投入するスクリプト（backend/tools/seedPhotoCategories.js / updatePhotoCategories.js / listCategories.js）を追加しています。

7. 地図に線が描かれない不具合（NZ-143: fc3a531 / 9d799cc / c6c440c）

ルートの線が地図に描かれない不具合の修正です。原因の1つは、地図ライブラリが別スレッドで動かす処理（ワーカー）のファイルをビルド後に読み込めなかったことで、 RouteMap.vue でワーカーの URL を明示的に指定（setWorkerUrl）して解決しました（c6c440c）。あわせて線とスポットの色を青に変えています（fc3a531）。 9d799cc は原因の切り分け用のログの追加です。

⚠️ 注意ポイント

0. 許容範囲のコメントが一部古い（2026-10-28 追記）

service.js の isWithinTargetRange のコメントは「下限×0.6」のままですが、実際の値は constants.js の DISTANCE_LOWER_RATIO = 0.5 です。値は定数を正としてください。 また、マスタテーブル（michimaster とカテゴリマスタ）はコンソールで手作りされており、CDK 管理・環境分離・属性名の規約（snake_case の genre_id など）から外れたままです。

1. spotとwaypointの使い分け

コード内で「spot」と「waypoint」という似た言葉が出てきますが、意味が違います：

  • spot（スポット）: ユーザーが立ち寄る場所（公園、カフェなど）
  • waypoint（経由点）: 経路を描くための座標の点（道の曲がり角など）

混同すると、「巡ったスポット数」に道の折れ点まで数えて、おかしな数字が表示されます。

2. 座標の順序 [経度, 緯度]

Amazon Location Serviceは、座標を [経度, 緯度] の順で扱います。 これは一般的な「緯度、経度」とは逆なので注意してください。

// AWS Location Service position: [139.7671, 35.6812] // [経度, 緯度] // 一般的な表記 (35.6812, 139.7671) // (緯度, 経度)

3. レイヤーの責務を守る

このプロジェクトでは、以下のレイヤー構成を守ります：

  • Handler: リクエストの受付とレスポンスの返却だけ
  • Service: ビジネスロジック（どんなルートを作るか）
  • Repository: 外部サービスへのアクセスだけ

例えば、Repositoryにビジネスロジックを書いたり、Handlerで直接DBにアクセスしたりしてはいけません。

✅ 動作確認方法

ローカルでの確認手順

  1. バックエンドとフロントを同時起動
    # プロジェクトルートで実行 npm run dev

    これで、ローカルAPIサーバー（http://localhost:3001）とフロントエンド（http://localhost:5173）が起動します。

  2. フロントエンドからルート作成を試す
    • ブラウザで http://localhost:5173 を開く
    • ジャンル（自然など）と距離（3kmなど）を入力
    • 「ルート作成」ボタンをクリック
    • 地図上にルートが表示されればOK
  3. ログで内容を確認

    バックエンドのターミナルに、各Stepのログが出力されます：

    検索対象のカテゴリを決定しました 候補スポットを取得しました ルート案を生成しました 目標距離の許容範囲内のルートを作成しました

# backendディレクトリで実行 cd backend npm test

主要な関数（service.jsやvalidator.js）のテストが実行されます。 すべてのテストが通ることを確認してください。
