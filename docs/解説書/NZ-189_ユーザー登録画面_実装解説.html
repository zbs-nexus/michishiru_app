📖 この機能について

アプリの利用者が、自分でアカウントを作れる画面（/sign-up）を追加しました。ログイン画面の「アカウントをお持ちでない方は」のリンクから開けます。

あわせて、ログインの仕組みを支える Cognito のユーザープール（利用者の名簿のようなもの）を、手作業ではなく CDK（AWS の構成をコードで書く仕組み）で作るように変えました。それに伴い、自動デプロイの手順も変わっています。

ログイン画面と Cognito の基本は docs/Cognitoログイン画面_構築手順書.html を参照してください。ただし手順書の「GitHub の Variables に ID を登録する」手順は、この変更で不要になりました（後述）。

🎯 なぜこの機能が必要？

  • これまでは管理者がコンソールで1人ずつユーザーを作る必要がありました。
  • ユーザープールを手作業で作ると、dev と prod で設定がずれたり、IDを GitHub に登録し忘れたりします。コードにしておけば、同じ設定で何度でも作れます。

🔄 処理の流れ（ユーザー登録）

[ログイン画面] 「ユーザー登録」リンク
     ▼
[SignUpView 1段目] ユーザー名・メールアドレス・パスワード
     │  authStore.signUp → authService.signUpWithEmail → Cognito signUp
     │  （Cognito がメールに6桁の確認コードを送る）
     ▼
[SignUpView 2段目] 確認コード
     │  authStore.confirmSignUp → authService.confirmSignUpWithCode → Cognito confirmSignUp
     ▼
[ログイン画面] /login?registered=1 → 「ユーザー登録が完了しました」
Step 1: 登録情報を送る
SignUpForm.vue が入力値（ユーザー名とメールは前後の空白を除く）を親に渡し、SignUpView.vue がストアの signUp を呼びます。この時点のユーザーは「未確認」で、まだログインできません。
Step 2: 確認コードを入れる
SignUpConfirmForm.vue に送り先（一部が隠された形）を表示します。メールに届いたコードを入れると、ストアの confirmSignUp でユーザーが有効になります。届かないときは「再送」で resendCode を呼びます。
Step 3: ログイン画面へ
成功すると /login?registered=1 に移り、完了メッセージが出ます。自動ではログインしないので、登録した内容でログインしてもらいます。

🔄 処理の流れ（デプロイ）

GitHub Actions（deploy.yml）
  1. cdk deploy（1回目）… ユーザープールを含むインフラを作る
       └ --outputs-file cdk-outputs.json に UserPoolId などが書き出される
  2. node tools/exportCognitoOutputs.js
       └ cdk-outputs.json から ID を取り出し、VITE_COGNITO_* として次のステップへ渡す
  3. frontend で npm run build … ID がビルド結果に埋め込まれる
  4. cdk deploy（2回目）… できあがった frontend/dist を S3 に配信する

なぜ2回デプロイするのか: ユーザープールの ID は、作ってみるまで決まりません。フロントはビルドするときに ID を埋め込むので、「プールを作る → ID を受け取る → ビルド → 配信」の順にする必要があります。1回目の時点では frontend/dist がないので、静的ファイルのアップロードは行われません。

💻 コードの解説

frontend/src/services/authService.js — signUpWithEmail

const { isSignUpComplete, nextStep } = await cognitoSignUp({
  username,
  password,
  options: { userAttributes: { email } }
});

if (nextStep.signUpStep === 'CONFIRM_SIGN_UP') {
  return {
    isConfirmationRequired: true,
    codeDeliveryDestination: nextStep.codeDeliveryDetails?.destination ?? null
  };
}
  • 入力: ユーザー名・メールアドレス・パスワード。出力: 確認コードが必要か、と送り先。
  • ユーザープールはメールアドレスを必須にしているので、登録時に必ず送ります。
  • 想定外の次の手順（自動サインインなど）が返ってきたら、失敗として扱います。
  • ほかに confirmSignUpWithCode（コードで有効化）と resendConfirmationCode（コード再送）を追加しました。

エラー文言

Cognito のエラー名を日本語に置き換える表（ERROR_MESSAGES）に、登録で出るものを追加しました。toSignUpErrorMessage は表にないエラーのとき「ユーザー登録に失敗しました…」を返します。

エラー名画面の文言
UsernameExistsExceptionこのユーザー名は既に使われています
InvalidPasswordExceptionパスワードの条件を満たしていません…
CodeMismatchException確認コードが違います
ExpiredCodeException確認コードの有効期限が切れています。コードを再送してください

frontend/src/stores/authStore.js

signUp / confirmSignUp / resendCode を追加しました。通信中は isSigningUp を true にしてボタンを押せなくし、失敗したら errorMessage に文言を入れます。

frontend/src/constants/authValidation.js（新規）

パスワードの最小文字数（8）、条件の説明文、確認コードの桁数（6）をまとめた定数です。ユーザー登録とパスワード再設定の両方で使います。

frontend/src/assets/styles/global.css / LoginForm.vue

ログイン画面にあった入力欄のスタイルを auth-form / auth-field / auth-error などの共通クラスとして global.css に移しました。ログイン・登録・再設定の画面で同じ見た目を使い回せます。

iac/lib/michishiru-stack.ts — ユーザープール

const userPool = new cognito.UserPool(this, 'UserPool', {
  userPoolName: `michishiru-users-${stage}`,
  selfSignUpEnabled: true,          // 利用者が自分で登録できる
  signInAliases: { username: true }, // ユーザー名でサインイン
  signInCaseSensitive: false,        // 大文字小文字の違いで別人にならない
  standardAttributes: { email: { required: true, mutable: true } },
  autoVerify: { email: true },       // メールの確認コードで有効化
  ...
  deletionProtection: isProd,
  removalPolicy: isProd ? cdk.RemovalPolicy.RETAIN : cdk.RemovalPolicy.DESTROY
});
  • 環境ごとに別のプール（michishiru-users-dev / michishiru-users-prod）を作ります。
  • パスワードは8文字以上で、大文字・小文字・数字・記号が必須です。
  • 本番は誤って消えないよう保護し（RETAIN）、開発は作り直せるようにしています（DESTROY）。
  • アプリクライアント（michishiru-web-<環境>）はシークレットを持たせません。ブラウザに置く値は誰でも見られるので、SPA ではシークレットが使えないためです。
  • preventUserExistenceErrors: true で、ログイン失敗時に「そのユーザーはいない」と分からないようにしています。
  • ID は CfnOutput（UserPoolId / UserPoolClientId）として出力され、デプロイ時に受け取れます。

tools/exportCognitoOutputs.js（新規）

iac/cdk-outputs.json から Michishiru-<stage> スタックの出力を読み、VITE_COGNITO_USER_POOL_ID / VITE_COGNITO_USER_POOL_CLIENT_ID として GITHUB_ENV（後のステップに環境変数を引き継ぐための GitHub Actions の仕組み）に書き込みます。出力が見つからないときはエラーで止めます。

VITE_ で始まる値は、ビルドのときにプログラムへ埋め込まれます。実行時には読まれないので、ビルドより前に渡しておく必要があります。なお、ユーザープールID とクライアントID は秘密の値ではありません（constants/authConfig.js のコメント参照）。

.github/workflows/deploy.yml

  • デプロイ先を決める setup ジョブを分けました。GitHub の Environment（環境ごとのデプロイ履歴）はジョブの開始時に決まるため、先に別のジョブで決めておく必要があるからです。
  • 以前の「Variables に ID が登録されているか確認する」ステップを削除し、上の「2回デプロイ」の流れに変えました。

⚠️ 注意ポイント

構築手順書の一部が古くなった
docs/Cognitoログイン画面_構築手順書.html の「コンソールでユーザープールを作る」「GitHub の Variables に ID を登録する」手順は、今は不要です。プールは CDK が作り、ID はデプロイの出力から自動で渡されます。また、michishiru-stack.ts の CfnOutput の説明文にも「GitHub の Environment 変数に設定する」と古い記述が残っています。
パスワードの条件は2か所
画面の説明（constants/authValidation.js）と実際のルール（michishiru-stack.ts の passwordPolicy）は別々に書かれています。変えるときは両方直してください。
ユーザープールの論理ID（UserPool）を変えない
CDK の論理IDを変えると、プールが作り直されて登録済みのユーザーが全員消えます（prod は RETAIN なので古いプールは残りますが、アプリからは新しい空のプールが使われます）。
確認メールは Cognito の既定の送信元から届く
UserPoolEmail.withCognito() を使っているため、送信元は AWS のアドレスで、1日に送れる数にも上限があります。迷惑メールフォルダも確認してください。独自ドメインから送るには SES の設定が必要です。

✅ 動作確認方法

  1. ローカルでは frontend/.env.local に VITE_COGNITO_USER_POOL_ID と VITE_COGNITO_USER_POOL_CLIENT_ID を書きます（dev 環境の値を使う。*.local は Git の管理外です）。
  2. リポジトリのルートで npm run dev を実行します。
  3. ログイン画面から「ユーザー登録」を開き、ユーザー名・メールアドレス・パスワードを入れて登録します。
  4. メールに届いた6桁のコードを入れ、ログイン画面に「ユーザー登録が完了しました」と出ることを確認します。
  5. 登録した内容でログインできることを確認します。
  6. 同じユーザー名でもう一度登録し「このユーザー名は既に使われています」と出ることも確認します。
  7. フロントのチェック: frontend/ で npm run lint と npm run build（フロントの自動テストは未導入）。
  8. IaC のチェック: iac/ で npm run build、npm test（ユーザープールとアプリクライアントのテストが追加されています）、npx cdk synth。
