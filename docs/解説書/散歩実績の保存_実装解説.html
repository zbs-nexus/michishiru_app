散歩実績の保存 - 実装解説

🗓 対象期間: 2026-10-14 〜 2026-10-21
📅 マージ日: 2026-10-14（本体）, 2026-10-21（保存のタイミングの変更）
🌿 対象ブランチ: feature/NZ-176, feature/NZ-236
🔖 対象マージ: dc87c1c（実績の保存API・退避と再送。同じマージの「計測の信頼性」の部分は 散歩実績の計測 で扱う）, c20633a（保存を結果画面から案内画面の終了処理へ移動）

🧩 先に知っておきたいこと

実績はまず画面の中で計測される
歩いた距離・巡ったスポット数・所要時間は、案内中に walkStore へ積み上げられます。 積み上げ方は 散歩実績の計測 を参照してください。この解説書は、その値をサーバーへ残す部分です。
Lambda のレイヤー責務（handler / service / repository）
handler はリクエストの受付と返却、service は業務の判断、repository は DynamoDB への読み書きだけを担います。 詳しくは ルート作成API の解説を参照してください。
冪等（べきとう）
「同じ要求を何回送っても、結果が1回送ったときと同じになる」性質です。通信が不安定だと同じ実績を送り直すことがあるため、 散歩ごとのID（walkId）で「もう保存済みか」を見分け、累計が二重に増えないようにしています。
localStorage
ブラウザが端末内に持つ小さな保存領域です。画面を閉じても残りますが、ブラウザのデータ削除や別ブラウザへの乗り換えで消えます。 保存に失敗した実績の一時的な退避先として使っています。
Cognito の sub
ログインした利用者ごとに Cognito が発行する変わらないIDです。API Gateway のオーソライザーが検証したトークンから取り出すので、 利用者が他人の ID を名乗ることはできません（APIの認可 を参照）。

📖 この機能について

散歩を終えたとき、その回の実績（総距離・スポット数・所要時間・計測状態など）を DynamoDB の WalkResult-<環境> テーブルへ保存し、同時に利用者ごとの累計（散歩の回数・累計距離・累計スポット数・累計時間）へ足す機能です。

通信できずに保存に失敗した場合は、端末の localStorage へ退避し、次にログインしたときや通信が戻ったときに自動で送り直します。

🎯 なぜこの機能が必要？

これまでの実績は walkStore にしか無く、画面を再読み込みすると消えていました。 1回ごとの散歩結果（US-8）を見せるだけならそれで足りますが、「これまでに何km歩いたか」を使う機能 （マスコットのレベルアップ）には、利用者ごとに積み上がった記録が必要です。

前提条件書の「ユーザー単位のデータ管理」は「未定（キーに sub を含めるか）」のままですが、 この実績テーブルは sub をキーにして利用者ごとに分けています。

🔄 処理の流れ

Step 1: 終了の確定（案内画面）
終了確認で「終了する」を押すと、RouteNavigationView の handleConfirmEnd が 「記録中…」を全画面に出し、walkStore.endWalk() で終了時刻を確定します。
Step 2: 送る内容の組み立て（useWalkResultSave）
saveCurrentWalkResult() がストアの値を API の形に変換します（時刻はISO形式、距離は整数のメートル、ジャンルは英語ID）。 このとき walkId を crypto.randomUUID() で1回だけ決めます。
Step 3: 送信（walkResultService）
POST /api/v1/walk-results を idToken 付きで送ります。失敗したときは 「時間を置けば通る（通信不能・429・5xx）」と「何度送っても通らない（その他の4xx）」に分けて例外を投げます。
Step 4: サーバー側の保存（createWalkResult Lambda）
handler がトークンの sub を利用者IDとし、validator で値を検証します。 service は計測状態を見て「累計にも足す」か「記録だけ残す」かを選び、repository が DynamoDB へ書き込みます。
Step 5: 失敗時の退避
「時間を置けば通る」失敗だけを localStorage へ退避し、「通信が回復したときに自動で保存します」とトーストで知らせます。 通らない失敗は退避せず「実績を保存できませんでした」と出します。
Step 6: 結果画面へ
保存の後にマスコットの実績を取り直してレベルアップを判定し（マスコットのレベルアップ）、 結果画面へ進みます。保存に失敗しても結果画面には進みます。
Step 7: 退避した実績の再送（App.vue）
ログイン済みになったとき（再読み込み直後を含む）と、ブラウザが online に戻ったときに flushPendingWalkResults() が退避分を順に送り直します。

💻 コードの解説

テーブルの形（WalkResult-<環境>）

1つのテーブルに2種類のアイテムを入れています（単一テーブル設計）。

アイテムpksk主な属性
1回分の実績USER#<sub>WALK#<endedAt>#<walkId>totalDistanceM / spotCount / elapsedMinutes / startedAt / endedAt / measurementStatus / routeTitle / genreId
利用者の累計USER#<sub>TOTALwalkCount / cumulativeDistanceM / cumulativeSpotCount / cumulativeMinutes / updatedAt

sk を終了時刻から始めているので、将来「履歴を新しい順に出す」ときも pk で絞って WALK# の前方一致で引けます。そのため GSI は作っていません。

backend/functions/createWalkResult/service.js

const { isStored } =
  item.measurementStatus === MEASUREMENT_STATUS_UNAVAILABLE
    ? await repositories.createWalkResultWithoutTotals(item)
    : await repositories.createWalkResultWithTotals(item);

if (!isStored) {
  return { walkId: item.walkId, isAlreadySaved: true };
}
  • 一度も測位できなかった散歩（unavailable）は、距離もスポット数も実際の行動を表していないので、記録だけ残して累計には足しません
  • 途中まで測れた散歩（partial）は、測れた分に意味があるので累計に足します
  • 同じ walkId が保存済みなら isAlreadySaved: true の成功として返します。退避分の再送で必ず通る道なので、エラーにすると利用者に無意味な失敗が見えてしまいます

backend/functions/createWalkResult/repository.js（累計と同時に保存）

new TransactWriteCommand({
  TransactItems: [
    { Put: { ..., Item: toWalkResultItem(walkResult),
             ConditionExpression: 'attribute_not_exists(pk)' } },
    { Update: { ..., Key: { pk: ..., sk: TOTAL_SORT_KEY },
                UpdateExpression:
                  'ADD walkCount :one, cumulativeDistanceM :distanceM, ...' } }
  ]
})
  • トランザクション（2つの書き込みを「両方成功」か「両方なし」にまとめる仕組み）で、1回分の保存と累計の加算を同時に行います
  • 1回分の Put は「同じキーがまだ無いこと」が条件です。再送でキーが重なるとトランザクション全体が止まるので、累計も二重に増えません
  • 累計は ADD でサーバー側に足させるので、累計アイテムを先に作っておく必要がありません（初回の散歩で自動的にできます）
  • テーブル名の環境変数が未設定なら保存せずエラーにします。成功を装うと退避も働かず、実績が失われるためです

validator.js の主な検証

項目上限など
walkIdUUID v4 の形式
totalDistanceM200,000m（200km）まで。巨大な誤値が累計に入るのを防ぐ
spotCount50 まで
elapsedMinutes1,440分（24時間）まで。案内画面の閉じ忘れなどの異常値を弾く
measurementStatuscomplete / partial / unavailable のいずれか（フロントの walkStore と同じ3値）
routeTitle120文字を超えたらエラーにせず切り詰める

frontend/src/composables/useWalkResultSave.js

関数入力 → 出力ポイント
saveCurrentWalkResult()なし → 保存できたか（boolean）案内を経ていない（startedAt が無い）なら送らずに成功扱い。失敗時は種類に応じて退避するか決め、saveErrorMessage に文言を入れる
flushPendingWalkResults()なし → なし退避した本人（ownerUsername）がログインしているときだけ送る。通らない内容は捨て、通信がまだ戻っていなければ途中で切り上げる
// 退避した本人がサインインしているときだけ送る。別のユーザーの分は
// 消さずに残し、その人がサインインしたときに送られるようにする
if (pendingResult.ownerUsername !== authStore.username) {
  continue;
}

保存APIは「送ってきたトークンの持ち主」の実績として保存します。localStorage はサインアウトしても消えないので、 持ち主を確かめずに送ると、同じ端末で別の人がログインしたときにその人の累計へ足されてしまいます。

再送中の旗 isFlushing は ref ではなくファイル直下の普通の変数です。 「ログイン」と「通信の復帰」がほぼ同時に起きても、composable を呼んだ場所をまたいで二重送信を防ぐためです。

frontend/src/utils/pendingWalkResults.js

localStorage のキー michishiru.pendingWalkResults に、退避分を最大20件まで配列で持ちます（超えたら古いものから捨てる）。 読み書きに失敗しても例外を投げません。退避はできたらする（best effort）ものなので、ここで落ちると「保存に失敗した」と知らせる本来の処理まで止まるためです。

⚠️ 注意ポイント

利用者IDはリクエストから読まない
handler は event.requestContext.authorizer.claims.sub だけを使います。ボディに userId を入れても無視されます。 新しく利用者ごとのAPIを作るときも同じ方針にしてください。
計測状態の3値はフロントとバックエンドの両方にある
backend/functions/createWalkResult/constants.js の MEASUREMENT_STATUSES と、 frontend/src/stores/walkStore.js の MEASUREMENT_STATUS は同じ値でなければなりません。片方だけ増やすと保存が 400 で落ちます。
useWalkResultSave.js 冒頭のコメントが古い
ファイル冒頭に「保存の起点は結果画面（WalkResultView.vue）」とありますが、c20633a 以降の保存の起点は 案内画面の終了処理（RouteNavigationView.vue の handleConfirmEnd）です。結果画面は保存しません。
チュートリアル中は保存しない
チュートリアルの終了処理は保存・取り直しを飛ばして結果画面へ進みます（チュートリアル）。

✅ 動作確認方法

  1. ローカルで保存まで確かめるには、AWS の認証情報と環境変数 WALK_RESULT_TABLE_NAME（例: WalkResult-dev）が必要です。未設定だと API は 503 を返し、フロントは退避へ積みます（その動きも確認対象）
  2. npm run dev で起動し、ルートを作って案内を開始し、少し歩いて（または短時間で）終了する
  3. 「記録中…」の後に結果画面が出ること、DynamoDB の WalkResult-dev に1回分のアイテムと TOTAL のアイテムがあることを確かめる
  4. ブラウザの開発者ツールでオフラインにして終了し、「通信が回復したときに自動で保存します」と出ること、localStorage に michishiru.pendingWalkResults が積まれることを確かめる。オンラインに戻すと送られて消えることも確かめる
  5. テスト: backend で npm test（functions/createWalkResult/__tests__/ の repository / service / validator）、 frontend で npm test（useWalkResultSave / walkResultService / pendingWalkResults / App / RouteNavigationView / WalkResultView のテスト）、iac で npm test
