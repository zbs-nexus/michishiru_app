👤 対象読者: 開発初心者向け

📖 この機能について

この作業は、チーム全員が同じルールでコードを書けるようにするための「開発規約」を整備したものです。

プログラミングでは、同じことを実現するにもいろいろな書き方があります。 例えば、変数名を「routeName」にするか「route_name」にするか、ファイル名を「RouteService.js」にするか「route-service.js」にするか、などです。

チームで開発する場合、各自が好き勝手に書くと：

  • コードが読みにくくなる
  • ファイルを探すのに時間がかかる
  • 間違いに気づきにくくなる

そこで、「うちのプロジェクトではこう書こう」というルールを決めて、ドキュメント化したのがこのNZ-58の作業です。

🎯 なぜこの規約が必要？

1. コードの一貫性

同じ概念には同じ名前を使うと、チーム全員が同じ理解で開発できます。 例えば、「立ち寄り先」を指す言葉が「spot」「waypoint」「place」「location」とバラバラだと、どれが正しいか分からなくなります。

2. レビューの効率化

規約があると、レビュー時に「この書き方は規約と違う」と指摘しやすくなります。 規約がないと、レビュアーごとに基準が違って混乱します。

3. 新しいメンバーの教育

新しくプロジェクトに参加した人が、「このプロジェクトではどう書けばいいの？」と迷ったとき、規約ドキュメントを見れば分かります。

🔍 主要な規約の詳細解説

1. 命名規則（naming-conventions.md）

なぜ命名規則が大切？

プログラミングでは、「名前を付ける」ことが非常に多いです（変数、関数、ファイル、クラスなど）。 名前が統一されていないと、コードを読むときに毎回「これは何だろう？」と考える必要があります。

基本的な書き方

対象 規則 例
変数・関数 camelCase（最初は小文字、以降は大文字で単語を区切る） routeName, getUserById
定数 UPPER_SNAKE_CASE（全て大文字、アンダースコアで区切る） MAX_SPOTS, API_BASE_URL
クラス・コンポーネント PascalCase（最初も大文字） RouteService, RouteMap
ファイル名 種類によって使い分け 後述

Boolean（真偽値）の命名

「はい/いいえ」で答えられる変数は、is/has/can/shouldで始めると分かりやすいです。

// 良い例 isLoading // 読み込み中？ hasRoute // ルートを持っている？ canEdit // 編集できる？ shouldRefresh // 再読み込みすべき？ // 悪い例 loading // 何をしているのか不明瞭 route // 有無なのかデータ自体なのか分からない

2. 用語辞書（naming-glossary.md）

なぜ用語辞書が必要？

同じ概念を指す言葉が複数あると、コードが混乱します。 例えば、「立ち寄り先」を指すのに「spot」「waypoint」「place」が混在すると、それぞれが別のものなのか同じものなのか分からなくなります。

特に重要な2組の用語

用語 意味 具体例
spot ユーザーが立ち寄る場所 公園、カフェ、神社（1ルートに2〜5個）
waypoint 経路を描くための座標の点 交差点、道の折れ点（1ルートに数十個）

混同すると何が起きる？

「巡ったスポット数」を表示する機能で、waypointを数えてしまうと：

// 間違い スポット数: 37個 ← 道の折れ点まで数えている // 正しい スポット数: 4個 ← 実際に立ち寄った場所だけ

3. レイヤー構成（back-layer-architecture.md）

なぜレイヤーに分けるの？

1つのファイルにすべての処理を書くと、コードが長くなりすぎて読めなくなります。 また、1箇所を変更したときに、他の部分に影響が出やすくなります。

レイヤーに分けると、「この層はこれだけをする」と決まるので、役割が明確になります。

3層の役割分担

Handler (入口) ↓ リクエストを受け取って、レスポンスを返すだけ Service (脳) ↓ ビジネスロジック（どんなルートを作るか）を決める Repository (手足) ↓ データベースや外部サービスにアクセスする
レイヤー やって良いこと やってはいけないこと
Handler
  • JSONを解析する
  • バリデーション（入力チェック）を呼ぶ
  • レスポンスを整形する
  • ビジネスロジックを書く
  • DBに直接アクセスする
Service
  • データを加工する
  • 条件分岐を書く
  • 複数のRepositoryを組み合わせる
  • HTTPレスポンスを作る
  • DBに直接アクセスする
Repository
  • DBクエリを実行する
  • 外部APIを呼ぶ
  • データの形を変換する
  • ビジネスロジックを書く
  • バリデーションする

4. Gitワークフロー（git-workflow.md）

なぜブランチ戦略が必要？

チームで同時に開発すると、それぞれが異なる機能を作ります。 全員が同じブランチで作業すると、他の人の変更と衝突（コンフリクト）が頻繁に起きます。

ブランチを分けて、完成したものから順にマージしていくと、衝突を減らせます。

ブランチの種類

ブランチ 役割 直接プッシュ
main 本番環境（ユーザーが使うもの） 禁止（PRのみ）
develop 開発中の統合（みんなの変更を集める場所） 禁止（PRのみ）
feature/NZ-X-xxx 機能開発（レビュー対象） 禁止（PRのみ）
test/NZ-X 作業用（試行錯誤する場所） 可

コミットメッセージの書き方

コミットメッセージには、「何をしたか」だけでなく「種別」も入れると、履歴が見やすくなります。

// 良い例 feat(NZ-106): ルート作成APIを追加 fix(NZ-58): 命名規則のtypoを修正 docs: READMEを更新 // 悪い例（種別がない） ルート作成APIを追加 ← 何の変更か分からない 修正 ← 何を修正したのか不明
種別 用途
feat 新機能
fix バグ修正
docs ドキュメント・規約
refactor リファクタリング（動作を変えずにコードを整理）
test テスト
ci CI/CD の設定変更

⚠️ 規約を守らないとどうなる？

1. レビューで差し戻される

規約に違反しているコードは、レビューで指摘されて修正が必要になります。 最初から規約に沿って書く方が、結果的に早く終わります。

2. バグが見つけにくくなる

例えば、「spot」と「waypoint」を混同していると、「スポット数が37個」という明らかにおかしい値が表示されても、 「仕様通り」に見えてしまい、バグに気づけません。

3. 他のメンバーが理解できない

自分だけのルールで書いたコードは、他のメンバーが読むときに時間がかかります。 チーム開発では、「自分以外の人が読めるコード」を書くことが大切です。

✅ 規約の使い方

1. 新しい機能を作るとき

  1. .kiro/steering/ の該当ファイルを開く
  2. 命名規則を確認してから、変数名やファイル名を決める
  3. 用語辞書を確認して、正しい用語を使う
  4. レイヤー構成ルールに従って、ファイルを配置する

2. レビューするとき

  1. 規約に違反していないかチェックする
  2. 違反があれば、該当する規約ファイルのセクションを示して指摘する
  3. 「例外一覧」に載っているものは指摘しない

3. 迷ったとき

  1. まず規約ファイルを検索する
  2. 見つからなければ、チームで相談する
  3. 決まったら、規約ファイルに追記する

🚀 次に学ぶこと

規約を身につけるために

  • 既存のコードを読む
    すでに規約に沿って書かれたコードを読むと、「こう書けばいいんだ」と実例で理解できます。
  • レビューを積極的に受ける
    自分が書いたコードをレビューしてもらうと、どこが規約と違うか気づけます。
  • レビューをする
    他の人のコードをレビューすると、「自分だったらこう書く」という視点が身につきます。

📚 まとめ

NZ-58で整備した開発規約は、チーム全員が同じルールでコードを書くための「共通言語」です。

最初は覚えることが多くて大変かもしれませんが、慣れてくると：

  • 「この名前はこう書く」と迷わなくなる
  • 「このファイルはここに置く」と即座に判断できる
  • 他の人のコードもすぐに理解できる

規約は「縛り」ではなく、チームで効率よく開発するための「道具」です。 ぜひ活用してください！
