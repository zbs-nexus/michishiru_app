散歩の案内画面で地図を長押しすると、その場所に赤いピンが立ち、画面下部に口コミ投稿フォームが開きます。 ロケーション名・ジャンル・5段階評価・写真（最大4枚）を入力して投稿すると、場所と評価が保存され、 自分が投稿した場所はオレンジのピンで地図に表示されます。 この解説書では、フロントエンド・バックエンド・インフラの3方向から、その仕組みを順に追っていきます。

🧩 先に知っておきたいこと

Composable（コンポーザブル）とは
Vue で「画面の見た目を持たない、状態つきの処理のかたまり」を関数として切り出したものです。 ファイル名は use〇〇.js で始まり、呼ぶと「状態」と「その状態を変える関数」をまとめて返します。 この機能では useReviewPosting.js（投稿の進行状況）、useMyReviews.js（自分の口コミ一覧）、 useMapLongPress.js（長押しの検出）の3つが登場します。
Lambda の4ファイル構成（handler / service / repository / validator）
バックエンドの1つの API は、役割ごとに4つのファイルへ分かれています。 handler.js がリクエストの受け取りとレスポンスの返却、validator.js が入力の形式チェック、 service.js が「どう処理するか」の判断（業務ロジック）、repository.js が DynamoDB や S3 への読み書きです。 呼び出しは handler → service → repository の一方向だけで、逆向きには呼びません。
DynamoDB は「条件で絞り込む検索」が得意ではない
DynamoDB はキー（住所のようなもの）を指定して読み書きするデータベースです。 「現在地から40m以内の場所」のような条件で全件を探す操作は、遅くて高くつきます。 そのため、あらかじめ「探しやすいキー」を一緒に保存しておき、そのキーで引くのが基本になります。 この機能では座標を格子状のマス目に変換した geoCell がそのキーです。
GSI（グローバルセカンダリインデックス）とは
DynamoDB のテーブルに対して「別のキーでも引けるようにする索引」です。本の巻末にある索引と同じ役目です。 この機能では GSI-GeoCell（マス目から場所を引く）と GSI-UserReview（ユーザーから口コミを引く）の2つを作っています。
署名付きURL（presigned URL）とは
「このURLに、これから5分間だけ、この1ファイルを置いてよい」という限定的な許可が埋め込まれたURLです。 S3（AWSのファイル置き場）への書き込み権限をブラウザへ渡さずに、ブラウザから直接アップロードさせるために使います。 写真の表示側も同じ仕組み（1時間だけ読める GET 用のURL）を使っています。
ユーザーの識別は Cognito の sub で行う
ログイン基盤（Amazon Cognito）が利用者ごとに発行する、変わらないIDが sub です。 ユーザー名は後から変更されうるため、データの持ち主を表すのには sub を使います。 API Gateway がトークンを検証したうえで Lambda へ渡してくれるので、Lambda 側でトークンを検証する処理は書きません。

📖 この機能について

口コミ投稿は、散歩中に見つけた「よかった場所」をその場で記録し、評価を共有する機能です。 ルート案内の画面（RouteNavigationView.vue）の上に重ねて動くため、散歩を中断せずに投稿できます。

操作としては次の3つができます。

  • 新しい場所に口コミを付ける（初回投稿）: ロケーション名・ジャンル・評価・写真を登録する
  • すでに誰かが登録した場所に評価を付ける（評価のみ）: 名前とジャンルは固定表示され、星だけを付ける
  • 自分が作った場所を編集する（本人編集）: 名前・ジャンル・写真・評価を書き換える

この3つの切り替えは、長押しした座標に「すでに場所があるか」と「その場所を作ったのが自分か」の2点で自動的に決まります。 利用者がモードを選ぶ操作はありません。

🎯 なぜこの機能が必要？

ミチシルは条件を入力すると AI が散歩ルートを自動生成します。ただしルートは毎回その場で作られるため、 「この公園のベンチがよかった」「この路地は静かだった」といった利用者自身が見つけた価値は、散歩が終わると何も残りません。 口コミ投稿は、その情報をアプリの中に残すための機能です。

前提条件書のユーザーストーリー（US-1〜US-8）には口コミに該当するものはありません。 US-6「案内画面表示」の画面に対して後から追加された機能であり、 受け入れ条件は前提条件書ではなく、この解説書と実装（およびブランチ上の各コミット）が実質的な仕様になっています。 そのため、辞書（naming-glossary.md）側には口コミの節が追加され、用語が先に固められました。

次に、利用者が投稿するまでの流れを順に追います。

Step 1: 地図を長押しする（useMapLongPress.js）
MapLibre（地図ライブラリ）には「長押し」というイベントがありません。そこで、押し始めてから 500ms の間、 指やカーソルが 10px 以上動かず、離されもしなかった場合を長押しとみなします。 地図をドラッグしたりズームしたりしたときは「地図を操作したい」のであって長押しではないので、判定を取り消します。
Step 2: フォームを開き、ピンを立てる（RouteNavigationView.vue）
先にフォームを表示してから、nextTick()（描画が終わるのを待つ処理）のあとにフォームの高さを測ります。 画面の上には「次の目的地」のバナー、下にはフォームがあるため、地図の中央にピンを置くと隠れてしまいます。 そこで上下に挟まれた「見えている範囲」の中央にピンが来るよう、地図中央からのずれ（pinOffsetY）を計算してから地図を動かします。
Step 3: その座標に既存の場所があるか問い合わせる（GET /api/v1/spots）
半径40m以内に登録済みの場所があれば、その情報（名前・ジャンル・平均評価・写真）と、 自分がすでに付けている評価、そして自分がその場所の作成者か（isOwner）が返ってきます。 なければ { exists: false } が返り、初回投稿として扱われます。 フォームはこの結果を見て、3つのモード（新規 / 本人編集 / 評価のみ）を切り替えます。
Step 4: 入力して投稿ボタンを押す（ReviewPostForm.vue）
不足している必須項目があれば、送信せずにフォーム内へ「ロケーション名・5段階評価を入力してください」のような メッセージを出します。評価のみモードでは、名前・ジャンル・写真は送りません（null と空配列を送ります）。
Step 5: 写真があれば先に S3 へ直接アップロードする（POST /api/v1/review-photo-uploads → S3 へ PUT）
写真の枚数ぶんの署名付きURLとオブジェクトキーをまとめて発行してもらい、ブラウザから S3 へ直接 PUT します。 成功したら、受け取ったキーの一覧だけを次の投稿リクエストに含めます。画像データ自体は API を通りません。
Step 6: 口コミを投稿する（POST /api/v1/reviews）
サーバー側はもう一度その座標の近くに場所があるかを調べ、次の3つに振り分けます。
  • 場所がない → 新しい場所を作り、同時に自分の口コミを1件作る（初回投稿）
  • 場所があり、作成者が自分 → 名前・ジャンル・写真を上書きし、評価も更新する（本人編集）
  • 場所があり、作成者が他人 → 自分の評価だけを追加・更新する（評価のみ）
フロントから送られた情報を信じず、サーバー側で再判定するのがポイントです。
Step 7: 結果を画面へ反映する（RouteNavigationView.vue）
成功したらフォームを閉じ、画面上部に「口コミを投稿しました」というトースト（数秒で消える通知）を出します。 そのあと loadMyReviews() を呼び直して、投稿した場所をオレンジのピンとして地図へ反映します。 失敗した場合はフォームを閉じずにエラーを出すので、入力をやり直せます。

APIの一覧

この機能で追加された API は4本です（10/14 に5本目の GET /api/v1/review-spots が追加。下の「🆕」の節を参照）。いずれもログインが必須です。

メソッド・パス Lambda 役割
GET /api/v1/spots?lng=&lat= getSpot 長押しした座標に既存の場所があるかを解決する。写真の表示URL・自分の評価・isOwner も返す
POST /api/v1/reviews createReview 口コミの投稿・本人編集。場所の評価の集計も同時に更新する
POST /api/v1/review-photo-uploads createPhotoUploadUrls 写真アップロード用の署名付きURL（最大4件）を発行する
GET /api/v1/my-reviews getUserReviews 自分が投稿した口コミの一覧を、場所の座標・名前つきで返す

💻 コードの解説

backend/shared/utils/geo.js

「半径40m以内なら同じ場所」という判定の土台です。距離の計算（ハバーサイン公式）と、 座標をマス目のキーへ変換する処理が入っています。 

/**
 * 同じ場所とみなす半径（メートル）。
 * 案内画面の通過判定（ARRIVAL_THRESHOLD_M）と同じ40mに合わせている。
 */
export const SAME_PLACE_RADIUS_M = 40;

/**
 * 候補絞り込み用グリッドの一辺（メートル）。
 * 半径と同じ40mにすると、対象セルとその周囲8セル（3×3）の問い合わせで
 * 半径40m以内のスポットを必ず候補に含められる。
 */
const GEO_CELL_SIZE_M = SAME_PLACE_RADIUS_M;

なぜマス目に分けるのか： DynamoDB には「40m以内を探す」という問い合わせがありません。 そこで地球全体を一辺40mのマス目で区切り、場所を保存するときに「どのマスに入るか」を geoCell （例: "99123:388540"）として一緒に保存しておきます。 探すときは自分のマスと周囲8マスの計9マスだけを引けば済みます。

なぜ9マスなのか： マスの一辺が半径と同じ40mなので、自分のマスの端にいる場合でも、 40m先はせいぜい隣のマスまでしか届きません。斜め方向も含めて3×3の9マスを見れば、取りこぼしがなくなります。 1マスだけでは、マスの境界ぎわにある場所を見落とします。 

export const toNeighborGeoCells = (position) => {
  const { latIndex, lngIndex } = toCellIndices(position);
  const cells = [];

  for (let deltaLat = -1; deltaLat <= 1; deltaLat += 1) {
    for (let deltaLng = -1; deltaLng <= 1; deltaLng += 1) {
      cells.push(`${latIndex + deltaLat}:${lngIndex + deltaLng}`);
    }
  }

  return cells;
};

9マスで集めた候補は「だいたい近い」だけなので、最後に findNearestWithinRadiusM() で実距離を測り、 40m以内で最も近いものを1つ選びます。マス目は候補をしぼるため、距離は正確に判定するためという二段構えです。

backend/functions/createReview/service.js

投稿の振り分けを決めている中心部分です。handler から渡された値だけを見て、HTTP のことは知りません。

export const createReview = async (input, repository = reviewRepository, { retried = false } = {}) => {
  if (!input.userId) {
    throw createUnauthorizedError('口コミの投稿にはログインが必要です');
  }

  const candidates = await repository.findNearbySpots(input.position);
  const existingSpot = findNearestWithinRadiusM(
    input.position, candidates, SAME_PLACE_RADIUS_M
  );

  if (existingSpot !== null) {
    // 作成者本人は名前・ジャンル・写真も編集でき、他ユーザーは評価のみ
    if (existingSpot.createdByUserId === input.userId) {
      return editOwnedSpot({ spot: existingSpot, input }, repository);
    }

    return postSubsequentReview(
      { spot: existingSpot, rating: input.rating, userId: input.userId },
      repository
    );
  }

  try {
    return await postFirstReview(input, repository);
  } catch (error) {
    // 別のユーザーが同じ場所を先に作成した競合。1度だけ2回目以降として再試行する
    if (error.code === ERROR_CODES.REVIEW_CONFLICT && !retried) {
      return createReview(input, repository, { retried: true });
    }

    throw error;
  }
};

最後の catch が何をしているか： 「場所があるか調べる」と「場所を作る」の間に、 別の人が同じ場所を先に作ってしまうことがあります（ごく短い時間ですが起こりえます）。 その場合は DynamoDB 側の条件付き書き込みが失敗し、競合エラーになります。 そこで1回だけ処理全体をやり直します。やり直したときには場所が見つかるので、 「2回目以降（評価のみ）」の経路に自然に流れます。retried フラグがあるのは、 やり直しが無限に続かないようにするためです。

backend/functions/createReview/repository.js

DynamoDB と S3 への読み書きを担当します。評価の集計を壊さないため、書き込みはトランザクション（複数の書き込みをまとめて、 全部成功か全部失敗のどちらかにする仕組み）で行います。 

export const addReview = async ({ spotId, userId, rating, now }) => {
  await sendTransaction(
    new TransactWriteCommand({
      TransactItems: [
        {
          Put: { /* 自分の口コミ行（sk = REVIEW#<userId>）を作る */
            ConditionExpression: 'attribute_not_exists(sk)'
          }
        },
        {
          Update: { /* 場所メタ行（sk = SPOT）の集計へ加算する */
            UpdateExpression:
              'ADD ratingSum :rating, ratingCount :one SET updatedAt = :now',
            ConditionExpression: 'attribute_exists(spotId)',
            ExpressionAttributeValues: { ':rating': rating, ':one': 1, ':now': now }
          }
        }
      ]
    })
  );
};

テーブルの形： 1つのテーブル（Review-<環境>）に2種類の行が入っています。 パーティションキーはどちらも spotId で、ソートキーで区別します。

ソートキー（sk） 何の行か 主な属性
SPOT 場所そのものの情報（場所メタ） spotName, genreId, position, geoCell, ratingSum, ratingCount, photoKeys, createdByUserId
REVIEW#<userId> 1人のユーザーがその場所に付けた口コミ userId, rating, createdAt

ConditionExpression は「この条件を満たすときだけ書く」という指定です。 attribute_not_exists(sk) なら「まだ自分の口コミ行がないときだけ作る」という意味で、 同じ人が二重に投稿して件数が2つ増えるのを防ぎます。条件を満たさないと書き込みは失敗し、 repository が競合エラーへ変換して service に伝えます。

評価を書き換えるときは、合計（ratingSum）に差分だけを足します（updateReviewRating）。 星3から星5へ変えたなら +2 です。件数（ratingCount）は変わりません。

backend/functions/getSpot/service.js

長押しした座標に既存の場所があるかを返します。ここで isOwner が決まります。

// 写真は非公開バケットにあるため、表示用の署名付きURLを付けて返す
const photoUrls = await repository.createPhotoViewUrls(spot.photoKeys ?? []);

// 認証済みなら、呼び出し元が既にこの場所へ投稿しているかを合わせて返す
const userReview =
  userId === null ? null : await repository.getUserReview(spot.spotId, userId);

// 呼び出し元がこの場所の作成者か（本人なら名前・ジャンル・写真も編集できる）。
// 他ユーザーのIDは外へ出さないよう、createdByUserId は返却から除く
const { createdByUserId, ...publicSpot } = spot;
const isOwner = userId !== null && createdByUserId === userId;

return { exists: true, spot: { ...publicSpot, photoUrls }, isOwner, userReview };

注目したいのは最後の3行です。createdByUserId（作成者のID）を使って isOwner を計算した後、 分割代入でその項目をレスポンスから取り除いています。 フロントが必要なのは「自分が作成者かどうか」という真偽値だけで、他人のIDを知る必要はありません。 判定に使った材料をそのまま返さないのは、個人を特定できる値を外に出さないための配慮です。

frontend/src/composables/useReviewPosting.js

投稿の進行状況（解決中・投稿中・エラー）を持ち、写真のアップロードと投稿の順番を組み立てます。 API の呼び出しそのものは reviewService.js に任せ、ここでは状態の移り変わりだけを扱います。 

const post = async ({ photos = [], keptPhotoKeys = [], ...payload }) => {
  isPosting.value = true;
  errorMessage.value = null;

  try {
    let newPhotoKeys = [];

    if (photos.length > 0) {
      const uploads = await fetchPhotoUploadUrls(photos.length);
      await Promise.all(
        uploads.map((upload, index) => uploadPhoto(upload.uploadUrl, photos[index]))
      );
      newPhotoKeys = uploads.map((upload) => upload.key);
    }

    // 残す既存写真＋新規アップロードぶんが、最終的な写真キーになる
    const photoKeys = [...keptPhotoKeys, ...newPhotoKeys];

    return await postReview({ ...payload, photoKeys });
  } catch (error) {
    errorMessage.value = error.message;
    return null;
  } finally {
    isPosting.value = false;
  }
};

Promise.all は何をしているか： 複数の写真を1枚ずつ順番に待つのではなく、まとめて同時にアップロードします。 4枚あっても待ち時間は1枚ぶんに近くなります。

finally が必要な理由： 成功しても失敗しても isPosting を false に戻さないと、 投稿ボタンが押せないまま固まります。finally はどちらの場合も必ず通るので、 このような「後片付け」を書く場所になります。

frontend/src/services/reviewService.js

口コミ関連の API 通信をまとめたファイルです。認可の付け方と、S3 への直接 PUT の違いが見どころです。

export const resolveSpot = async ({ lng, lat }) => {
  const idToken = await fetchIdToken();
  const query = new URLSearchParams({ lng: String(lng), lat: String(lat) });

  const response = await fetch(`${API_BASE_PATH}/spots?${query.toString()}`, {
    headers: { Authorization: idToken }
  });

  await ensureUsableResponse(response);

  return response.json();
};

/**
 * 署名付きURLへ写真を直接アップロードする（S3へのPUT）。
 * S3への直PUTのため、Authorizationヘッダーは付けない（URL自体が署名を含む）。
 */
export const uploadPhoto = async (uploadUrl, file) => {
  const response = await fetch(uploadUrl, {
    method: 'PUT',
    headers: { 'Content-Type': file.type || 'application/octet-stream' },
    body: file
  });

  if (!response.ok) {
    throw new Error(`写真のアップロードに失敗しました（${response.status}）`);
  }
};

ミチシルの API はログイン必須なので、IDトークンを Authorization ヘッダーに載せます。 Bearer のような接頭辞は付けません（API Gateway がヘッダーの値をそのままトークンとして扱う設定のため）。 一方 S3 への PUT は、URL 自体に許可が埋め込まれているため Authorization を付けません。付けると署名の検証が通りません。

ensureUsableResponse() では、応答が成功かどうかだけでなくJSONかどうかも確認しています。 API をまだ繋いでいない環境では SPA の index.html（HTML）が 200 で返ってくるため、 そのまま解析しようとすると意味の分からないエラーになるからです。

iac/lib/michishiru-stack.ts

テーブル・バケット・Lambda・API の定義です。GSI の設計意図がコメントに書かれています。

// DynamoDB: 口コミ（場所メタ＋口コミ）を格納するテーブル（単一テーブル設計）
//   pk=spotId, sk='SPOT'（場所メタ）/ 'REVIEW#<userId>'（各ユーザーの口コミ）
const reviewTable = new dynamodb.TableV2(this, 'ReviewTable', {
  tableName: `Review-${stage}`,
  partitionKey: { name: 'spotId', type: dynamodb.AttributeType.STRING },
  sortKey: { name: 'sk', type: dynamodb.AttributeType.STRING },
  billing: dynamodb.Billing.onDemand(),
  removalPolicy: isProd ? cdk.RemovalPolicy.RETAIN : cdk.RemovalPolicy.DESTROY,
  globalSecondaryIndexes: [
    {
      // 近接する場所をグリッドのセルで引くための GSI（半径40mの候補絞り込み）。
      // 場所メタ行のみ geoCell を持つため、口コミ行は含まれない（疎なインデックス）
      indexName: 'GSI-GeoCell',
      partitionKey: { name: 'geoCell', type: dynamodb.AttributeType.STRING },
      sortKey: { name: 'spotId', type: dynamodb.AttributeType.STRING }
    },
    {
      // ユーザーが投稿した口コミを新しい順に引くための GSI。
      // 口コミ行のみ userId を持つため、場所メタ行は含まれない（疎なインデックス）
      indexName: 'GSI-UserReview',
      partitionKey: { name: 'userId', type: dynamodb.AttributeType.STRING },
      sortKey: { name: 'createdAt', type: dynamodb.AttributeType.STRING }
    }
  ]
});

「疎なインデックス」とは： DynamoDB の GSI には、キーに指定した属性を持っている行だけが入ります。 場所メタの行だけが geoCell を持つので、GSI-GeoCell を引くと場所だけが返り、口コミの行は混ざりません。 同じ理屈で、userId を持つのは口コミの行だけなので、GSI-UserReview には口コミだけが入ります。 この性質を利用して、1つのテーブルに入れた2種類のデータを、索引側で自然に分けています。

API 側は4本すべてに Cognito オーソライザー（cognitoAuthorized）を付けています。 認可は API Gateway が行うため、Lambda にトークンの検証処理はありません。 Lambda は event.requestContext.authorizer.claims.sub から利用者を読み取るだけです （backend/shared/utils/requestContext.js）。

⚠️ 注意ポイント

0. 紫のピンの件数には上限がある（10/14 追加）

getReviewSpots はページングせず、新しい順に DEFAULT_QUERY_LIMIT 件までしか返しません。投稿が増えると古い場所のピンは出なくなります。 また GSI-SpotList は全場所が1つのパーティション（sk = 'SPOT'）に集まる構成で、件数上限つきの読み取りのみのため現在の規模では許容している、とコメントにあります。

1. 平均評価（ratingAverage）は保存していない

DynamoDB に保存しているのは合計（ratingSum）と件数（ratingCount）だけで、 平均は読み出すときに計算しています。 

ratingAverage: ratingCount === 0 ? 0 : ratingSum / ratingCount

平均も一緒に保存すると、合計・件数・平均の3つを常に同時に正しく更新しなければならず、 どこかで更新が漏れると「平均が実態と合わない」という、気付きにくいずれが起きます。 計算で求めれば、その食い違いが起こる余地そのものがなくなります。

2. 写真は「場所ごと」に最大4枚で、設定できるのは初回投稿と本人編集のとき

写真は口コミ（個人の評価）ではなく場所に紐づきます（sk = SPOT の行の photoKeys）。 そのため、他人が作った場所に評価を付けるときは写真を送れません（送っても service.js が扱いません）。 名前・ジャンル・写真を変えられるのは、その場所を最初に登録した本人だけです。

3. 写真の実体の削除は「ベストエフォート」

本人編集で写真を外したとき、DynamoDB の photoKeys から消すのと合わせて S3 の実体も削除しますが、 この削除は失敗しても投稿は成功扱いにし、警告ログだけを残します。 

} catch (error) {
  logWarn('不要になった写真の削除に失敗しました', {
    errorName: error.name,
    count: photoKeys.length
  });
}

理由は、本体（DynamoDB）の更新がすでに終わっているためです。削除の失敗でエラーを返すと、 利用者には「投稿に失敗した」と見えるのに実際は保存されている、という混乱が起きます。 残ってしまったファイルは参照されないだけなので、影響はストレージ費用に限られます。

4. 写真は CloudFront 経由で配信していない（循環参照を避けるため）

当初は他の静的ファイルと同じく CloudFront から配信する想定でしたが、そうすると次の依存の輪ができます。 

写真バケットのポリシー → 配信（CloudFront）を参照
配信（CloudFront） → /api/* 経由で API Gateway → 写真URL発行Lambda
写真URL発行Lambda → 写真バケットを参照   ← 一周して戻ってくる

CloudFormation はこの輪を解決できずデプロイに失敗します。 そのため写真は CloudFront を通さず、getSpot が返す署名付きGET URL（有効期限1時間）で直接取得する形にしています。 同じ理由で、アップロード用の CORS 設定も配信ドメインではなく '*' を許可しています （PUT 先のURL自体が5分間しか有効でないため、オリジンを絞らなくても成立します）。

5. spot と waypoint を混同しない

この機能で出てくる spot は「利用者が立ち寄る場所」です。 経路の線を描くための座標の点は waypoint で、まったく別のものです。 混同すると「巡ったスポット数」に道の曲がり角まで数えてしまい、エラーにならないまま数字だけがおかしくなります。 詳細は用語辞書の「特に間違えやすい2組」を参照してください。

6. ロケーション名は spotName。location 単独は使わない

口コミ対象の場所の名称は spotName に統一されています。 location だけだと「現在地」なのか「口コミの対象」なのか判別できないため、用語辞書で禁止されています。 画面に出る「ロケーション名」というラベルに引かれて locationName と書かないよう注意してください。

設計書 ルート関連の API 仕様と DynamoDB の設計。口コミ API（/spots / /reviews / /review-photo-uploads / /my-reviews）はこの時点では未記載なので、仕様はコードと本解説書を参照する
仕様書 画面仕様と開発コマンド（npm run dev などの一覧）。口コミ画面の記載はまだない
口コミの場所を巡るルート 投稿された口コミの場所をルートの候補に混ぜる機能（続きの機能）
チュートリアル ダミーの紫ピンで口コミの評価を練習する流れ
