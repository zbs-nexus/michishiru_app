🧩 先に知っておきたいこと

Amazon Cognito のユーザープール
ユーザー名とパスワードを預かり、ログインの確認と「ログイン済みの証明（トークン）」の発行を代わりにやってくれる AWS のサービスです。 ミチシルはユーザー名でサインインし、ログイン画面はアプリ内に自作しています（Cognito が用意するログイン画面は使わない）。
Amplify（aws-amplify/auth）
ブラウザから Cognito を呼ぶためのライブラリです。前提条件書は「ホスティングに AWS Amplify を使わない」と決めていますが、これは配信サービスの話で、 このライブラリ（認証のクライアント部品）は使っています。ログイン状態はブラウザの保存領域に残るので、再読み込みしてもログインしたままです。
SRP
パスワードそのものをネットワークに流さずに「正しいパスワードを知っている」ことを証明する方式です。Amplify の signIn が既定で使います。
VITE_ で始まる環境変数
Vite はビルド時に VITE_ で始まる環境変数を成果物へ埋め込みます。実行時には読みに行かないため、ビルドのときに値が揃っていないと「空のまま配信」されます。

📖 この機能について

ユーザー名とパスワードでログインする画面（/login、ルート名 login）です。 ログインしていない人はどの画面を開いてもログイン画面へ送られ、ログイン済みの人がログイン画面を開くとホームへ送られます。 ログイン画面からはユーザー登録とパスワードの再設定へ進めます。

🎯 なぜこの機能が必要？

口コミ・散歩の実績・マスコットのレベルなど、利用者ごとのデータを扱うには「誰が使っているか」を確かめる必要があります。 また、API を呼べる人をログイン済みの人に限ることで、ルート作成（AI と地図サービスの利用料がかかる）を第三者に勝手に使われないようにします （APIの認可）。

🔄 処理の流れ

Step 1: 起動時に Cognito の設定を渡す（main.js）
constants/authConfig.js がビルド時の環境変数からユーザープールIDとアプリクライアントIDを読み、 揃っていれば Amplify.configure({ Auth: AUTH_CONFIG }) を最初の画面を描く前に呼びます。揃っていなければコンソールにエラーを出します。
Step 2: 画面を開くたびにログイン状態を確かめる（router/index.js）
beforeEach が、再読み込み直後なら一度だけ authStore.restoreSession() でセッションを復元し、 公開画面（meta.isPublic）以外は未ログインならログイン画面へ送ります。
Step 3: 入力してログイン（LoginForm → LoginView → authStore → authService）
LoginForm が submitLogin を emit し、LoginView が authStore.signIn() を呼びます。 ストアは signInWithPassword() で Cognito に問い合わせ、成功したらユーザー名を控えます。
Step 4: 結果
成功したらホーム（route-condition）へ進みます。失敗したら Cognito の例外名を日本語の文言に変換してフォームに表示します。

💻 コードの解説

frontend/src/services/authService.js

export const signInWithPassword = async (username, password) => {
  const { isSignedIn, nextStep } = await cognitoSignIn({ username, password });

  if (isSignedIn) {
    return;
  }

  // 未確認のユーザー・MFA・初回パスワード変更など、追加の手続きを求められた場合。
  // 対応する画面を用意していないため、失敗として上位へ返す
  const error = new Error(`サインインが完了しませんでした: ${nextStep.signInStep}`);
  error.name =
    SIGN_IN_STEP_ERROR_NAMES[nextStep.signInStep] ?? nextStep.signInStep;
  throw error;
};
  • Amplify v6 は、追加の手続きが要るときに例外ではなく「次の手続き（nextStep）」として返します。この関数はそれを例外に変え、呼び出し側が成功・失敗だけを見れば済むようにしています
  • 例外名と画面の文言の対応は ERROR_MESSAGES にまとめています（例: NotAuthorizedException と UserNotFoundException はどちらも「ユーザー名またはパスワードが違います」。ユーザーの有無を言い当てないため）
  • ログイン状態の確認は fetchSignedInUsername()、API用のトークンは fetchIdToken() が返します

frontend/src/stores/authStore.js

名前役割
username / isSignedInログイン中のユーザー名と、ログイン済みか（ユーザー名があれば真）

frontend/src/router/index.js（ガード）

if (!authStore.isSessionRestored) {
  await authStore.restoreSession();
}

if (to.meta.isPublic) {
  // ログイン済みならログイン画面には留まらせず、ホームへ送る
  return authStore.isSignedIn ? { name: 'route-condition' } : true;
}

if (!authStore.isSignedIn) {
  return { name: 'login' };
}

公開画面はログイン・ユーザー登録・パスワード再設定の3つです。開発サーバーのデザイン確認画面（/design-preview）だけは判定より先に通します。

CI（.github/workflows/deploy.yml）— 194f15e 時点

当初は、GitHub の Variables に登録した VITE_COGNITO_USER_POOL_ID / VITE_COGNITO_USER_POOL_CLIENT_ID をビルドへ渡し、空ならデプロイを止めていました。 現在は cdk deploy --outputs-file の出力から tools/exportCognitoOutputs.js が取り出して渡す方式です（Variables への登録は不要）。

⚠️ 注意ポイント

ユーザープールIDはシークレットではない
ユーザープールIDとアプリクライアントIDはビルド成果物に含まれ、誰でも見られます。SPA 用のアプリクライアントはクライアントシークレットを持たないため、 見られても認証を突破する材料にはなりません。ただし環境ごとに値が違うので、コードに直書きしないでください（前提条件書のルール）。
追加の手続きには画面が無い
MFA や初回のパスワード変更（仮パスワード）を求められるユーザーは、このアプリではログインできず「管理者に連絡してください」と出ます。 また、確認コードの入力を終えていない（未確認の）ユーザーも同じく「管理者に連絡してください」の文言になりますが、 現在はユーザー登録画面から自分で確認コードを入力できます。文言と実際の手段が合っていない点は見直しの候補です。
ローカルでは接続情報を自分で用意する
frontend/.env.local に VITE_COGNITO_USER_POOL_ID と VITE_COGNITO_USER_POOL_CLIENT_ID（dev のユーザープールの値）を書かないと、ログインできません。

✅ 動作確認方法

  1. frontend/.env.local に dev のユーザープールの接続情報を設定する（値は Michishiru-dev スタックの出力 UserPoolId / UserPoolClientId）
  2. npm run dev で起動し、/ を開くと /login へ送られることを確かめる
  3. 正しいユーザー名・パスワードでホームへ進むこと、間違えると「ユーザー名またはパスワードが違います」と出ることを確かめる
  4. ログインしたまま再読み込みしてもホームに留まること、ログイン済みで /login を開くとホームへ送られることを確かめる
  5. テスト: frontend で npm test（src/services/__tests__/authService.test.js / src/components/feature/auth/__tests__/LoginForm.test.js。いずれも後のマージで追加）
