🗓 対象期間: 2026-10-01 〜 2026-10-14
📅 マージ日: 2026-10-07（10:23）, 2026-10-14（09:16）
🌿 対象ブランチ: feature/NZ-230（PR #69「散歩実測値の取得」）, feature/NZ-176（PR #79）
🔖 対象マージ: 95b51ab（GPSの軌跡から距離を積む。計画ファイルでは段階1）, dc87c1c（計測の信頼性: 計測状態・欠落の検知・画面の消灯抑止）

※ 2026-10-28 更新: 次の目的地の到達判定（40m以内で自動）は廃止され、「次の目的地へ」ボタンでのみ到達済みにする方式に変わっています（次の目的地表示）。「巡ったスポット」もボタンで到達済みにした数です。

🧩 先に知っておきたいこと

Pinia のストアとは
Vue で「複数の画面から読み書きできる値の置き場所」を作る仕組みです。案内画面から結果画面へ移動すると案内画面は破棄され、その中で宣言した変数は消えてしまいます。画面をまたいで残したい値はストアに置きます。
Composable とは
use で始まる名前の関数で、画面の見た目を持たずにロジックだけを切り出したものです。useWalkRecord は画面に何も表示せず、現在地が変わったときに距離を計算してストアへ書き込むだけを担います。
watch（監視）とは
Vue の機能で、指定した値が変わったときに関数を実行します。この機能では「現在地が更新されるたびに距離を測り直す」ために使っています。
GPSの精度（accuracy）とは
ブラウザが返す「本当の位置はこの半径○メートルの円のどこか」という目安の数字で、小さいほど正確です。立ち止まっていても座標は数メートル揺れ続けます。現在地を取得する仕組み自体は 現在地取得機能の実装解説 で説明済みです。
SPA はリロードで状態が消える
この画面はブラウザのメモリ上で動くため、再読み込みするとストアの中身は初期値に戻ります。実績をサーバーへ保存する処理は、このマージの時点ではまだありません。

📖 この機能について

案内中にブラウザから届く現在地をつなぎ合わせて「実際に歩いた距離」を積み上げ、散歩結果画面の総距離・巡ったスポット・所要時間を実測値で表示する機能です。

このマージで追加されたファイルは2つだけです。

ファイル担うこと
frontend/src/composables/useWalkRecord.js現在地の変化を監視し、「歩いたとみなせる区間」だけを選んで距離を積む
frontend/src/stores/walkStore.js積んだ距離・到達したスポット・開始/終了時刻を、画面をまたいで保持する

残りの変更は、この2つを案内画面から呼び出し、結果画面の表示元を差し替える配線です。

🎯 なぜこの機能が必要？

関連するユーザーストーリーは US-8（散歩結果確認）「散歩の結果を確認したい。なぜなら、距離や訪れたスポットを確認したいからだ」です。

このマージの前、結果画面はルート作成時の予測値を出していました。

<!-- 変更前（routeStore = ルート作成時の予測値） -->
:distance-km="routeStore.currentRoute.distanceKm"
:spot-count="spotCount"
:duration-minutes="routeStore.currentRoute.durationMinutes"

この値は Amazon Location Service が計算した「このルートを歩けばこれくらい」という見積もりなので、途中で近道をしても、1か所しか立ち寄らずに終了しても、いつも同じ数字が出ます。歩いた本人にとって確認する意味がありません。そこで、案内中に自分で測った値へ差し替えました。

🔄 処理の流れ

useLocationTracking（ブラウザの watchPosition から現在地を受け取る）
   │
   ▼  currentLocation / accuracy
useWalkRecord（8段のガードで「歩いた区間」だけを選ぶ）
   │
   ▼  walkStore.addDistanceM(segmentDistanceM)
walkStore（totalDistanceM に積む / 到達スポット・開始終了時刻も持つ）
   │
   ▼  totalDistanceKm / spotCount / elapsedMinutes
WalkResultView → WalkResultStats（結果画面に表示）
Step 1: 案内開始と同時に計測を初期化する（RouteNavigationView.vue）
onMounted で walkStore.startWalk() を呼び、そのあとで startTracking()（現在地の追跡開始）を呼びます。順番が逆だと、初回の測位で積んだ距離を直後の初期化が消してしまいます。
Step 2: 現在地が1件届く（useLocationTracking.js）
ブラウザの watchPosition が位置を知らせるたびに、currentLocation（座標）と accuracy（精度）が更新されます。測位前の currentLocation には仮の座標（新宿）が入っていて、accuracy は null です。
Step 3: 区間距離を測り、採用するか決める（useWalkRecord.js）
前回採用した地点（起点）から現在地までの距離を segmentDistanceM（区間距離）として計算し、ゆらぎ・飛び・精度の3種類のふるいにかけます。判定の内容は次章で詳しく説明します。
Step 4: 採用した区間だけを積む（walkStore.addDistanceM）
ふるいを通った区間距離を totalDistanceM に足し、起点を現在地へ進めます。useWalkRecord は値を返さず、ストアへ直接書き込みます。
Step 5: 到達したスポットをストアへ写す（RouteNavigationView.vue）
到達済みの管理そのものは既存の useRouteProgress が行います（現在は「次の目的地へ」ボタンを押したときに到達済みになります）。その結果（visitedSpotIds）を watch で監視し、変わるたびに walkStore.setVisitedSpotIds() へ渡します。案内画面が破棄されても結果画面から読めるようにするためです。
Step 6: 終了ボタンで時刻を確定して遷移する（handleConfirmEnd）
確認モーダルで「終了する」が押されたら、router.push の前に walkStore.endWalk() を呼んで終了時刻を確定させます。結果画面は所要時間をそこから計算します。
Step 7: 結果画面が実績を表示する（WalkResultView.vue）
walkStore の totalDistanceKm / spotCount / elapsedMinutes を WalkResultStats に渡します。測位できなかった場合は、数値の下に注記を出します。

💻 コードの解説

frontend/src/composables/useWalkRecord.js — どの区間を「歩いた」とみなすか

このファイルの本体は「判定の順番」です。しきい値は3つあり、それぞれ防ぎたいものが違います。

定数値これが無いと起きること
MIN_SEGMENT_DISTANCE_M10 m立ち止まっていても座標が数メートル揺れるため、歩いていない距離が増え続ける（GPSのゆらぎ）
MAX_SEGMENT_DISTANCE_M200 m徒歩では1回の測位間隔で進めない距離が一気に加算される。移動ではなく座標の誤り（測位の飛び）
MAX_MEASURABLE_ACCURACY_M100 m精度が極端に悪い測位では、歩いた分とゆらぎを区別できないのに積んでしまう
const MIN_SEGMENT_DISTANCE_M = 10;
const MAX_SEGMENT_DISTANCE_M = 200;
export const MAX_MEASURABLE_ACCURACY_M = 100;

（上はコメントを省いた宣言部分です。ファイルには、それぞれの値を選んだ理由がコメントで書かれています。）

監視の中は番号付きのガードが8段並びます。最初の3段は次のとおりです。

    // ① 初回の測位までは現在地がフォールバック座標（新宿）のままなので弾く。
    // 弾かないと実際の現在地との間に巨大な偽の区間が生まれる。
    // accuracyは実際に測位できた時点で数値が入る
    if (accuracy.value === null) {
      return;
    }

    // ② 測位そのものは届いたので、精度の良し悪しに関わらず記録する。
    // 距離を積めたかどうかとは別の事実で、結果画面が
    // 「位置情報を取得できなかった」と「歩いた距離が0だった」を言い分けるために使う
    walkStore.markLocationFixed();

    // ③ 精度が悪すぎる測位は、歩いた距離とゆらぎを区別できないため積算しない。
    // 起点は据え置き、精度が回復した時点でそれまでの移動を測れるようにする
    if (accuracy.value > MAX_MEASURABLE_ACCURACY_M) {
      return;
    }

後半で、ゆらぎと飛びを分けて扱います。どちらも距離は積まないのに、起点の扱いが逆なのがこの実装の要点です。

    // ⑥ 飛び判定。加算はしないが起点は打ち直す。
    // 古い起点を残すと、以降の測位でも同じ巨大な区間を測り続けてしまう
    if (segmentDistanceM > MAX_SEGMENT_DISTANCE_M) {
      previousPosition = {
        lat: currentLocation.value.lat,
        lng: currentLocation.value.lng
      };
      return;
    }

    // ⑦ ゆらぎ判定。加算せず、起点も据え置く。
    // 起点を据え置くことで、小さな移動が累積してしきい値を超えた時点でまとめて積める。
    // しきい値に精度を使うのは、精度が悪い場所では揺れの幅もその分大きくなるため。
    // ③で精度を MAX_MEASURABLE_ACCURACY_M 以下に絞っているため、このしきい値が
    // ⑥の MAX_SEGMENT_DISTANCE_M を超えることはない（採用できる区間が必ず存在する）
    if (segmentDistanceM < Math.max(accuracy.value, MIN_SEGMENT_DISTANCE_M)) {
      return;
    }

    // ⑧ 実際に歩いた区間として積算し、起点を現在地へ進める
    walkStore.addDistanceM(segmentDistanceM);
ガード条件距離を積むか起点（previousPosition）
① 未測位accuracy が null積まないそのまま
③ 精度が悪いaccuracy > 100積まない据え置き（回復後にまとめて測れる）
④ 最初の1件起点が未設定積まない現在地を起点にする
⑤ 座標が不正距離が null積まないそのまま
⑥ 飛び区間距離 > 200 m積まない打ち直す
⑦ ゆらぎ区間距離 < max(精度, 10 m)積まない据え置く
⑧ 採用上のどれにも当たらない積む現在地へ進める
  • 飛びで起点を打ち直す理由: 誤った座標を起点のまま残すと、次の測位でも同じ巨大な区間を測り続け、以降ずっと距離が積めなくなります。
  • ゆらぎで起点を据え置く理由: ゆっくり歩いている人は1回の測位で数メートルしか進みません。毎回起点を進めてしまうと、どの区間も10m未満で永久に加算されません。起点を動かさなければ、合計が10mを超えた時点でまとめて積めます。
  • ゆらぎのしきい値に accuracy を混ぜているのは、精度が悪い場所では揺れの幅もその分大きくなるためです（精度が30mなら30m未満は揺れとみなす）。

距離の計算そのものは frontend/src/utils/geoDistance.js の calculateDistanceM（球面上の2点間の距離を求めるハバーサイン公式）に任せています。座標として扱えない値が渡されると null を返すため、⑤でそれを見ています。

frontend/src/stores/walkStore.js — 実績の置き場所

ストアID は 'walk'。ルート作成時の予測値を持つ routeStore とは別に作られています。責務が違い、リセットするタイミングも別（条件のリセットと実績のリセットを分けたい）だからです。

種別名前内容
状態totalDistanceM積算した距離（メートル）。内部は常にメートルで持つ
状態visitedSpotIds到達したスポットのIDの一覧
状態startedAt / endedAt案内の開始・終了時刻（エポックミリ秒）
状態hasLocationFix一度でも現在地を採用できたか
算出値totalDistanceKm表示直前にkmへ換算する（丸め誤差を積み上げないため）
算出値spotCountvisitedSpotIds.length。経路の折れ点（waypoint）ではなく立ち寄り先の数
算出値elapsedMinutes開始から終了までの分数
操作startWalk()距離・スポット・終了時刻などを初期化し、開始時刻を入れる
操作addDistanceM() / markLocationFixed() / setVisitedSpotIds()計測結果の書き込み
操作endWalk() / resetWalk()終了時刻の確定 / 全状態を初期値へ戻す
  const elapsedMinutes = computed(() => {
    if (startedAt.value === null) {
      return 0;
    }

    return Math.round(
      ((endedAt.value ?? Date.now()) - startedAt.value) / MILLISECONDS_PER_MINUTE
    );
  });

endedAt がまだ無い（案内中の）場合は現在時刻までを返すので、案内中でも経過時間が読めます。?? は「左が null か undefined なら右を使う」という書き方です。

frontend/src/views/RouteNavigationView.vue — 配線

// 距離の積算は公開する状態を持たず、現在地のwatchでwalkStoreへ直接書き込む
useWalkRecord({ currentLocation, accuracy });

// 到達状況をストアへ写し、結果画面でも巡ったスポット数が読めるようにする。
// useRouteProgressは配列を丸ごと差し替えるためdeepは不要
watch(visitedSpotIds, (spotIds) => {
  walkStore.setVisitedSpotIds(spotIds);
});

現在地の追跡（useLocationTracking）はこの画面で1回だけ開始し、地図・次の目的地バナー・距離の積算の3者に同じ値を渡しています。それぞれが追跡を始めると watchPosition が二重に動いてしまうためです。

frontend/src/views/WalkResultView.vue — 表示元の差し替え

      <WalkResultStats
        :distance-km="walkStore.totalDistanceKm"
        :spot-count="walkStore.spotCount"
        :duration-minutes="walkStore.elapsedMinutes"
      />

WalkResultStats は受け取った3つの数値を「総距離 / 巡ったスポット / 所要時間」として並べるだけの表示部品です。props はすべて Number の必須なので、ストア側は null を返さず必ず数値（初期値は0）を返すようにしてあります。

このマージの時点では、測位できなかった場合だけ注記を出していました。

      <p
        v-if="!walkStore.hasLocationFix"
        class="hint"
        role="status"
      >
        位置情報を取得できなかったため、実績を計測できませんでした
      </p>

role="status" は、画面読み上げソフトにこの文章の出現を伝えるための指定です。

計測状態（measurementStatus）— dc87c1c で追加

現在の walkStore.js には、上の hasLocationFix だけでは言い分けられない状況のために、3値の measurementStatus が入っています。これは dc87c1c（2026-10-14 / feature/NZ-176）で加わったもので、段階1（95b51ab）の時点のコードには存在しません。

  const measurementStatus = computed(() => {
    if (hasLocationFix.value === false) {
      return MEASUREMENT_STATUS.UNAVAILABLE;
    }

    if (hasMeasurementGap.value === true) {
      return MEASUREMENT_STATUS.PARTIAL;
    }

    if (totalDistanceM.value === 0) {
      return MEASUREMENT_STATUS.PARTIAL;
    }

    return MEASUREMENT_STATUS.COMPLETE;
  });
値どんな状態か結果画面の注記
unavailable一度も測位できていない位置情報を取得できなかったため、実績を計測できませんでした
partial測位はできたが、途切れた区間がある／距離が0のまま一部の区間を計測できなかったため、実際より短く表示されている可能性があります
complete測位できて距離も積めた注記なし

2値（測れた／測れなかった）ではなく3値にしているのは、「測れてはいるが足りていない」という状態が実際に起きるためです。トンネルで測位が止まった、画面を消していた、精度が悪い区間が続いた、といった場合に数値は出ますが実際より短くなります。そこで数値は常に表示したうえで、足りない可能性を注記で正直に伝える形にしています。判定は強い事実から順に見ます（測位できていない → 欠落を検知した → 距離が0のまま）。

欠落の検知（hasMeasurementGap）— dc87c1c で追加

hasMeasurementGap を立てるのは RouteNavigationView.vue です。次の2種類の「止まっていた時間」を散歩全体で合計し、合計が MEASUREMENT_GAP_THRESHOLD_MS（60秒）以上になったら walkStore.markMeasurementGap() を呼びます。

止まっていた時間どう測るか
測位の中断isMeasurementInterrupted（測位エラーが出ている、または精度が MAX_MEASURABLE_ACCURACY_M より悪い）が真の間。復帰しないまま続く場合に備え、残り時間でタイマーも張る
画面の非表示visibilitychange で hidden になってから戻るまで。非表示中は測位側では数えない（同じ時間を2回積まないため）
const addMeasurementGapMs = (gapMs) => {
  accumulatedGapMs += gapMs;

  if (accumulatedGapMs >= MEASUREMENT_GAP_THRESHOLD_MS) {
    walkStore.markMeasurementGap();
  }
};
  • 1回の中断ごとに判定を捨てず合計するのは、「信号待ちのたびに数十秒切れる」ような断続的な不調も拾うためです
  • 測位エラー1回では欠落にしません。タイムアウト（10秒）は屋内や高架下で普通に起き、その間に進む距離（約12m）では実害がないためです
  • 60秒より短い中断なら、復帰時の区間が200m以内に収まり、距離は直線でつながります
  • 一度立てた hasMeasurementGap は戻しません。途切れていた間の距離は取り戻せないためです

画面の消灯抑止（useScreenWakeLock）— dc87c1c で追加

スマートフォンは画面が自動で消えると測位が止まります。そこで案内中は、ブラウザの Screen Wake Lock API（画面を点けたままにする仕組み）で自動消灯を抑止します。 frontend/src/composables/useScreenWakeLock.js の requestScreenWakeLock() を案内画面の表示時と、非表示から戻ったとき（非表示になると自動で解放されるため）に呼びます。

  • 未対応のブラウザでは何もせずに抜けます（案内自体は消灯抑止なしでも成立する）
  • 取得の待ち合わせ中に画面を離れた場合は、取れたロックをその場で捨てます
  • 画面の破棄時（onBeforeUnmount）に必ず解放します。残すと案内画面を離れても消灯が止まったままになります

⚠️ 注意ポイント

実績は1回の散歩分しか残らず、リロードで消える
walkStore はブラウザのメモリ上にあるだけです。結果画面で再読み込みすると値は0に戻り、「ホームに戻る」を押すと resetWalk() で消えます。
※ 2026-10-28 更新: dc87c1c 以降は、終了時に1回分の実績がサーバー（WalkResult-<環境>）へ保存され、累計にも足されます。画面上の walkStore がリロードで消える点は変わりません（散歩実績の保存）。
hasLocationFix は「距離を積めた」ではなく「測位が届いた」
精度が悪くて距離を積めなかった場合でも、測位そのものが届けば true になります（ガード②）。これは「位置情報を取得できなかった」と「歩いた距離が0だった」を結果画面で言い分けるための区別です。混同すると、注記が出る条件を読み間違えます。
しきい値は単独で変えない
MAX_MEASURABLE_ACCURACY_M（100m）は、必ず MAX_SEGMENT_DISTANCE_M（200m）より小さくしておく必要があります。ゆらぎ判定のしきい値は max(精度, 10m) なので、精度の上限が200mを超えると「飛びでもゆらぎでもない区間」が存在しなくなり、距離が一切積まれなくなります。
実測値は予測値より短く出るのが普通
10m未満の細かい往復や、精度が悪い区間の移動は捨てられます。GPSの軌跡を直線でつないで測るため、カーブも内側を通ります。ルート作成時の距離と一致しなくても不具合ではありません。
spot と waypoint を混同しない
「巡ったスポット」は立ち寄り先（spot）の数です。経路を描くための座標点（waypoint、1ルートに数十個）を数えると、4箇所のはずが37箇所と表示されます。エラーにならないため気付きにくい不具合です。

✅ 動作確認方法

  1. リポジトリのルートで npm run dev を実行します（フロントとローカルAPIが同時に起動します）。
  2. ホーム画面で条件を選んでルートを作成し、提案 → 決定で案内画面へ進みます。
  3. Chrome の開発者ツールで位置を動かします。F12 →「︙」→「More tools」→「Sensors」→「Location」で「Other…」を選び、緯度・経度を入力します。
  4. 数十メートル〜百メートル程度ずつ動かし、終了後の「総距離」が動かした分だけ増えることを確認します。
    • ほんの少し（10m未満）だけ動かした場合は増えません（ゆらぎ判定）。
    • 一度に200mより遠くへ飛ばした場合も増えません（飛び判定）。
  5. 「次の目的地へ」を押すと「巡ったスポット」が増えることを確認します（2026-10-14 以降、近づいただけでは増えません）。
  6. 開発者ツールの「Sensors」で位置を「Location unavailable」にして60秒以上待つ、あるいは別のタブへ60秒以上切り替えてから戻り、終了後に「一部の区間を計測できなかったため…」の注記が出ることを確認します。
  7. 「終了」→「終了する」で結果画面に進み、「所要時間」が案内を始めてからの分数になっていることを確認します。
  8. 位置情報の許可をブロックしたまま案内を終了し、「位置情報を取得できなかったため、実績を計測できませんでした」が出ることを確認します。
  9. 「ホームに戻る」からもう一度ルートを作って案内・終了し、前回の距離やスポット数が積み上がっていないことを確認します。
  10. 静的検査とビルド: frontend/ で npm run lint と npm run build。
  11. 自動テスト: frontend/ で npm test（Vitest）。src/stores/__tests__/walkStore.test.js が measurementStatus の4通りを検証します。src/composables/__tests__/useScreenWakeLock.test.js が消灯抑止の取得・解放を、src/views/__tests__/RouteNavigationView.test.js が欠落の検知を検証します。※ これらのテストは dc87c1c で追加されたものです。段階1の検証は lint とビルド、手動確認で行われました。
