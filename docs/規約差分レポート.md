### 0.1 いちばん重要な結論

**規約の大半は「名前の付け方の間違い」ではなく、「規約が求めている仕組みがまだ存在しない」という状態です。**

規約はVue 3とAWS Lambdaで作られた本格的なアプリを前提にしています。一方、現在のミチシルは素のJavaScriptとExpressで作られた動作確認用のモックです。土台の技術が違うため、多くの項目が「不足」として現れています。

つまり、現在のコードが雑に作られているわけではありません。作られた目的（操作イメージの確認）と、規約が想定している目的（チーム開発・本番運用）が違うだけです。

### 0.4.1 対応済みの内容（2026年8月26日）

使用言語（JavaScript / HTML / CSS）の範囲内で、用語辞書に反する命名を修正しました。Vue移行は実施していません。

| 変更前 | 変更後 | 対象ファイル |
|---|---|---|
| `spot` | `waypoint-marker` | `index.html`、`styles.css` |
| `spot-icon` | `waypoint-icon` | 同上 |
| `spot-name` | `waypoint-name` | 同上 |
| `nav-spot` | `nav-waypoint` | 同上 |
| `start-point` | `origin` | 同上 |
| `endpoint` | `destination` | 同上 |
| `spots: 4` | `waypointCount: 4` | `app.js` |
| `spots: [...]` | `waypoints: [...]` | `server.js` |

提案画面の`spot`は、詳細画面に既存の`.waypoint`（経路上の点）があるため、単純な`waypoint`ではなく`waypoint-marker`としました。辞書に登録済みの`waypoint`と`marker`を組み合わせ、辞書準拠のまま両者を区別しています。

あわせて、距離の入力方式をプルダウンからスライダーへ変更し、選択肢を定数`DISTANCE_OPTIONS_KM`へ切り出しました。

## 1. 本書の目的と読み方

本書は、別チームが作成したステアリングガイドと、現在のミチシルのコードを1件ずつ突き合わせた結果をまとめたものです。

差分は次の3種類に分類しています。

| 分類 | 意味 | 対応の考え方 |
|---|---|---|
| 不足 | 規約が求めているものが存在しない | 必要になった段階で作る |
| 違反 | 存在するが規約と異なる | 早めに直す |
| 過剰 | 規約通りに作ると現状の規模に不釣り合い | 段階的に導入する |

「違反」は既にあるコードの修正で解決できるため、優先度が高くなります。

## 2. 用語辞書との差分（違反・優先度高）

規約の「ドメイン用語辞書」には、使ってはいけない表記揺れが定義されています。調査時点のコードは複数該当していました。

> **本章の状態:** 2.1と2.2は2026年8月26日に対応済みです。以下は指摘時点の記録として残しています。実際の反映内容は第0.4.1節を参照してください。2.3の未登録用語は未対応です。

### 2.1 禁止語の使用

| 現在のコード | 主な場所 | 規約の指定 | 修正後 |
|---|---|---|---|
| `spot` | `index.html`（クラス）、`styles.css` | `spot`は使用禁止 | `waypoint` |
| `spot-icon` | `index.html`、`styles.css` | 同上 | `waypoint-icon` |
| `spot-name` | `index.html`、`styles.css` | 同上 | `waypoint-name` |
| `nav-spot` | `index.html`、`styles.css` | 同上 | `nav-waypoint` |
| `spots: 4` | `app.js` | 同上 | `waypointCount: 4` |
| `spots: [...]` | `server.js`（API応答） | 同上 | `waypoints: [...]` |
| `start-point` | `index.html`、`styles.css` | `start`は使用禁止 | `origin` |
| `endpoint` | `index.html`、`styles.css` | 曖昧な表現 | `destination` |

### 2.2 同じ概念に2つの名前を使っている

これは特に注意すべき点です。同じ「経由地」を、画面によって別の名前で呼んでいます。

| 画面 | 使用している語 |
|---|---|
| ルート提案画面 | `spot` |
| ルート詳細画面 | `waypoint` |
| ルート案内画面 | `nav-spot` |

辞書は「同じ概念に複数の英語を使わない」と定めているため、これは違反です。すべて`waypoint`に統一する必要があります。

### 2.3 辞書に未登録の用語

規約は「新しいドメイン用語は辞書に追記してから使用する」と定めています。以下は現在使われていますが辞書にありません。

| 未登録の語 | 使用箇所 | 意味 |
|---|---|---|
| `purpose` | `app.js`、`index.html` | 散歩の目的 |
| `genre` | `app.js`、`index.html` | 散歩のジャンル |
| `refresh` / `exercise` / `sightseeing` / `cafe` | `data-value` | 目的の選択値 |
| `nature` / `city` / `history` / `gourmet` | `data-value` | ジャンルの選択値 |
| `turn-icon` | `styles.css` | 曲がる方向の表示 |
| `street-label` | `styles.css` | 通り名の表示 |
| `park` / `shrine` / `viewpoint` | クラス・API | 経由地の種類 |

対応方針は2つあります。

1. 辞書へ追記して正式な用語にする
2. 既存の辞書用語へ置き換える

なお`distance`（距離）と`duration`（所要時間）は辞書に登録済みで、現在のコードも正しく使えています。

## 3. 命名規則との差分

### 3.1 適合している項目

現在のコードは、基本的な命名形式は守れています。

| 対象 | 規約 | 現在の例 | 判定 |
|---|---|---|---|
| 変数・関数 | camelCase | `showScreen`、`createRoute`、`purposeButtons` | 適合 |
| 定数 | UPPER_SNAKE_CASE | `PORT` | 適合 |
| CSSクラス | kebab-case | `route-info-card`、`current-location` | 適合 |
| JSONキー | camelCase | `name`、`distance`、`duration` | 形式は適合 |
| Boolean | is/has/can | 該当なし | 判定対象外 |

### 3.2 違反している項目

| 対象 | 規約 | 現在 | 問題点 |
|---|---|---|---|
| APIパス | kebab-case、`/api/v1/routes` | `/api/route` | バージョンがない、単数形 |
| 環境変数 | UPPER_SNAKE_CASE で定義 | 未使用 | ポートとIPが直書き |
| ID属性 | `〇〇Id` 接尾辞、UUID v4 | `id: 1` | 接尾辞なし、連番 |
| 日時属性 | `createdAt` / `updatedAt` | なし | データに存在しない |
| JSONキーの語彙 | 辞書準拠 | `spots` | 用語辞書違反 |

APIパスの比較を示します。

```text
現在:  GET /api/route
規約:  GET /api/v1/routes
```

データ形式の比較を示します。

```text
現在
{
  "id": 1,
  "name": "緑とカフェのんびりコース",
  "spots": [...]
}

規約準拠
{
  "routeId": "3f2b8c1e-...",
  "routeName": "緑とカフェのんびりコース",
  "waypoints": [...],
  "createdAt": "2026-08-26T10:00:00Z"
}
```

### 3.3 判断が必要な項目

| 対象 | 状況 |
|---|---|
| `michishiru-mock`（`package.json`のname） | 規約は「ローマ字禁止」。ただしアプリ名は固有名詞なので、例外扱いにするかチームで確認が必要 |
| `docs/仕様書.md` などの日本語ファイル名 | 規約はディレクトリのkebab-caseのみ規定。ドキュメントの日本語名の可否が未定義 |

## 5. コンポーネント設計ルールとの差分

## 6. バックエンド・レイヤー構成の差分

> **本章の状態:** 2026年8月26日に解消済みです。4層への分割、JSDocの付与、テストの追加、ハードコードの解消を実施しました。以下は調査時点の記録です。

### 6.1 レイヤー分割がない

規約はバックエンドを4つに分けることを求めています。

```text
handler.js     受付と返却のみ
service.js     ビジネスロジック
repository.js  データ取得
validator.js   入力チェック
```

現在の`server.js`は32行にすべてが入っています。

| 規約の要求 | 現在の状態 | 分類 |
|---|---|---|
| `handler.js`にロジックを書かない | ハンドラー内で直接データを返している | 違反 |
| `service.js`を置く | なし | 不足 |
| `repository.js`を置く | なし | 不足 |
| `validator.js`を置く | なし | 不足 |
| Handler → Service → Repository の一方向呼び出し | 層が存在しない | 不足 |
| 1 Lambda = 1責務 | Lambda未使用 | 不足 |
| `shared/`に共通処理 | なし | 不足 |
| 関数ごとに`package.json` | ルートに1つのみ | 不足 |
| `__tests__/`にテスト | なし | 不足 |

### 6.2 ハードコードの違反

規約は環境変数のハードコードを禁止しています。現在の`server.js`には2箇所あります。

```javascript
const PORT = 3000;
console.log(`  スマホ: http://192.168.110.58:${PORT}`);
```

IPアドレスの直書きは、別のPCやネットワークで実行したときに誤った案内を表示します。

### 6.3 JSDocの不足

規約では次の箇所にJSDocが必須です。

| 対象 | 必須/任意 | 現在 |
|---|---|---|
| handler関数 | 必須 | なし |
| serviceのpublic関数 | 必須 | 層自体がない |
| repositoryの関数 | 必須 | 層自体がない |
| 複雑なロジック | 必須 | `createRoute`にJSDocなし |

現在のコードには日本語の行コメントはありますが、`@param`・`@returns`・`@throws`を使ったJSDocはありません。

## 11. 画面の分類方針（誤解防止）

現在の7画面をそのままViewにすると、規約の「1ルート = 1ファイル」と矛盾します。URLを持たない画面があるためです。

| 現在の画面 | URLを持つか | 規約での配置 |
|---|---|---|
| 初期入力 | 持つ | `views/` |
| ローディング | 持たない（処理中の表示） | `components/feature/` |
| ルート提案 | 持つ | `views/` |
| ルート詳細 | 持つ | `views/` |
| ルート案内 | 持つ | `views/` |
| 終了確認 | 持たない（モーダル） | `components/base/` |
| 散歩結果 | 持つ | `views/` |

したがって「Viewが7つ不足している」ではなく、「Viewが5つ、コンポーネントが2つ必要」という理解が正確です。
