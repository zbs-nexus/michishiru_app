1. CI/CD とは（ざっくり）

CI（継続的インテグレーション）＝ コードを push すると、自動でビルド・テストして壊れていないか確認する仕組み。

CD（継続的デリバリー/デプロイ）＝ コードを push すると、自動でAWSへデプロイ（公開）する仕組み。

このプロジェクトでは GitHub にプッシュするだけで、GitHub Actions が自動でビルドし、AWS（S3 + CloudFront）へ公開します。手作業でファイルをアップロードする必要はありません。

※ 誰が push しても同じように自動で走ります（人ではなく「ブランチ」で動きが決まります）。

4. 開発の進め方（毎日の作業）

はじめる前に：PC に用意するもの

CI/CD 自体はクラウド（GitHub Actions）で動くため、デプロイのために個人PCへ特別なインストールは不要です。必要なのは主にローカル開発用です。

用途必要なもの備考
push して CI/CD を動かすGit ＋ GitHub アカウント（リポジトリ権限）これだけで自動デプロイは走る
ローカルで開発・動作確認Node.js 24 系（npm 同梱）／ エディタ（VS Code 等）npm install → npm run dev など
インフラ(iac)をローカルで触る上記 Node.js（CDK は npx で実行）通常メンバーは基本不要
AWS CLI / AWS の認証情報は、通常の開発メンバーには不要です。パイプラインは GitHub 側の OIDC で AWS に接続します。AWS CLI が要るのは「初回セットアップ（ブートストラップ／OIDCスタック作成）」や手動の AWS 操作を行うインフラ担当者だけです。
  1. 最新を取得：git switch develop → git pull
  2. 変更を加える：（推奨）作業用ブランチ feature/○○ を切って開発、または develop で直接。
  3. develop へ反映：develop に push（またはPRでdevelopへマージ）。
    → dev環境へ自動デプロイが走る。
  4. 開発環境で動作確認：dev の URL を開いて確認。
    ※ CloudFront 反映に数分〜十数分かかることがあります。ブラウザは Ctrl+F5 で更新。
  5. 問題なければ本番へ：develop → main の PR を作成してマージ。
    → prod環境へ自動デプロイが走る。
  6. 本番確認：prod の URL で確認。

GitHub Actions の実行を見る

リポジトリの 「Actions」タブで実行状況が見られます。

  • Deploy ワークフロー … develop / main への push で実行。まず checks（build/test/synth）→ 成功したら deploy。最後の Show stack outputs に公開URL（SiteUrl）が出ます。
  • CI ワークフロー … develop / main 向け PR で実行（共通の checks を呼び出し）。
  • 共通のビルド・テストは再利用ワークフロー checks.yml にまとめ、CI と Deploy の両方から呼ばれます。
  • 失敗時は赤くなります。ステップを開くとログが見られます。

5. develop → main の PR について

PR（プルリクエスト）は「その時点の develop の最新」と main を比較します。したがって：

  • 他のメンバーが develop にマージした内容も自動的に PR に含まれます（PRページを開けば常に最新の develop HEAD が対象）。
  • develop→main の PR は毎回同じリンク/操作でOK。中身は最新の develop に応じて変わります。
だからこそ確認を：main へマージ＝本番反映です。マージ前に PR の差分を見て、「今 develop に入っている全員分の変更」がまとめて本番に出ることを理解してからマージしてください。

6. 注意点（必読）

やってはいけないこと
  • cdk-hnb659fds-assets-... バケットを削除しない（CDKデプロイの土台。消すと全デプロイが壊れます）。
  • スタックが管理している S3 バケット等を手動で削除・変更しない（不整合の原因）。不要な旧リソースは CDK が置き換え時に自動削除します。
  • GitHub Secret AWS_DEPLOY_ROLE_ARN を消さない／名前を変えない。
気をつけること
  • main へのマージ＝本番デプロイ。dev で確認してからにする。
  • develop / main への push では、まず CI（lint・テスト・iac検証）が実行され、成功した場合のみ自動デプロイされます（CI が失敗するとデプロイは実行されません）。PR でも CI が実行されます。dev でも見た目・動作の確認をしましょう。
  • CloudFront は変更反映に数分〜十数分かかることがある。表示が古い時はブラウザを強制更新（Ctrl+F5）。
  • S3 のバケット名は世界で一意。新しい環境や名前を足す時は名前衝突に注意。
  • 現在ホーム画面に出ている「デプロイテスト」バナーは検証用。本番運用前に削除予定。
豆知識：本プロジェクトの GitHub OIDC のトークンは「不変ID付き」形式（repo:owner@ID/repo@ID:...）です。IAMロールの信頼ポリシーは両形式に対応済みなので、通常は意識不要です。

7. 仕組みを理解するための重要ファイル

ファイル役割まず見るポイント
.github/workflows/deploy.yml CD（デプロイ）の定義 develop / main への push で起動。checks（品質ゲート）を needs し、成功後に Determine stage → OIDC認証 → cdk deploy Michishiru-<stage>。
.github/workflows/checks.yml 共通の品質チェック（再利用ワークフロー） frontend(lint/build) / backend(test) / iac(build/test/synth) の3ジョブ。CI と Deploy の両方から uses で呼ばれる。
.github/workflows/ci.yml CI（PR時のチェック）の定義 develop / main 向け PR で checks.yml を呼び出す。
iac/bin/iac.ts CDKアプリの入口 アカウント/リージョン、Michishiru-dev/Michishiru-prod の生成、withBackend の切替。
iac/lib/michishiru-stack.ts インフラ本体の定義 S3 + CloudFront（フロント配信）、withBackend で Lambda/API Gateway/DynamoDB を追加、バケット名 michishiru-<stage>。
iac/lib/oidc-stack.ts GitHub連携（OIDC）とデプロイロール GitHub Actions が AWS を操作できる仕組み（信頼ポリシー）。
frontend/ Vue 3 のフロントエンド（配信対象） npm run build で dist/ を生成 → S3 へ。
backend/ Lambda 関数のコード（現在は未デプロイ） バックエンド有効化時に withBackend=true で使用。
まず理解すべき順番：①deploy.yml（流れ）→ ②iac/bin/iac.ts（環境の作り分け）→ ③michishiru-stack.ts（何が作られるか）。この3つで「push すると何が起きるか」が分かります。

8. 用語集

GitHub Actions
GitHub 上でコマンドを自動実行する仕組み。.github/workflows/*.yml に定義。
ワークフロー
Actions の1つの自動処理。ここでは「CI」と「Deploy」の2つ。
AWS CDK
インフラ（S3やCloudFrontなど）を TypeScript のコードで定義するツール。cdk deploy で構築。
スタック
CDK が作るリソースのまとまり。環境ごとに Michishiru-dev / Michishiru-prod。
S3
ファイル置き場。ここではフロントの成果物（HTML/JS/CSS）を配置。
CloudFront
S3 の前段に立つ配信網（CDN）。公開URLはここのドメイン。キャッシュあり。
OIDC
GitHub と AWS を安全につなぐ認証方式。長期のアクセスキーを持たずに済む。
IAMロール
AWS 上の「権限のまとまり」。GitHub Actions はこのロールを一時的に借りて操作する。
ブートストラップ
CDK を使う前に1回だけ行う土台作り（cdk-hnb659fds-*）。
withBackend
バックエンド（Lambda等）を作るかのスイッチ。現在 false（フロントのみ）。

9. 困ったときは

  • デプロイが赤い（失敗）：Actions タブ → 該当実行 → 失敗ステップのログを確認。Could not load credentials や AssumeRoleWithWebIdentity 系は認証(OIDC/Secret)まわり。
  • 画面に変更が出ない：CloudFront の反映待ち（数分）＋ブラウザ強制更新（Ctrl+F5）。dev/prod で URL が違うので開いている環境も確認。
  • どの環境を見ている？：dev=d29zgbkwje7tko / prod=d1hx5thfn4k5nf。
  • 本番に出したくないものを develop に入れている間は main にマージしない。

不明点は CI/CD 構築担当に確認してください。この資料は現状（フロントのみ自動デプロイ／バックエンド未有効化）を前提にしています。
