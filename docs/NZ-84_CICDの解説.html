1. バックエンドの全体像（push → Lambda / API Gateway）

GitHub に push するだけで、GitHub Actions が自動でビルド・テストし、AWS CDK が AWS へデプロイします。バックエンド有効化後は、フロントに加えて Lambda / API Gateway / DynamoDB も同じ流れで自動作成・更新されます。

公開URLは1つのまま（同一 CloudFront）。/api/* へのリクエストは CloudFront 経由で API Gateway → Lambda → DynamoDB に届きます。フロントと同一オリジンになるため CORS 設定は不要です。

3. Kiro でバックエンドを開発する手順

Kiro には「こういう Lambda を追加して」とやりたいことを伝えれば、命名規則・レイヤー構成・CDK への配線まで規約に沿って作ってくれます。ただし最後に人が検証してコミット・PRするのは変わりません。標準的な流れは次のとおりです。

  1. Kiro に依頼する：例「ルートを削除する Lambda を追加して。DELETE /api/v1/routes/{id} で受ける」
  2. Kiro が2種類のものを作る（ここが肝心 → 詳細は次章）
    • (A) バックエンドのコード：backend/functions/<関数名>/ にレイヤー分割で生成
    • (B) CDK の配線：iac/lib/michishiru-stack.ts に Lambda 定義・API ルート・権限を追記
  3. ローカルで検証（Kiro が代行することも多い）
    • バックエンド：backend/ で npm test
    • インフラ：iac/ で npm run build → npm test → npx cdk synth -c withBackend=true
    • 画面込みの動作確認：ルートで npm run dev（フロント＋ローカルAPIを同時起動）
  4. 作業ブランチにコミット：feature/NZ-<課題番号>-<内容>。コミットは feat(NZ-XX): ○○ の形
  5. develop へ PR → マージで dev 自動デプロイ → dev URL で確認 → develop → main の PR で prod 反映

覚えておくこと：Kiro が「コードを書く」だけでは AWS に Lambda はできません。CDK への配線（B）まで含めて初めてデプロイ対象になります。Kiro に頼むときは「API から呼べるように配線まで」とお願いすると確実です。

Kiro が作るバックエンドのファイル構成（レイヤー分割）

backend/functions/<関数名>/      ← 関数名は camelCase 動詞+名詞（例: getRoute, deleteRoute）
├── handler.js      受付とレスポンス返却だけ（AWSが呼ぶ入口。export const handler）
├── service.js      ビジネスロジック（HTTPに依存しない）
├── repository.js   DynamoDB / 外部API アクセス
├── validator.js    入力チェック（入力が無い関数では省略可）
├── constants.js    環境変数はここだけで読む（process.env）
├── package.json    "name" は kebab-case（getRoute → get-route）
└── __tests__/
    └── service.test.js   ← これが無いと CI で検証されない

呼び出しの向きは handler → service → repository の一方向。テーブル名などの環境依存値は constants.js 経由で受け取り、コードにハードコードしません。

【補足】フォルダ名と package.json の name は書き方が違う

ここは全員がつまずくポイントなので先に説明します。同じ1つの関数なのに、2か所で表記が変わります。

なぜ揃えないの？ → npm がパッケージ名に大文字を許可していないからです。"name": "getConditions" と書くとエラーになります。そのため name だけ、やむを得ず小文字＋ハイフンにします。コードやフォルダは今までどおり camelCase のままでOKです（例外はこの1か所だけ）。

4. Kiro で書いた内容がどう Lambda / API Gateway になるか

ポイントは「コード」と「CDK の定義」の2つがそろって初めて AWS リソースになる、という点です。

backend の
コード
handler など
＋
CDK の定義
michishiru-stack.ts
→
cdk synth
CloudFormation
テンプレート生成
→
cdk deploy
差分を反映
→
Lambda /
API Gateway
作成・更新

CDK の定義（Lambda 1つあたり）は、こんな数行です。

// ① Lambda 関数を定義（論理ID = GetConditionsFunction）
const getConditionsFn = new lambda.Function(this, 'GetConditionsFunction', {
  runtime: lambda.Runtime.NODEJS_LATEST,
  handler: 'functions/getConditions/handler.handler', // ← backend のどのコードを動かすか
  code: backendCode,                                   // ← backend ディレクトリをアップロード
  environment: { CONDITION_TABLE_NAME: conditionTable.tableName },
});
conditionTable.grantReadData(getConditionsFn);          // ② 権限（このテーブルを読める）

// ③ API Gateway に公開パスを生やす
const conditionsResource = v1Resource.addResource('conditions');
conditionsResource.addMethod('GET', new apigateway.LambdaIntegration(getConditionsFn));
「差分から自動で作られる」の“差分”とは？
git のコード差分ではなく、CDK が生成する CloudFormation テンプレートの差分です。cdk deploy が「今デプロイされている状態」と「新しいテンプレート」を比べ、増えた定義は作成・変わった定義は更新・消えた定義は削除します。だから Lambda 定義（上の①〜③）を書かないと、コードだけ置いても Lambda はできません。

5. 既存の変更 / 新規作成 / 削除

ケースやることAWS 上の挙動
既存 Lambda の処理を変更 backend/functions/<関数>/ のコードを編集するだけ 同じ Lambda を更新（in-place）。作り直さない。物理名も維持
新しい Lambda を追加 コード作成 ＋ CDK に Function 定義を追記（＋API ルート・権限） push 時に新規作成
Lambda を削除 CDK から Function 定義（と API ルート）を削除 push 時に削除
論理ID（'GetConditionsFunction' の部分）は変えないこと。同じ論理IDのまま中身を変えれば「更新」ですが、論理IDを変えると CloudFormation は「別物」とみなし、旧 Lambda を削除して新 Lambda を作り直します（置き換え）。DynamoDB テーブルで論理IDを変えるとデータが消えるので特に危険です。
補足：現在 getRoute と getConditions は同じコード資産（backend/ 全体）を共有しています。そのため backend 内のどれか1ファイルを変えると、デプロイ時に両方の Lambda のコードが新しい束へ更新されます（中身は同じソースなので実害なし）。

6. 初心者が押さえるべき CI/CD ポイント

  1. コードだけでは動かない。Lambda は CDK に配線されて初めて作られる（第4章）。「backend にファイルを置いた＝デプロイされる」ではない。
  2. テストが緑じゃないとデプロイされない。push すると checks（build / test / synth）が先に走り、成功したときだけ cdk deploy が実行される。
  3. __tests__/*.test.js が無いと CI で検証されない。backend の CI は node --test "functions/**/__tests__/**/*.test.js"。拡張子は .test.js 固定（.spec は不可）。
  4. synth も CI で走る。iac ジョブが npx cdk synth -c withBackend=true を実行するので、CDK の書き間違いはマージ前に検知できる。
  5. ブランチ＝環境。develop は dev、main は prod。マージ＝その環境へデプロイ。develop / main への直接 push は禁止、必ず PR。
  6. 環境変数は constants.js 経由。テーブル名などは CDK が environment で渡し、コードは constants.js でだけ process.env を読む。ハードコードしない。
  7. DynamoDB の初期データ。新しいテーブルは空なので、必要なら backend/ で npm run seed を実行して投入する（本番テーブルへの手動操作は避け、スクリプト経由で）。
  8. 物理名は自動生成 & 東京リージョン。コンソールで見つからない時は、まずリージョンが東京か、次に Deploy ワークフローが成功しているかを確認。
  9. API は同一オリジンで叩く。フロントは絶対URLではなく相対パス /api/v1/... を使う。これで Lambda / API Gateway の名前や URL が変わっても追従不要。

7. 注意点（必読）

やってはいけないこと
  • michimaster テーブルを削除しない（getConditions が参照。消すと壊れる）。
  • cdk-hnb659fds-assets-... バケットを削除しない（CDKデプロイの土台）。
  • スタックが管理する S3 / Lambda / API Gateway / DynamoDB を手動で変更・削除しない（コードと実体がズレる。変更は CDK 経由で）。
  • CDK の論理IDを後から変えない（置き換え＝削除＆再作成が起きる）。
  • GitHub Secret AWS_DEPLOY_ROLE_ARN を消さない／名前を変えない。
気をつけること
  • main へのマージ＝本番デプロイ。dev で確認してから。バックエンド有効化後は本番にも Lambda / API Gateway / DynamoDB が作られる。
  • API Gateway は現状「未認証」で公開される（認証は未決定事項）。誰でも /api/* を叩ける点に留意。
  • michimaster は dev / prod 共通の名前を参照している。prod に同名テーブルが無いと prod の getConditions だけ失敗する（分離するなら Condition-<stage> 化が必要）。
  • CloudFront は反映に数分〜十数分かかることがある。古い表示は Ctrl+F5。

8. 重要ファイル

ファイル役割まず見るポイント
backend/functions/<関数>/ Lambda のコード（レイヤー分割） handler.js が入口。service→repository の順に処理。
iac/lib/michishiru-stack.ts インフラ本体の定義 withBackend 内で Lambda / API Gateway / DynamoDB を定義。新規 Lambda はここに配線。
iac/bin/iac.ts CDKアプリの入口 アカウント/リージョン、Michishiru-dev/prod の生成、withBackend の切替。
.github/workflows/deploy.yml CD（デプロイ） develop / main への push で起動。checks 成功後に cdk deploy Michishiru-<stage> -c withBackend=true。
.github/workflows/checks.yml 共通の品質チェック（再利用） frontend(lint/build) / backend(test) / iac(build/test/synth) の3ジョブ。
.github/workflows/ci.yml CI（PR時のチェック） develop / main 向け PR で checks.yml を呼ぶ。
tools/localApiServer.js ローカル開発用の API ハーネス npm run dev で /api/* を Lambda ハンドラへ橋渡し。新 API はここにも登録。
理解する順番：①deploy.yml（流れ）→ ②michishiru-stack.ts（何が作られるか・どう配線するか）→ ③backend/functions（中身）。

9. 用語集

CI / CD
push で自動ビルド・テスト（CI）／自動デプロイ（CD）する仕組み。
AWS CDK
インフラを TypeScript で定義するツール。cdk deploy で構築。
スタック
CDK が作るリソースのまとまり。環境ごとに Michishiru-dev/prod。
論理ID
CDK 上のリソース名（例 GetConditionsFunction）。変えると置き換えが起きる。
物理名
AWS 上の実際の名前。指定しないと CDK が自動生成する。
Lambda

DynamoDB

synth
CDK コードから CloudFormation テンプレートを生成すること。
withBackend

seed
DynamoDB に初期データを投入すること（npm run seed）。

10. 困ったときは

  • API Gateway / Lambda がコンソールで見つからない：①リージョンが東京(ap-northeast-1)か、②アカウントが 961308088333 か、③Deploy ワークフローが成功しているか（最後の「スタックの出力を表示する」に ApiEndpoint が出る）を確認。
  • デプロイが赤い（失敗）：Actions タブ → 失敗ステップのログ。AssumeRoleWithWebIdentity 系は認証(OIDC/Secret)、synth 失敗は CDK の記述ミス。
  • API が 503 / データが出ない：参照先テーブルの有無を確認（getConditions は michimaster、getRoute は Route-<stage>）。テーブルが空なら npm run seed。
  • 画面に変更が出ない：CloudFront の反映待ち＋Ctrl+F5。dev/prod で URL が違う点も確認。

不明点は CI/CD 構築担当に確認してください。この資料は現状（バックエンド有効化済み・API は未認証で公開・michimaster は既存テーブル参照）を前提にしています。
