# ルート生成方式検証 実装説明書

条件（ジャンル・距離・現在地）から散歩ルートを自動生成し、GeoJSON としてフロントエンドへ返して地図へ描画する方式の検証内容をまとめる。

Amazon Location Service と Amazon Bedrock を使う方式を採るかどうかは未確定であり、本書は**方式を確定させるための検証**を2段階に分けて記述する。

| 項目 | 内容 |
|---|---|
| 対象 | US-2（ルート作成処理）、US-3（ルート提案モーダル）の地図描画部分 |
| 作業ブランチ | `test/kato-case`（作業用。自動デプロイ対象外） |
| 現在の状態 | **段階1a 完了。**ブラウザでルート線・スポット・現在地の描画を確認済み。段階1b は未着手 |
| AWSへの影響 | なし（段階1a はリソースを作らず、AWS を呼ばない） |

---

## 1. 全体像

### 想定する処理フロー

```
[フロントエンド]
  条件（genre / distance / lat / lng）
        │  POST /api/v1/routes
        ▼
[Handler]     リクエスト受付・バリデーション
        ▼
[Service]     呼び出し順序の制御・距離調整の判断・GeoJSON組み立て
        ▼
[Repository]  ① 検索キーワード取得（検索条件マスタ）
              ② 周辺スポット検索（Location Service Places）
              ③ スポット選定とコース名生成（Bedrock）
              ④ 徒歩ルートの距離計算（Location Service Routes）
        ▼
[Service]     実測距離が目標を大幅超過 → 末尾スポットを削って ④ を再実行
        ▼
  GeoJSON（FeatureCollection）を含むレスポンス
        │
        ▼
[フロントエンド]  MapLibre GL へそのまま渡して描画
```

### レイヤーの責務

`back-layer-architecture.md` の3層構成に沿って配置する。外部サービスの呼び出しをすべて Repository に閉じ込める点が要である。

| レイヤー | ファイル | 担当 |
|---|---|---|
| Handler | `handler.js` | リクエストボディの解析、バリデーター呼び出し、レスポンス整形 |
| Validator | `validator.js` | `genre` / `distance` / `lat` / `lng` の型・必須・範囲チェック（純粋関数） |
| Service | `service.js` | Repository の呼び出し順序、距離調整の判断、GeoJSON の組み立て |
| Repository | `repository.js` | 検索条件マスタ・Location Service・Bedrock へのアクセス |

`ミチシル_前提条件.md` の「外部APIの呼び出しは Lambda（Repository層）から行う」に従い、地図APIとAIの呼び出しはすべて Repository に置く。フロントエンドから直接呼ばないため、認証情報がブラウザへ出ない。

## 2. API仕様

### エンドポイント

| 項目 | 内容 |
|---|---|
| メソッド・パス | `POST /api/v1/routes` |
| 成功時ステータス | 201 |
| Lambda論理名 | `generateRoute`（`backend/functions/generateRoute/`） |

既存の `GET /api/v1/routes`（`getRoute`）はDBに登録済みのルートを取得する処理で、条件から生成する本APIとは別物である。同じパスでメソッドが異なるため共存でき、REST としても「取得」と「作成」の区別が自然に表現できる。

### リクエスト

```json
{
  "genre": "nature",
  "distance": 3,
  "lat": 35.681236,
  "lng": 139.767125
}
```

| キー | 型 | 説明 |
|---|---|---|
| `genre` | String | ジャンル。必須 |
| `distance` | Number | 目標距離（km）。1〜10 の範囲。必須 |
| `lat` | Number | 現在地の緯度。必須 |
| `lng` | Number | 現在地の経度。必須 |

`distance` に単位を付けないのは、`naming-conventions.md` の「例外: API のリクエスト/レスポンスのキーは `distance`（km固定）とする」に従うため。フロントエンド内部では `distanceKm` を使い、サービス層で変換する。

`purpose`（目的）は含めない。develop で目的の選択自体が削除され、`routeStore` からも除去されているため（合意済み）。

### レスポンス

```json
{
  "routeId": "9f1c...",
  "routeName": "自然をたどる3スポットコース",
  "story": "大手町の森、KITTE屋上庭園、和田倉噴水公園をめぐります。",
  "distance": 2.28,
  "duration": 34,
  "spotCount": 3,
  "origin": { "lat": 35.681236, "lng": 139.767125 },
  "spots": [
    {
      "spotId": "...",
      "name": "大手町の森",
      "spotType": "park",
      "lat": 35.687,
      "lng": 139.7645,
      "description": "緑が多く、腰を下ろして休める場所です。"
    }
  ],
  "geojson": { "type": "FeatureCollection", "features": [] }
}
```

### GeoJSON の構造

**1つの FeatureCollection にルート線・出発地・スポットをまとめる。** フロントエンドはこれを加工せずそのまま地図ライブラリへ渡し、`properties.featureKind` で描画を振り分ける。

| featureKind | geometry | 個数 | properties |
|---|---|---|---|
| `route` | LineString | 1 | - |
| `origin` | Point | 1 | `name` |
| `spot` | Point | 1〜3 | `spotId` / `name` / `spotType` / `visitOrder` |

LineString の座標列が用語辞書の `waypoint`（経路を描くための座標の点）に相当する。ユーザーが立ち寄る `spot` とは別概念であり、両者を別の feature として分けている。

**座標は `[経度, 緯度]` の順で持つ。** GeoJSON の仕様であり、アプリ内で扱う `{ lat, lng }` とは順序が逆になる。Service 層の `toGeoJsonPosition` でのみ入れ替え、他の場所では変換しない。

#### spot と waypoint を分けた理由

`naming-conventions.md` の未決定事項 #2 に挙がっている負債への対応である。既存の `getRoute` は `waypoints` しか返さないため、US-8 の「廻ったスポット数」を数えるときに経路の折れ点まで数えてしまう危険がある。実際、3スポットのルートで LineString は49点になる。ここを混同すると `spotCount` が `3` ではなく `49` と表示され、**エラーにならず数字だけが狂う**ため気付きにくい。

新規実装では最初から `spots`（配列）と `spotCount`（数値）を独立して返し、経路の点は GeoJSON の中だけに閉じ込める。

## 3. 段階を2つに分けた理由

方式が未確定な段階で、いきなり AWS リソースを作って実装すると次の3つの問題が起きる。

**dev / prod 環境への影響を切り離せない。** `deploy.yml` は `develop` / `main` への push で `Michishiru-dev` / `Michishiru-prod` をデプロイする。検証用のリソースを既存スタックへ足すと、方式を採用しなかった場合に取り消す作業が必要になる。CDK のリソースは論理ID を変えるとリソースが再作成されるため、追加と削除を繰り返すのは事故の温床である。

**検証したい2つのことが混ざる。** 今回確かめたいのは「GeoJSON をフロントエンドへ渡して地図に描けるか」と「Location Service と Bedrock を組み合わせて実用的なルートが作れるか」の2点である。前者はフロントエンドとAPI契約の問題で、後者はAWSサービスの精度・応答時間・費用の問題であり、原因の切り分けが必要な性質が違う。同時に着手すると、地図が出ないときに契約の問題かAWS側の問題か判断できない。

**AWS の資格情報とモデル利用の準備が前提条件になる。** ローカルには AWS の資格情報が設定されていない（`aws sts get-caller-identity` が `NoCredentials` を返す）。ここが整うまで待つと、資格情報と無関係に進められるフロントエンドの実装も止まる。

そこで**「AWS を1回も呼ばない範囲」と「AWS を呼ぶ範囲」で切った。**

| | 段階1a | 段階1b |
|---|---|---|
| 確かめること | GeoJSON の契約と地図描画 | AWSサービスの精度・応答時間・費用 |
| AWSへの接続 | なし | あり（ローカルの資格情報で呼ぶ） |
| 作成するAWSリソース | なし | なし |
| 前提条件 | なし | 資格情報 + IAM権限 |
| 発生する費用 | なし | Bedrock と Location Service の API 利用分 |

段階1a と 1b のどちらも**AWSリソースを作らない**点が重要である。CloudFormation スタックに差分が出ないため、dev / prod への影響は「小さい」ではなく物理的に発生しない。

### 段階2以降との関係

方式を採用する判断になった後の流れも整理しておく。

| 段階 | AWSリソース | デプロイ方法 | 自動デプロイ |
|---|---|---|---|
| 1a | 作らない | なし（ローカル実行のみ） | 無関係 |
| 1b | 作らない | なし（ローカル実行のみ） | 無関係 |
| 2 | 検証用スタックを別に作る | 手動（ローカルから `cdk deploy`） | 対象外 |
| 3（本採用） | `MichishiruStack` に統合 | GitHub Actions | ここで初めて対象になる |

段階2 が自動デプロイの対象外になるのは、`deploy.yml` がスタック名を明示してデプロイしているためである。

```
npx cdk deploy "Michishiru-${{ steps.vars.outputs.stage }}"
```

`Michishiru-dev` / `Michishiru-prod` 以外の名前のスタックはパイプラインが触らない。スタック名は `iac-rules.md` の「環境に依存しないスタックは `Michishiru<用途>Stack`」に従う。

ただし `checks.yml` の最終ステップが引数なしの `npx cdk synth` で**全スタックを合成する**ため、`bin/iac.ts` へ検証用スタックを追加した状態で develop へマージすると、合成に失敗した場合にデプロイの品質ゲートで止まる。リソースには影響しないがパイプラインには影響しうる。既存の `withBackend` と同じく context フラグで囲むか、検証ブランチに留めることで回避する。

## 4. 段階1a: AWS を呼ばずに GeoJSON 描画を確認する

### 実装する処理

| 対象 | 内容 |
|---|---|
| `backend/functions/generateRoute/` | Handler / Validator / Service / Repository / constants の5ファイル |
| `tools/localApiServer.js` | `POST /api/v1/routes` の登録と、リクエストボディの読み取り追加 |
| `frontend/src/services/routeService.js` | `generateRoute` の追加 |
| `frontend/src/composables/useRouteGeneration.js` | 生成状態の管理 |
| `frontend/src/components/feature/route/RouteGeoJsonMap.vue` | GeoJSON の描画 |
| `frontend/src/views/RouteGenerationSpikeView.vue` | 検証用画面 |
| `frontend/src/router/index.js` | 検証用画面のルート定義（`/spike/route-generation`） |
| `frontend/vite.config.js` | `maplibre-gl` を依存最適化の対象から除外（後述） |

### Repository を「差し替え口」として設計する

段階1a の Repository は固定データを返すが、**関数の入出力を段階1b で呼ぶ外部サービスに合わせておく。** これにより段階1b では Repository の中身だけを書き換え、Service より上を変更せずに済む。

| 関数 | 段階1a | 段階1b での実体 |
|---|---|---|
| `getSearchKeywords` | `constants.js` の対応表を返す | DynamoDB の検索条件マスタ |
| `searchNearbySpots` | 東京駅周辺18件から絞って返す | Location Service Places（`SearchNearby`） |
| `selectSpotsByAi` | 候補から3件選びテンプレートで文言生成 | Bedrock（`InvokeModel`） |
| `calculateWalkingRoute` | 座標を補間して距離を算出 | Location Service Routes（`CalculateRoutes`） |

`calculateWalkingRoute` の固定実装は、出発地とスポットを結ぶ各区間に12点の中間座標を生成し、進行方向に対して横へわずかにずらして曲線に見せている。直線で結ぶと道なりの形にならず、地図描画の確認材料にならないためである。距離はその座標列に対する球面距離の合計とする。

### ローカルでの動かし方

`tools/localApiServer.js` は Lambda ハンドラを Node のプロセス内で直接 import して呼ぶ仕組みで、`ROUTE_HANDLERS` にメソッドとパスとハンドラの対応を並べるだけでエンドポイントが増える。`frontend/vite.config.js` が `/api` を同ハーネス（ポート3001）へプロキシするため、リポジトリルートで `npm run dev` を実行すればフロントエンドから呼べる。

既存のハーネスは `GET` のみを想定してリクエストボディを読んでいなかったため、ボディを文字列として読み切る処理を追加し、API Gateway と同じく `event.body` へ文字列で渡す形にした。

### 地図描画: ベースマップを使わない

`RouteGeoJsonMap.vue` は MapLibre GL に**空のスタイル**を与え、背景色のみのレイヤーの上に GeoJSON を描く。

```javascript
const BLANK_STYLE = {
  version: 8,
  sources: {},
  layers: [{ id: 'background', type: 'background', paint: { 'background-color': '#eef3f6' } }]
};
```

地図タイルの配信には認証（Location Service の API キー等）が必要で、そのキーはブラウザへ露出する。ルート線とスポットの位置関係を確かめるだけなら不要なため、段階1a では持ち込まない。ベースマップは段階1b 以降に足す。

**文字を描く `symbol` レイヤーも使わない。** MapLibre で `text-field` を使うにはフォント（glyphs）の配信元が必要になるため、スポット名と立ち寄り順のラベルは `maplibregl.Marker` に DOM 要素を渡して表示する。線と円は GeoJSON ソースから `line` / `circle` レイヤーで描き、`filter` で `featureKind` を振り分ける。

### 段階1a で確認できたこと

| 確認項目 | 結果 |
|---|---|
| 正常系 | 201 を返し、FeatureCollection に5 feature（線1・出発地1・スポット3）が入る |
| 経路の座標数 | 3スポットのループで LineString 49点 |
| 距離と所要時間 | 目標3km に対し実測2.28〜3.55km / 34〜53分（ジャンルにより変動） |
| 距離調整の発火 | 目標1km 指定でスポットが3件→1件へ削減され、25点のルートになる |
| 異常系 | 不正値で 400 を返し、複数のエラーメッセージを連結して返す |
| 座標の並び順 | 先頭座標が `[139.767125, 35.681236]` で `[経度, 緯度]` 順になっている |
| Vite プロキシ経由の疎通 | `POST /api/v1/routes` が 201 + `application/json` を返す |
| 画面描画 | ブラウザでルート線（緑）・スポット（橙＋ラベル）・現在地（青）が描画される |
| 品質チェック | `frontend` の lint とビルド、`backend` のテスト10件がすべて通過 |

**GeoJSON をそのままフロントエンドへ渡して地図に描けることを確認できたため、段階1a の目的は達成した。**

### develop の変更を受けた修正（適用済み）

段階1a の実装後に develop が3コミット進み、`test/kato-case` へマージした。以下を適用済みである。

| ファイル | 修正内容 |
|---|---|
| `validator.js` | `purpose` の検証を削除 |
| `constants.js` | `ALLOWED_PURPOSES` を削除。コース名のテンプレートを目的別からジャンル別へ差し替え |
| `repository.js` | `selectSpotsByAi` の引数から `purpose` を除去 |
| `service.js` | `generateRoute` の引数から `purpose` を除去 |
| `routeService.js` | リクエストボディから `purpose` を除去し、`isJsonResponse` の判定を追加 |

`isJsonResponse`（`frontend/src/utils/apiResponse.js`）は、API が未配線の環境で SPA の `index.html` が 200 で返るケースを解析前に弾く共通処理で、`fetchRoute` と `fetchConditionOptions` の両方で使われている。新設した `generateRoute` も同じ作法に揃えた。

`purpose` の残骸がないことは全文検索で確認済み（`generateRoute` 配下および追加したフロントエンドのファイルで0件）。

### MapLibre の導入でつまずいた3点

同じ罠を踏まないよう記録する。**いずれも症状が「無言で描画されない」ため原因が分かりにくい。**

#### 1. default エクスポートが存在しない（ビルドが失敗する）

`maplibre-gl` の6系は ESM で default エクスポートを持たない。

```javascript
// 失敗する: [MISSING_EXPORT] "default" is not exported by maplibre-gl.mjs
import maplibregl from 'maplibre-gl';

// 正しい書き方（Map は Vue 側の名前と衝突しうるためリネームする）
import { LngLatBounds, Map as MapLibreMap, Marker, NavigationControl } from 'maplibre-gl';
```

こちらはビルドエラーになるため気付ける。

#### 2. Vite の依存最適化が Web Worker を壊す（描画されない）

MapLibre は GeoJSON の解析を Web Worker で行うが、Vite の依存最適化を通すと Worker のファイルが見つからなくなる。

```
The file does not exist at ".../node_modules/.vite/deps/maplibre-gl-worker.mjs"
which is in the optimize deps directory.
```

`frontend/vite.config.js` で除外する。設定後は依存最適化のキャッシュ（`node_modules/.vite`）を削除して開発サーバを再起動する必要がある。

```javascript
optimizeDeps: {
  exclude: ['maplibre-gl']
}
```

**Worker が読めないと GeoJSON ソースが読み込まれず、それを参照する `line` / `circle` レイヤーが何も描かない。**一方 `Marker` は DOM 要素なので影響を受けず表示される。「ラベルだけ出て線と丸が出ない」という症状になる。

#### 3. リアクティブな値をそのまま渡せない（描画されない）

MapLibre は GeoJSON を Worker へ `postMessage` で渡すため構造化複製（structured clone）が行われる。Vue のリアクティブ Proxy は構造化複製できず `DataCloneError` になる。

| 渡す値 | 構造化複製 |
|---|---|
| 素のオブジェクト | 成功 |
| `reactive(obj)` | **失敗**（DataCloneError） |
| `ref(obj).value` | **失敗**（DataCloneError） |
| `shallowRef(obj).value` | 成功 |
| `toRaw(ref(obj).value)` | 成功 |

対策を2段構えにした。

- `useRouteGeneration` の `generatedRoute` を `shallowRef` にする。中身を部分的に書き換えることはなく常に全体を差し替えるため、浅い参照で足りる
- `RouteGeoJsonMap` 側でも `toRaw()` で素の値へ戻してから渡す。呼び出し元の実装に依存しないようにする

あわせて `map.on('error', ...)` を追加した。**MapLibre の失敗は例外にならずこのイベントへ流れるため、リスナーが無いと無言で描画されないだけになる。**

## 5. 段階1b: AWS の実サービスへ差し替える

### 実装する処理

Repository の4関数の中身を実サービスの呼び出しへ置き換える。Service より上は変更しない。

| 処理 | 使うサービス | 概要 |
|---|---|---|
| 検索キーワード取得 | DynamoDB（検索条件マスタ） | ジャンルに対応する英語の検索語を取得する |
| 周辺スポット検索 | Location Service Places | 現在地周辺の実在スポットを15〜20件取得する |
| スポット選定と文言生成 | Bedrock | 候補から2〜3件を選び、コース名と紹介文を JSON で出力させる。**呼び出しは1回のみ** |
| ルート距離計算 | Location Service Routes | 現在地を発着とする徒歩周回ルートの実距離と所要時間を求める |

### AI の呼び出しを1回に抑える理由

条件に合うスポットの選定と、コース名・紹介文の生成を1回のプロンプトでまとめて行う。呼び出し回数がそのまま費用と応答時間に効くためである。

距離が目標を超過した場合も**AI を呼び直さない。** Service 層で末尾のスポットを配列から取り除き、ルート計算のみ再実行する。AI の再呼び出しに比べて速く、費用も増えない。削減の判断は `DISTANCE_OVERSHOOT_RATIO`（目標の1.25倍）で行い、`MIN_SPOT_COUNT` を下回るまでは削らない。

### 作成する AWS リソースはない

段階1b で新しく作るリソースは1つもない。調査した結果、必要なのは**Lambda 実行ロールの IAM 権限だけ**である。

**Location Service の Places / Routes は API v2 でリソースが不要になった。** v1 の place index / route calculator を事前に作る必要はなく、v2 は簡素化されたインターフェースでリソースの作成・管理なしに使える。v1 は将来的に非推奨になる可能性がある（[CalculateRoute API リファレンス](https://docs.aws.amazon.com/location/previous/APIReference/API_CalculateRoute.html)、[create-place-index CLI リファレンス](https://docs.aws.amazon.com/cli/latest/reference/location/create-place-index.html)）。SDK 上のクライアントも `location` ではなく `geo-places` / `geo-routes` になる。

**Bedrock も基盤モデルの利用申請が基本的に不要である。** AWS Marketplace の権限が揃っていればモデルアクセスは既定で有効になっている（[Request access to models](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)）。

（上記の内容はライセンス上の制約に配慮して要約・言い換えている）

したがって規約面でも有利に働く。`ミチシル_前提条件.md` の「外部API利用時のルール」はAPIキーの管理を主眼にしているが、Bedrock と Location Service v2 は IAM ロールで認証するためキーそのものが存在せず、Secrets Manager も不要になる。

| `backend/` | `@aws-sdk/client-geo-places` / `@aws-sdk/client-geo-routes` / `@aws-sdk/client-bedrock-runtime` |

SDK のクライアント名が `location` ではなく `geo-places` / `geo-routes` なのは、Places / Routes が API v2 で別サービスとして分かれたため。

#### モデルの候補（`ap-northeast-1` で利用可能なもの）

用途は「候補スポットのリストから2〜3件を選び、コース名と紹介文をJSONで出力する」で、長文生成ではない。応答時間と費用を優先して軽量なモデルから試すのが妥当と考えられる。

| モデルID | 想定 |
|---|---|
| `anthropic.claude-haiku-4-5-20251001-v1:0` | 軽量・高速。第一候補 |
| `amazon.nova-2-lite-v1:0` | 同じく軽量。費用面の比較対象 |
| `anthropic.claude-sonnet-4-6` | 選定の質が足りない場合の引き上げ先 |

モデルIDは `constants.js` で環境変数から受け取る形にし、コードに直接書かない（`back-layer-architecture.md` の「環境変数の参照は `constants.js` に集約する」に従う）。

`ap-northeast-1` で直接呼べないモデルを選ぶ場合はクロスリージョン推論プロファイルを使うことになり、**IAMポリシーに書くARNの形式が変わる。**これは `AccessDeniedException` の典型的な原因である。

### 段階1b で測るもの

方式の採否を判断するための材料を得ることが目的である。

| 観点 | 理由 |
|---|---|
| 応答時間 | Places → Bedrock → Routes（+ 超過時の再計算）が直列に並ぶ。API Gateway の統合タイムアウトは29秒が上限で、超える場合は非同期化が必要になり構成が変わる |
| 1リクエストあたりの費用 | Bedrock と Location Service の課金がユーザー操作1回ごとに発生する。再作成（US-5）で繰り返し呼ばれる点も含めて見積もる |
| スポット選定の妥当性 | AI が条件に合う場所を選べているか。散歩として成立する組み合わせになるか |
| 距離の収まり | 目標距離に対する超過の頻度と、末尾削除による調整が実用的に効くか |

## 6. 規約に準拠したポイント

- **レイヤー構成**（`back-layer-architecture.md`）
  - Handler はリクエスト受付とレスポンス返却のみ。ビジネス判断を持たない
  - Service は HTTP に依存せず、プレーンなオブジェクトを受け取って返す
  - 外部サービスの呼び出しは Repository に閉じ込める
  - Validator は純粋関数（データ取得・副作用なし）
- **ファイル名**（`back-lambda-rules.md`）
  - レイヤーファイルは役割名で固定（`handler.js` / `service.js` / `repository.js` / `validator.js`）
  - 機能名はフォルダ名（`functions/generateRoute/`）で表現する
  - `package.json` の `name` は `generate-route`（npm がパッケージ名に大文字を許可しないため）
- **命名**（`naming-conventions.md`）
  - Lambda 論理名は camelCase の動詞+名詞（`generateRoute`）
  - APIパスは `/api/v1/routes`（バージョン付き・複数形）
  - JSONキーは camelCase。距離は API 境界のみ `distance`、内部は `distanceKm`
  - Boolean は `isGenerating` / `hasGeneratedRoute`
  - Vueコンポーネントは PascalCase 2語以上（`RouteGeoJsonMap.vue`）、composable は `use` + camelCase
- **ディレクトリ配置**（`directory-structure.md`）
  - API通信 → `services/`、リアクティブなロジック → `composables/`、表示 → `components/feature/route/`
  - 検証用画面は URL を持つため `views/`
- **props / emit の書き分け**（`component-design.md`）
  - 宣言は camelCase、テンプレートの属性は kebab-case
  - props は `required` または `default` を必ず指定する
- **アクセシビリティ**：読み込み中に `role="status"`、失敗メッセージに `role="alert"`、地図に `aria-label`
- **JSDoc**：Handler / Service の公開関数 / Repository の関数に `@description` / `@param` / `@returns` / `@throws` を記載

## 7. 未対応・申し送り

- **【後で考慮】立ち寄り順が地理的に最適化されないため、ルートが自己交差する。**
  段階1a では候補配列から順に3件取るだけなので、現在地→スポット1→2→3→現在地を結ぶと線が交差する。**段階1bでAIに順序を任せた場合も同じ問題が起きうる。**プロンプトで「移動距離が短くなる順に並べる」と指示するか、選定後にプログラム側で並べ替えるかを決める必要がある。距離の計算にも影響するため、段階1bの実測前に方針を決めておくのが望ましい。
- **【後で考慮】目標距離を下回るケースがある。**
  目標3km に対しジャンル「街歩き」で 0.88km になった。距離調整は超過時にスポットを削る方向にしか働かず、不足時に伸ばす処理がない。ご提示のフロー（案1）どおりの挙動だが、実用上は下振れの扱いを決める必要がある。段階1bで実サービスに繋いだときの分布を見て判断する。
- **【未決定】ベースマップを表示するかどうか。**
  段階1a は地図タイルを使わず、灰色の背景に GeoJSON のみを描いている。タイル配信には認証が必要で、キーがブラウザへ露出するためである。選択肢は下表のとおり。

  | 方法 | 認証 | 詳細度 | 備考 |
  |---|---|---|---|
  | OpenStreetMap のラスタタイル | 不要 | 街路レベル | 第三者サーバへのリクエストが発生。著作権表示が必要。タイル利用ポリシー上、開発時の軽い利用向け |
  | MapLibre の公式デモタイル | 不要 | 世界地図レベル | ズーム14では実用にならない |
  | Amazon Location Service の地図 | APIキー必要 | 街路レベル | 本採用時の想定。キーに利用制限をかける前提 |

- **バンドルサイズが増えた。** `maplibre-gl` の導入で `dist/assets/index-*.js` が約1.1MB（gzip 302kB）になり、Vite が500kB超の警告を出している。動作に支障はないが、本採用時は地図コンポーネントを動的 `import()` で分割する余地がある。
- **【要確認】ルート作成の失敗時に画面から復帰できない。**
  develop の `RouteConditionView.vue` は `useRouteCreation` から `errorMessage` を受け取っておらず、`createRoute` が失敗しても `isCreating` が解除されない。結果としてロード画面のまま原因も表示されず、リロード以外に復帰手段がない。`BaseToast` は条件未選択の通知にのみ使われている。「応答を待ち続ける」意図的な仕様だとしても出口が必要と考えられるため、NZ-1 の担当者へ確認が必要。
- **用語辞書への追記は未実施。** 方式が未確定の段階で共有辞書へ手を入れるのは順序が逆であり、辞書の変更はチーム全員への通知と `docs` 種別の独立したPRが必要なため、方式確定時にまとめて出す。追記が必要な語は下表のとおり。
- **フロントエンドのテストは未実装**（未決定事項 #4 によりテストツール未定）。バックエンドのテストも検証段階のため未作成。方式が確定して本採用へ進む段階で、`validator.js` と `service.js`（距離調整・GeoJSON組み立て）にテストを追加する。
- **`purpose` 削除と要件定義の不整合。** `ミチシル_前提条件.md` の US-1 は「目的を１つ選択できるボタンがあること」を受け入れ条件に挙げており、develop の変更と食い違っている。実装側の合意は取れているとのことなので、要件定義側の更新が必要。
- **検証用画面とルート定義は本採用時に削除する。** `RouteGenerationSpikeView.vue` と `/spike/route-generation` のルート定義は検証専用であり、既存のルート作成フローへ統合する際に破棄する。
