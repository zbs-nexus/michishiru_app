画面遷移（追加後）

[ログイン画面 /login] ← 未ログインの場合、どのURLを開いてもここへ送られる │ │ ユーザー名 + パスワード → Cognito が認証 ▼ [ホーム画面 / (US-1)] │ │ ルート作成ボタン押下 ▼ [ロード画面 (US-2)] → [ルート提案 (US-3)] → [案内 (US-6)] → [散歩結果 (US-8)]

2. 設計方針（着手前に目を通すところ）

2-1. ホストされたログイン画面（マネージドログイン）を使わない理由

Cognito には Cognito 側がホストするログインページ（マネージドログイン、旧ホストUI）があります。今回は使いません。

観点 マネージドログイン 自前のログイン画面（今回採用）
見た目 Cognito のドメインの画面へ遷移する。カスタマイズに制限あり ミチシルの画面としてそのまま作れる
実装量 少ない（リダイレクトのみ） 入力欄とエラー表示を自分で作る
認証方式 OIDC のリダイレクト（認可コード + PKCE） SRP（パスワードを送信せずに認証）
クリア条件との相性 「ログイン画面」が別ドメインの画面になる アプリ内の画面として表示できる

2-2. 使用ライブラリ

aws-amplify の認証モジュール（aws-amplify/auth）を使います。SRP の計算、トークンの保存、 有効期限切れ時の自動更新までライブラリが行うため、自分で書く部分がログイン画面とエラー表示だけになります。

⚠️ 「Amplify は使わない」という前提条件との関係

ミチシル_前提条件.md の「Amplify は使わない」はホスティングと CI/CD（AWS Amplify のサービス）を指しています。 今回入れるのは npm パッケージの認証ライブラリだけで、ホスティングは S3 + CloudFront のままです。 Amplify CLI の初期化（amplify init）も行いません。レビューで指摘されやすい点なので、PR の説明にこの一文を添えてください。

2-3. ユーザープールIDとアプリクライアントIDをフロントに置いてよいのか

置いてよい値です。どちらも公開前提の識別子で、シークレットではありません。ログインページの HTML を見れば分かる情報であり、 これを知っていてもユーザー名とパスワードが無ければ認証は通りません。

一方でクライアントシークレットは絶対にフロントへ置けません。今回は SPA 用のアプリクライアント（シークレットなし）を作るため、そもそも発行されません。 前提条件書の「APIキー・シークレットをフロントに埋め込まない」に抵触しない構成です。

2-4. 責務の置き場所

LoginView.vue 画面の組み立てと、成功後のホームへの遷移 └ LoginForm.vue 入力欄。認証は行わず、入力値を emit するだけ stores/authStore.js ログイン状態の保持（画面をまたぐためPinia） services/authService.js Cognito との通信と、例外→日本語メッセージの変換 router/index.js 未ログインのアクセスを /login へ送る判定

3. 第1部: AWS コンソールでの作成手順

前提

リージョンは アジアパシフィック（東京）ap-northeast-1 を使います（既存リソースと同じ）。 コンソール右上のリージョンが東京になっているか、作業前に必ず確認してください。 必要な権限は AmazonCognitoPowerUser 相当です。

1
ユーザープールを作成する
  1. コンソールで「Cognito」を検索して開き、左メニューの ユーザープール を選ぶ
  2. ユーザープールを作成 を押す
  3. アプリケーションの定義
    • アプリケーションタイプ: シングルページアプリケーション (SPA) を選ぶ
      重要 これを選ぶとクライアントシークレット無しのアプリクライアントが作られます。後から変更できません。
    • アプリケーションの名前: michishiru-web-dev
  4. オプションの設定
    • サインイン識別子のオプション: ユーザー名 のみを選ぶ（クリア条件が「ユーザー名とパスワード」のため）
    • サインアップの必須属性: email を選ぶ
      ユーザー名でサインインする場合、パスワード再設定のコード送信先として email または電話番号が必要になります。
  5. リターンURLを追加: http://localhost:5173 と入力する
    自前のログイン画面ではリダイレクトを使わないため実際には未使用ですが、ウィザードの入力欄なので埋めます（5173 は Vite の既定ポート）。
  6. アプリケーションを作成 を押す
  7. 完了画面でコード例が表示される。下へスクロールして 概要に移動 を押す
⚠️ ウィザードで作ると後から変えられない設定

このクイック作成では、ユーザー名の大文字小文字を区別しない（JohnD と johnd が同一ユーザー）、 preferred_username をエイリアスとして使えない、という設定が固定されます。 変更にはユーザープールの作り直しが必要です。今回の用途では問題ありませんが、本番用に作り直す際は認識しておいてください。

2
アプリクライアントの設定を確認する
  1. ユーザープールの左メニュー アプリクライアント を開き、作成されたクライアントを選ぶ
  2. クライアントシークレットが なし になっていることを確認する
  3. ログインページ／認証フロー の設定で、以下が有効になっていることを確認する
    認証フロー設定理由
    ALLOW_USER_SRP_AUTH有効今回使う方式。パスワードをネットワークに流さない
    ALLOW_REFRESH_TOKEN_AUTH有効再読み込み時のセッション復元に必要
    ALLOW_USER_PASSWORD_AUTH無効のままパスワードを平文で送る方式。SRP があるので不要
3
セルフサインアップを無効にする

コンソールのクイック作成では誰でも自分でアカウントを作れる状態になります。 ミチシルは今のところ管理者がユーザーを登録する運用にするため、閉じておきます。

  1. ユーザープールの サインアップ タブを開く
  2. セルフサービスのサインアップ の 編集 を押す
  3. セルフ登録を有効にする のチェックを外して保存する
4
テスト用ユーザーを作成する
  1. ユーザープールの ユーザー タブ → ユーザーを作成
  2. 招待メッセージ: 招待を送信しない
  3. ユーザー名: michishiru-test
  4. E メールアドレス: 受け取れるアドレス（テストのみなら架空でも可）を入力し、E メールアドレスを検証済みとしてマークする にチェック
  5. パスワード: パスワードを設定 を選び、Michishiru#2026 のように既定のポリシーを満たす値を入れる
    既定のポリシー: 8文字以上／大文字・小文字・数字・記号をそれぞれ1文字以上
  6. ユーザーを作成 を押す

作成直後、このユーザーのステータスは FORCE_CHANGE_PASSWORD（パスワードの変更が必要）です。この状態ではログインが完了しません。続けて Step 5 を行ってください。

5
パスワードを恒久化して CONFIRMED にする（つまずきポイント）

管理者が作ったユーザーのパスワードは「仮パスワード」として扱われ、初回ログイン時に新しいパスワードの設定を要求されます。 今回は初回パスワード変更画面を作らないため、パスワードを恒久パスワードに変えてしまいます。

コンソールの画面上にこの操作のボタンが無いため、CloudShell（コンソール右上のターミナルアイコン）から1行実行します。コンソール内で完結する作業です。 

aws cognito-idp admin-set-user-password \
  --user-pool-id ap-northeast-1_XXXXXXXXX \
  --username michishiru-test \
  --password 'Michishiru#2026' \
  --permanent \
  --region ap-northeast-1

実行後、ユーザー タブを再読み込みし、ステータスが 確認済み（CONFIRMED） になっていることを確認します。

将来やるなら

アプリ側で初回パスワード変更に対応する場合は、signIn の戻り値 nextStep.signInStep が CONFIRM_SIGN_IN_WITH_NEW_PASSWORD_REQUIRED のときに新パスワード入力画面を出し、confirmSignIn を呼びます。今回は範囲外です。

フロントで使う値を控える

/**
 * @description Cognito への接続情報を定義する。
 *
 * ユーザープールIDとアプリクライアントIDは公開前提の識別子であり、シークレットではない。
 * SPA用のアプリクライアントはクライアントシークレットを持たないため、
 * ビルド成果物に含まれても認証を突破する材料にはならない。
 * 環境（dev/prod）で値が変わるため、ビルド時に環境変数から取り込む。
 */

/** ユーザープールID。未設定の場合はnull */
const USER_POOL_ID = import.meta.env.VITE_COGNITO_USER_POOL_ID ?? null;

/** アプリクライアントID。未設定の場合はnull */
const USER_POOL_CLIENT_ID = import.meta.env.VITE_COGNITO_USER_POOL_CLIENT_ID ?? null;

/** Amplify へ渡す認証の設定 */
export const AUTH_CONFIG = {
  Cognito: {
    userPoolId: USER_POOL_ID,
    userPoolClientId: USER_POOL_CLIENT_ID
  }
};

/** 接続情報が揃っているかどうか */
export const HAS_CONFIGURED_AUTH =
  USER_POOL_ID !== null && USER_POOL_CLIENT_ID !== null;

Cognito との通信を service に閉じ込める

ライブラリへの依存をこのファイルだけに留めます。将来ライブラリを差し替える場合も、直すのはここだけになります。 Cognito の例外名を画面に出す日本語へ変換するのもここで行います。

frontend/src/services/authService.js 新規
import {
  getCurrentUser,
  signIn as cognitoSignIn,
  signOut as cognitoSignOut
} from 'aws-amplify/auth';

/**
 * @description Cognito を使った認証処理をまとめる。
 * ライブラリへの依存をこのファイルに閉じ込め、呼び出し側は例外だけを扱う。
 */

/** Cognito が返す例外名と、画面に出す文言の対応 */
const ERROR_MESSAGES = {
  NotAuthorizedException: 'ユーザー名またはパスワードが違います',
  UserNotFoundException: 'ユーザー名またはパスワードが違います',
  UserNotConfirmedException: 'このユーザーは有効化されていません。管理者に連絡してください',
  PasswordResetRequiredException: 'パスワードの再設定が必要です。管理者に連絡してください',
  TooManyRequestsException: '試行回数が多すぎます。しばらく待ってから試してください',
  EmptySignInUsername: 'ユーザー名を入力してください',
  EmptySignInPassword: 'パスワードを入力してください',
  // 仮パスワードのまま（手順書 第1部 Step 5 が未実施）の場合に出る
  CONFIRM_SIGN_IN_WITH_NEW_PASSWORD_REQUIRED:
    'パスワードの初期設定が必要です。管理者に連絡してください'
};

/** 対応表に無い例外に使う文言 */
const DEFAULT_ERROR_MESSAGE = 'ログインに失敗しました。通信状況を確認してください';

/**
 * @description 認証の例外を、画面に出せる文言へ変換する
 * @param {Error} error 発生した例外
 * @returns {string} 画面に出す文言
 */
export const toAuthErrorMessage = (error) =>
  ERROR_MESSAGES[error?.name] ?? DEFAULT_ERROR_MESSAGE;

/**
 * @description ユーザー名とパスワードでサインインする。
 * 通信方式はSRPで、パスワードそのものはネットワークに流れない。
 * @param {string} username ユーザー名
 * @param {string} password パスワード
 * @returns {Promise<void>} 成功時は何も返さない。失敗時は例外を投げる
 */
export const signInWithPassword = async (username, password) => {
  const { isSignedIn, nextStep } = await cognitoSignIn({ username, password });

  if (isSignedIn) {
    return;
  }

  // MFAや初回パスワード変更など、追加の手続きを求められた場合。
  // 対応する画面を用意していないため、失敗として上位へ返す
  const error = new Error(`サインインが完了しませんでした: ${nextStep.signInStep}`);
  error.name = nextStep.signInStep;
  throw error;
};

/**
 * @description サインアウトしてトークンを破棄する
 * @returns {Promise<void>}
 */
export const signOutFromCognito = () => cognitoSignOut();

/**
 * @description 保存されているセッションから、サインイン中のユーザー名を取得する。
 * 再読み込み後にログイン状態を復元するために使う。
 * @returns {Promise<string|null>} ユーザー名。未サインインの場合はnull
 */
export const fetchSignedInUsername = async () => {
  try {
    const { username } = await getCurrentUser();

    return username;
  } catch {
    // 未サインインでも例外になる仕様のため、サインインしていない状態として扱う
    return null;
  }
};

ログイン状態をストアで保持する

ルーターガードと複数の画面から参照するため、Pinia で持ちます（routeStore.js と同じ書き方に揃えています）。

frontend/src/stores/authStore.js 新規
import { computed, ref } from 'vue';
import { defineStore } from 'pinia';
import {
  fetchSignedInUsername,
  signInWithPassword,
  signOutFromCognito,
  toAuthErrorMessage
} from '@/services/authService';

/**
 * @description ログイン状態を保持するグローバルストア。
 * ルーターガードと各画面から参照するため、Piniaで一元管理する。
 */
export const useAuthStore = defineStore('auth', () => {
  /** サインイン中のユーザー名。未サインインの場合はnull */
  const username = ref(null);

  /** Cognito のセッションを確認済みかどうか（再読み込み直後の二重確認を防ぐ） */
  const isSessionRestored = ref(false);

  /** サインインの通信中かどうか */
  const isSigningIn = ref(false);

  /** 直近のサインイン失敗の理由。成功時はnull */
  const errorMessage = ref(null);

  /** サインイン済みかどうか */
  const isSignedIn = computed(() => username.value !== null);

  /**
   * @description 保存されているセッションからログイン状態を復元する
   * @returns {Promise<void>}
   */
  const restoreSession = async () => {
    username.value = await fetchSignedInUsername();
    isSessionRestored.value = true;
  };

  /**
   * @description ユーザー名とパスワードでサインインする
   * @param {string} inputUsername 入力されたユーザー名
   * @param {string} inputPassword 入力されたパスワード
   * @returns {Promise<boolean>} 成功したかどうか
   */
  const signIn = async (inputUsername, inputPassword) => {
    isSigningIn.value = true;
    errorMessage.value = null;

    try {
      await signInWithPassword(inputUsername, inputPassword);
      username.value = await fetchSignedInUsername();

      return true;
    } catch (error) {
      errorMessage.value = toAuthErrorMessage(error);

      return false;
    } finally {
      isSigningIn.value = false;
    }
  };

  /**
   * @description サインアウトする
   * @returns {Promise<void>}
   */
  const signOut = async () => {
    await signOutFromCognito();
    username.value = null;
    errorMessage.value = null;
  };

  return {
    username,
    isSessionRestored,
    isSigningIn,
    errorMessage,
    isSignedIn,
    restoreSession,
    signIn,
    signOut
  };
});
7
入力フォームのコンポーネントを作る

認証は行わず、入力値を親へ渡すだけにします。 BaseButton は type="button" 固定でフォーム送信ができないため、 Enter キーでログインできるようここでは type="submit" のボタンを使い、見た目は共通クラスの primary-btn を借ります。

frontend/src/components/feature/auth/LoginForm.vue 新規
<script setup>
import { ref } from 'vue';

/**
 * @description ユーザー名とパスワードの入力欄を提供する。
 * 認証は行わず、入力された値を親へ渡すだけに留める。
 */
defineProps({
  /** サインインの通信中かどうか */
  isSigningIn: {
    type: Boolean,
    default: false
  },
  /** 表示するエラーの文言。無い場合はnull */
  errorMessage: {
    type: String,
    default: null
  }
});

const emit = defineEmits(['submitLogin']);

/** 入力中のユーザー名 */
const username = ref('');

/** 入力中のパスワード */
const password = ref('');

/**
 * @description 入力値を親へ渡す。
 * 前後の空白はコピー貼り付けで混ざりやすいため、ユーザー名だけ取り除く。
 * @returns {void}
 */
const handleSubmit = () => {
  emit('submitLogin', {
    username: username.value.trim(),
    password: password.value
  });
};
</script>

<template>
  <form
    class="login-form"
    @submit.prevent="handleSubmit"
  >
    <label class="login-field">
      <span class="login-label">ユーザー名</span>
      <input
        v-model="username"
        type="text"

ルーターにログイン判定を追加する

既存のガード（ルート未取得なら条件入力へ戻す）と1つの beforeEach にまとめ、 ログイン判定 → ルート取得判定 の順で見ます。ガードを2つに分けると実行順が読みにくくなるためです。

frontend/src/router/index.js 変更（全文）
import { createRouter, createWebHistory } from 'vue-router';
import LoginView from '@/views/LoginView.vue';
import RouteConditionView from '@/views/RouteConditionView.vue';
import RouteNavigationView from '@/views/RouteNavigationView.vue';
import RouteSuggestionView from '@/views/RouteSuggestionView.vue';
import WalkResultView from '@/views/WalkResultView.vue';
import { useAuthStore } from '@/stores/authStore';
import { useRouteStore } from '@/stores/routeStore';

/**
 * @description URLと画面の対応を定義する。
 * ローディングと終了確認はURLを持たない表示状態のため、Viewには含めない。
 */
const routes = [
  {
    path: '/login',
    name: 'login',
    component: LoginView,
    // 未ログインで開ける唯一の画面
    meta: { isPublic: true }
  },
  {
    path: '/',
    name: 'route-condition',
    component: RouteConditionView
  },
  {
    path: '/suggestion',
    name: 'route-suggestion',
    component: RouteSuggestionView,
    meta: { requiresRoute: true }
  },
  {
    path: '/navigation',
    name: 'route-navigation',
    component: RouteNavigationView,
    meta: { requiresRoute: true }
  },
  {
    path: '/result',
    name: 'walk-result',
    component: WalkResultView,
    meta: { requiresRoute: true }
  },
  {
    path: '/:pathMatch(.*)*',
    redirect: { name: 'route-condition' }
  }
];

const router = createRouter({
  history: createWebHistory(),
  routes,
  scrollBehavior: () => ({ top: 0 })
});

// ログイン状態とルート取得状態を、この順で見て遷移を決める
router.beforeEach(async (to) => {
  const authStore = useAuthStore();

  // 再読み込み直後はストアが空になるため、残っているセッションを一度だけ確認する
  if (!authStore.isSessionRestored) {
    await authStore.restoreSession();
  }

  if (to.meta.isPublic) {
    // ログイン済みならログイン画面には留まらせず、ホームへ送る
    return authStore.isSignedIn ? { name: 'route-condition' } : true;
  }

  if (!authStore.isSignedIn) {
    return { name: 'login' };
  }

  if (!to.meta.requiresRoute) {
    return true;
  }

  const routeStore = useRouteStore();

  // ルート未取得の状態で直接URLを開いた場合は条件入力へ戻す
  return routeStore.hasRoute ? true : { name: 'route-condition' };
});

export default router;

5. dev 環境へ反映する場合

.env.local はローカル専用です。GitHub Actions でビルドされる dev/prod 環境では値が入らず、 ログインできない状態のアプリが配信されます。CloudFront 上で動かすには、ビルドステップへ環境変数を渡します。

  1. GitHub のリポジトリ設定 → Settings → Secrets and variables → Actions → Variables タブ
  2. VITE_COGNITO_USER_POOL_ID と VITE_COGNITO_USER_POOL_CLIENT_ID を登録する
    シークレットではないため Variables で十分です（Secrets にしても動きます）。
  3. .github/workflows/deploy.yml のビルドステップに env を追加する
.github/workflows/deploy.yml（抜粋）変更
      - name: フロントエンドをビルドする
        working-directory: frontend
        env:
          VITE_COGNITO_USER_POOL_ID: ${{ vars.VITE_COGNITO_USER_POOL_ID }}
          VITE_COGNITO_USER_POOL_CLIENT_ID: ${{ vars.VITE_COGNITO_USER_POOL_CLIENT_ID }}
        run: |
          npm ci
          npm run build
dev と prod で別のユーザープールを使う場合

GitHub の Environments（dev / prod）を作り、環境ごとに同名の Variables を持たせます。 今回はコンソールで dev 用を1つ作っただけなので、まずは共通のリポジトリ Variables で構いません。

SPA のディープリンク（/login を直接開く）は、CloudFront の 403/404 を /index.html へ返す設定が iac/lib/michishiru-stack.ts に既にあるため、追加作業は不要です。

7. つまずきやすい点

症状原因対処
コンソールに Auth UserPool not configured .env.local が無い、または dev サーバーを再起動していない ファイルを確認し、npm run dev を再起動する
ResourceNotFoundException: User pool client ... does not exist アプリクライアントIDの誤り、またはリージョン違いのプールを見ている ユーザープールIDの先頭が ap-northeast-1_ になっているか、クライアントIDを取り違えていないか確認する
「パスワードの初期設定が必要です」と出る ユーザーが FORCE_CHANGE_PASSWORD のまま（第1部 Step 5 未実施） CloudShell で admin-set-user-password --permanent を実行する
正しいパスワードなのに「ユーザー名またはパスワードが違います」 Cognito は既定で「ユーザーが存在しない」ことを隠すため、ユーザー名の誤りも同じ文言になる コンソールの ユーザー タブでユーザー名の綴りとステータスを確認する
InvalidParameterException: USER_PASSWORD_AUTH flow not enabled signIn に authFlowType を指定して平文方式を使おうとしている 指定を外す。既定の SRP を使えばこのエラーは出ない
ログイン成功後もログイン画面に戻される signIn 後に username をストアへ入れていない authStore.signIn 内の fetchSignedInUsername の呼び出しを確認する
画面が真っ白で何も出ない main.js の import 追加ミス、またはガードが例外で止まっている ブラウザの開発者ツールのコンソールを見る

8. セキュリティ上おさえておくこと

🚨 ログイン画面を付けても API は保護されない

ルーターガードは画面の出し分けだけです。API Gateway は現在も未認証で公開されているため、 エンドポイントのURLを知っていれば誰でも /api/* を直接呼べます。 「認証を入れた」と言える状態にするには、API Gateway に Cognito オーソライザーを追加する作業が別途必要です（9章）。

項目現状備考
トークンの保存先 localStorage（ライブラリの既定） XSS があればトークンを抜かれる。innerHTML への外部入力の埋め込みを避ける
クライアントシークレット 無し（SPA用クライアント） フロントに置けないため、これが正しい構成
MFA 無効 必要になったらユーザープールの サインイン タブで有効化。アプリ側に確認コード入力画面の追加が必要
セルフサインアップ 無効（第1部 Step 3） 有効なままだと第三者がアカウントを作れる
パスワードポリシー 既定（8文字以上・4種混在） 変更する場合は 認証 → パスワードポリシー
ログイン試行の制限 Cognito 側で自動（連続失敗でスロットリング） アプリ側の実装は不要

9. この作業の後に残る課題

#課題内容
1 API Gateway の保護 メソッドに Cognito オーソライザー（authorizationType: COGNITO_USER_POOLS）を付け、 フロントは fetchAuthSession() で取り出した idToken を Authorization ヘッダーに付けて送る。 routeService.js / conditionService.js の共通化が必要
2 CDK への移行 今回コンソールで作ったユーザープールは CDK の管理外。 ミチシル_前提条件.md の「マスタテーブルのCDK管理」と同じ状態が増えるため、 環境分離（dev/prod）と合わせて iac/ へ取り込む
3 ドキュメントの更新 ミチシル_前提条件.md の「認証・認可: 未定」を Cognito 採用として「確定した要素」へ移し、構成図に Cognito を追加する。 naming-glossary.md に認証の用語（login / signIn / signOut の使い分け）を登録する
4 ユーザーストーリーの整理 ログイン画面は US-1 より前に位置する画面。US として受け入れ条件を起こし、docs/設計書.md の画面遷移図を更新する
5 初回パスワード変更・パスワード再設定 現状は管理者が CLI で恒久パスワードを設定する運用。ユーザー自身が変更できる画面が無い
6 ユーザー単位のデータ管理 ログインしても保存されるルートは全ユーザー共通。DynamoDB のキー設計に userId（Cognito の sub）を入れるか検討する
✅ 用語について

画面の名前は「ログイン画面」、コード上の関数名は signIn / signOut で書いています （Cognito と Amplify の API 名が signIn のため、揃えたほうが読みやすい）。 辞書へ登録する際はこの使い分けも書き添えてください。
