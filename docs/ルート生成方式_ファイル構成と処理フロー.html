1. この機能の概要

ユーザーが入力したジャンル・目標距離・現在地から、散歩ルートを自動生成して地図に表示します。

条件を入力
ジャンル / 距離
→
周辺スポットを
検索
→
AIが2〜3件
選定
→
徒歩ルートを
計算
→
距離が超過なら
スポットを削る
→
GeoJSONで返す
地図に描画

既存の getRoute（DBに登録済みのルートを取得）とは別の機能です。条件から新しく生成するため、Lambda の論理名を generateRoute としています。

API は POST /api/v1/routes、成功時 201。 既存の GET /api/v1/routes とはメソッドが違うため同じパスで共存できます。「取得」と「作成」を REST として自然に表現できる形です。

3. ファイルごとの役割

バックエンド

ファイル区分役割
handler.js新規 Lambda の入口。event.body（文字列）を JSON へ戻し、Validator を呼び、結果を { statusCode, headers, body } の形へ整えて返す。ビジネス判断は持たない。JSONとして解釈できないボディは 400 で弾く。
validator.js新規 genre / distance / lat / lng の必須・型・範囲を検査する純粋関数。エラーは全件集めて返すため、1回の応答で不足がすべて分かる。データ取得も副作用も持たない。
service.js新規 この機能の中核。① Repository の4関数を順番に呼ぶ、② 実測距離が目標を大幅超過したらスポットを削って再計算する、③ 結果を GeoJSON へ組み立てる。HTTP に依存せず、プレーンなオブジェクトを受け取って返す。
repository.js新規 外部サービスへのアクセスをすべてここに閉じ込める。4つの関数を公開し、段階1a は固定データ、段階1b は実サービスを呼ぶ。中身が変わっても入出力は変えないため、Service 以上は影響を受けない。
constants.js新規 許可値（ALLOWED_GENRES）、距離の上下限、徒歩の分速、超過の許容倍率（DISTANCE_OVERSHOOT_RATIO）、featureKind の値などを定義する。環境変数を読むのはこのファイルだけにする（段階1bでモデルIDを追加）。
package.json新規 関数ごとの依存関係の記録。name は generate-route（npm がパッケージ名に大文字を許可しないため、フォルダ名の camelCase と一致しない）。
shared/ 配下― 変更しない。errorCodes.js / errorHandler.js / logger.js / responseBuilder.js を getRoute と共用する。エラーコードもレスポンス形式も既存と同じになる。

4. 処理のデータフロー

ボタン押下から地図描画までを、データの形の変化とあわせて追います。

1

RouteGenerationSpikeView.vue

ユーザーが条件を選び、生成ボタンを押す。現在地は既定で東京駅、ボタン操作で端末の位置情報に差し替えられる。

generate({ genre: 'nature', distanceKm: 3, origin: { lat: 35.681236, lng: 139.767125 } })
2

useRouteGeneration.js

isGenerating を true にしてから service を呼ぶ。成否を boolean で返し、エラーは errorMessage に載せる。

3

routeService.js

内部表現の distanceKm を API の distance へ、origin を lat / lng へ展開して POST する。

POST /api/v1/routes
{ "genre": "nature", "distance": 3, "lat": 35.681236, "lng": 139.767125 }

単位を落とすのは naming-conventions.md の例外規定（API のキーは km 固定の distance）に従うため。

4

handler.js

文字列のボディを JSON へ戻し、Validator を呼ぶ。不正なら 400 とメッセージを返してここで終わる。

{ "code": "VALIDATION_ERROR", "message": "genreは必須です / distanceは1以上10以下で指定してください" }
5

service.js → repository.js ①

検索キーワードを取得する。ジャンルに対応する英語の検索語を得る。地図APIへは英語で問い合わせるため。

getSearchKeywords({ genre: 'nature' })
→ ['park', 'garden', 'riverside']
6

service.js → repository.js ②

周辺スポットを検索する。現在地の周りにある実在の場所を15〜20件集める。0件なら ROUTE_NOT_FOUND（404）で終了。

searchNearbySpots({ origin, genre, searchKeywords })
→ [{ spotId, name: '大手町の森', spotType: 'park', lat, lng, distanceFromOrigin }, ...]
7

service.js → repository.js ③

AIがスポットを選び、文言を作る。候補と条件を渡し、2〜3件の選定・コース名・紹介文を一度の呼び出しでまとめて得る。

selectSpotsByAi({ genre, distance, candidates })
→ { routeName: '自然をたどる3スポットコース',
    story: '大手町の森、KITTE屋上庭園…をめぐります。',
    spots: [{ spotId, name, spotType, lat, lng, description }, ...] }
呼び出しは1回だけ。回数がそのまま費用と応答時間に効くため、選定と文言生成を1つのプロンプトに束ねます。
8

service.js → repository.js ④

徒歩ルートを計算する。現在地を発着点にスポットを巡る周回ルートの実距離・所要時間・道沿いの座標列を得る。

calculateWalkingRoute({ origin, spots })
→ { distance: 2.28, duration: 34, waypoints: [{ lat, lng }, ... 49点] }
9

service.js

距離の調整。実測が目標の1.25倍を超えていたら、AIを呼び直さず末尾のスポットを配列から取り除いて ④ を再実行する。MIN_SPOT_COUNT を下回るまで繰り返す。

目標 1km / 実測 2.28km → 許容 1.25km を超過
  スポット 3件 → 2件 → 1件、実測 1.52km、経路 25点で確定

AI の再呼び出しに比べて速く、費用も増えません。

10

service.js

GeoJSON を組み立てる。ルート線・出発地・スポットを1つの FeatureCollection にまとめる。ここで座標を { lat, lng } から [経度, 緯度] へ入れ替える（GeoJSON の仕様。入れ替えるのはこの1箇所だけ）。

11

handler.js

201 で返す。

{ "routeId": "...", "routeName": "...", "story": "...",
  "distance": 2.28, "duration": 34, "spotCount": 3,
  "origin": { "lat": ..., "lng": ... },
  "spots": [ ... ],
  "geojson": { "type": "FeatureCollection", "features": [ ... ] } }
12

RouteGeoJsonMap.vue

geojson をそのままソースへ登録し、featureKind の filter で3つのレイヤーへ振り分ける。全 feature が収まるよう表示範囲を合わせる。

route  → line レイヤー（緑の線）
spot   → circle レイヤー（橙の丸）+ DOMマーカー（番号と名前）
origin → circle レイヤー（青の丸）

5. GeoJSON の構造

1つの FeatureCollection にすべてを入れます。フロントエンドが加工せずそのまま地図ライブラリへ渡せる形にするためです。

featureKindgeometry個数properties
routeLineString1―
originPoint1name
spotPoint1〜3spotId / name / spotType / visitOrder
{
  "type": "FeatureCollection",
  "features": [
    { "type": "Feature",
      "properties": { "featureKind": "route" },
      "geometry": { "type": "LineString",
                    "coordinates": [[139.767125, 35.681236], ... ] } },
    { "type": "Feature",
      "properties": { "featureKind": "origin", "name": "現在地" },
      "geometry": { "type": "Point", "coordinates": [139.767125, 35.681236] } },
    { "type": "Feature",
      "properties": { "featureKind": "spot", "spotId": "...", "name": "大手町の森",
                      "spotType": "park", "visitOrder": 1 },
      "geometry": { "type": "Point", "coordinates": [139.7645, 35.687] } }
  ]
}

spot と waypoint を分けている理由

混同すると、エラーにならず数字だけが狂います。

用語辞書では spot が「ユーザーが立ち寄る場所」、waypoint が「経路を描くための座標の点」です。3スポットのルートで LineString は49点になります。ここを混同すると US-8 の「廻ったスポット数」が 3 ではなく 49 と表示されます。

既存の getRoute は waypoints しか返さず、これが naming-conventions.md の未決定事項 #2 に挙がっている負債です。新APIでは spots（配列）と spotCount（数値）を独立して返し、経路の点は GeoJSON の中だけに閉じ込めます。

6. 段階1a と 段階1b の差分

変わるのは repository.js の中身だけです。関数の名前と入出力を先に固定してあるため、Service 以上は書き換えません。

Repository の関数1a 固定データ1b 実サービス
getSearchKeywordsconstants.js の対応表を返すDynamoDB（検索条件マスタ）
searchNearbySpots東京駅周辺18件から絞って返すLocation Service Places（SearchNearby）
selectSpotsByAi候補から3件選びテンプレートで文言生成Bedrock（InvokeModel）
calculateWalkingRoute座標を補間し球面距離を合計Location Service Routes（CalculateRoutes）
どちらの段階でも AWS リソースは1つも作りません。 Location Service の Places / Routes は API v2 でリソース作成が不要になり、Bedrock も基盤モデルの利用が既定で有効です。必要なのは実行ロールの IAM 権限だけなので、CloudFormation スタックに差分が出ず、dev / prod への影響は物理的に発生しません。

段階1a の calculateWalkingRoute は、各区間に12点の中間座標を作り進行方向の横へわずかにずらして曲線に見せています。直線で結ぶと道なりの形にならず、地図描画の確認材料にならないためです。

8. 注意点

MapLibre 導入でつまずいた3点（実際に踏んだ）

3つのうち2つは「無言で描画されない」症状になります。エラーが画面にもコンソールにも出ないため、原因の特定に時間がかかります。

① default エクスポートが存在しない

maplibre-gl の6系は ESM で default エクスポートを持ちません。ビルドが [MISSING_EXPORT] で失敗するため、これは気付けます。

// 失敗する
import maplibregl from 'maplibre-gl';

// 正しい書き方（Map は Vue 側の名前と衝突しうるためリネームする）
import { LngLatBounds, Map as MapLibreMap, Marker, NavigationControl } from 'maplibre-gl';

② Vite の依存最適化が Web Worker を壊す

MapLibre は GeoJSON の解析を Web Worker で行いますが、Vite の依存最適化を通すと Worker のファイルが見つからなくなります。

The file does not exist at ".../node_modules/.vite/deps/maplibre-gl-worker.mjs"
which is in the optimize deps directory.

frontend/vite.config.js で除外し、依存最適化のキャッシュ（node_modules/.vite）を削除して開発サーバを再起動します。

optimizeDeps: {
  exclude: ['maplibre-gl']
}

Worker が読めないと GeoJSON ソースが読み込まれず、それを参照する line / circle レイヤーが何も描きません。一方 Marker は DOM 要素なので影響を受けず表示されます。結果として「スポットのラベルだけ出て、線と丸が出ない」という症状になります。

③ リアクティブな値をそのまま渡せない

MapLibre は GeoJSON を Worker へ postMessage で渡すため構造化複製（structured clone）が行われます。Vue のリアクティブ Proxy は構造化複製できず DataCloneError になります。

渡す値構造化複製
素のオブジェクト成功
reactive(obj)失敗（DataCloneError）
ref(obj).value失敗（DataCloneError）
shallowRef(obj).value成功
toRaw(ref(obj).value)成功

対策は2段構えにしています。useRouteGeneration の generatedRoute を shallowRef にし、RouteGeoJsonMap 側でも toRaw() で素の値へ戻してから渡します。あわせて map.on('error', ...) を追加しました。MapLibre の失敗は例外にならずこのイベントへ流れるため、リスナーが無いと無言で描画されないだけになります。

この機能に固有の注意

  • 座標の順序。GeoJSON は [経度, 緯度]、アプリ内は { lat, lng } で順序が逆。入れ替えは service.js の1箇所に限定する。
  • 応答時間。スポット検索 → AI → ルート計算（+超過時の再計算）が直列に並ぶ。API Gateway の統合タイムアウトは29秒が上限で、超える場合は非同期化が必要になり構成が変わる。段階1bで実測する。
  • 費用。Bedrock と Location Service はユーザー操作1回ごとに課金される。再作成（US-5）で繰り返し呼ばれる点も含めて見積もる。
  • ベースマップは段階1aでは出さない。地図タイルの配信には認証が必要で、そのキーはブラウザへ露出する。線とスポットの位置関係の確認だけなら不要。表示する場合の選択肢は下の「未決定事項」を参照。
  • 文字描画に symbol レイヤーを使わない。MapLibre で text-field を使うにはフォント（glyphs）の配信元が必要になるため、ラベルは DOM マーカーで表示する。
  • バンドルサイズ。maplibre-gl の導入で index.js が約1.1MB（gzip 302kB）になり、Vite が500kB超の警告を出す。本採用時は地図コンポーネントを動的 import() で分割する余地がある。

後で考慮する事項

立ち寄り順が地理的に最適化されないため、ルートが自己交差します。段階1a では候補配列から順に3件取るだけなので、現在地→スポット1→2→3→現在地を結ぶと線が交差します。段階1bでAIに順序を任せた場合も同じ問題が起きえます。プロンプトで「移動距離が短くなる順に並べる」と指示するか、選定後にプログラム側で並べ替えるかを決める必要があります。距離の計算にも影響するため、段階1bの実測前に方針を決めるのが望ましいです。

目標距離を下回るケースがあります。目標3km に対しジャンル「街歩き」で 0.88km になりました。距離調整は超過時にスポットを削る方向にしか働かず、不足時に伸ばす処理がありません。フロー案1どおりの挙動ですが、実用上は下振れの扱いを決める必要があります。

既存コードとの関係で確認が必要な点

ルート作成の失敗時に画面から復帰できません。develop の RouteConditionView.vue は useRouteCreation から errorMessage を受け取っておらず、createRoute が失敗しても isCreating が解除されません。結果としてロード画面のまま原因も表示されず、リロード以外に復帰手段がありません。「応答を待ち続ける」意図的な仕様だとしても出口が必要と考えられるため、NZ-1 の担当者への確認事項です。

getRoute の距離チェックがマスタと不一致です。ALLOWED_DISTANCES_KM が [1, 3, 5, 8] の列挙のため、マスタの範囲（1〜10km）で 2km や 4km を選ぶと弾かれます。既存の負債で、新設する generateRoute は最初から 1〜10 の範囲チェックにしてあります。

ジャンルの許可値（nature / city / history / gourmet）はマスタの genreId と一致していることが 検索条件マスタAPI連携_実装説明書.md で確認済みです。
